# Практика: Диагностический поток Framework

## 1. Политика доказательств
Определите минимальные доказательства для падения assertion: идентичность теста, project, окружение, seed, идентификатор сценария, ошибку и выбранный артефакт.

## 2. Предскажите результат
Failure hook сам падает до создания вложения. Какая ошибка может замаскировать исходное падение?

## 3. Связывание данных
Свяжите структурированный журнал, вложение и отчёт одним идентификатором сценария без включения секрета.

## 4. Граница хранения
Разделите временный output, результаты reporter и опубликованный отчёт. Укажите владельцев очистки и срока хранения.

## 5. Automation QA-задача
Проверьте достаточность диагностики: можно ли воспроизвести отказ, сузить поиск и проверить гипотезу без данных production?

## 6. Мини-проект: диагностический поток
Объедините steps теста, безопасные журналы, ограниченную цепочку `Error.cause`, failure hook, доказательства Playwright и metadata отчёта. Проверьте значение не типа `Error` и циклическую цепочку cause. Основной набор тестов должен оставаться зелёным, а контролируемое падение — возвращать exit code `1`.
