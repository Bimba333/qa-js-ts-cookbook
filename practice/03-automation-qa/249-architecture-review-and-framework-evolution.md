# Практика: Architecture review и эволюция Framework

## 1. Evidence
Отделите наблюдаемый архитектурный сигнал от предпочтения автора. Приведите примеры цикла, global state или разрозненного чтения config и один пример личного предпочтения.

## 2. Coupling и cohesion
Объясните, почему изменение API transport обычно не должно требовать правки UI tests и что такая область влияния говорит о coupling.

## 3. Предскажите решение
Review получил цикл с severity `high` и дублирующийся helper с severity `low`. Какой refactoring должен быть первым и почему?

## 4. Speculative abstraction
Найдите проблему в предложении добавить универсальный DI container до появления подтверждённой потребности в другом способе сборки зависимостей.

## 5. Automation QA-задача
Составьте контрольный список для fixture scopes, владельца cleanup, `cause` ошибки, диагностики shard и публичных границ. Для каждого пункта укажите наблюдаемый сигнал.

## 6. Мини-проект: review decision
Реализуйте детерминированную функцию выбора следующего refactoring по severity и evidence. Равные сигналы сравнивайте без зависимости от locale; при отсутствии сигналов функция не должна придумывать изменение.
