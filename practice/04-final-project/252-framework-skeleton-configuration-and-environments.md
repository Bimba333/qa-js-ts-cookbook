# Практика: Каркас, configuration и environments

## 1. Классификация значений конфигурации

Распределите записи по категориям:

- необработанный ввод;
- проверенная конфигурация;
- профиль;
- ссылка на секрет;
- значение секрета;
- несекретные метаданные CI.

Записи:

1. `process.env.QA_UI_BASE_URL`;
2. `config.uiBaseUrl`;
3. строка `local`;
4. `secret://ci/qa-credentials`;
5. фактический пароль тестовой учётной записи;
6. `GITHUB_RUN_ID`;
7. `QA_OPERATION_TIMEOUT_MS="5000"`;
8. `config.operationTimeoutMs`.

Для каждой записи объясните:

- где она появляется;
- кто имеет право её читать;
- нужна ли проверка во время выполнения;
- можно ли включать её в сообщение об ошибке или log.

**Ожидаемый результат:** таблица из восьми строк с категорией, границей-владельцем и правилом безопасности.

**Критерии оценки:** необработанный ввод не назван конфигурацией; профиль не назван хранилищем секретов; ссылка отделена от значения секрета; числовая строка не считается числом до разбора.

## 2. Аудит границы необработанного ввода

Найдите нарушения:

```ts
// fixture.ts
const profile = process.env.QA_PROFILE ?? "production";

// rest-client.ts
const baseUrl = process.env.QA_REST_BASE_URL;

// composition-root.ts
const timeout = Number(process.env.QA_OPERATION_TIMEOUT_MS);

// test.ts
console.log(process.env.QA_CREDENTIALS_REF);
```

Предложите новое направление зависимостей без реализации REST-клиента:

```text
process.env
→ ? (граница-владелец)
→ ? (преобразование)
→ Composition Root
→ минимальный контекст
```

Для каждого исходного нарушения укажите риск, новую границу-владельца и способ проверить исправление.

**Ожидаемый результат:** исправленная схема, список четырёх нарушений и проверяемые правила импортов и чтения.

**Критерии оценки:** `process.env` остаётся в одном исполняемом модуле; значение `production` по умолчанию удалено; Composition Root получает готовую конфигурацию; ссылка на секрет не логируется без необходимости.

## 3. Исправление проверки во время выполнения

Исправьте функцию:

```ts
type Config = Readonly<{
  profile: "local" | "ci";
  timeoutMs: number;
}>;

function loadConfig(source: Record<string, string | undefined>): Config {
  return {
    profile: source.QA_PROFILE as "local" | "ci",
    timeoutMs: Number(source.QA_OPERATION_TIMEOUT_MS),
  };
}
```

Требования:

- отсутствующий `QA_PROFILE` вызывает ошибку с именем ключа;
- разрешены только `local` и `ci`;
- timeout должен быть целым числом от `100` до `120000`;
- ошибка не печатает необработанное значение;
- функция не возвращает частичную конфигурацию;
- результат нельзя изменить во время выполнения;
- непроверенное утверждение типа запрещено.

Добавьте минимум четыре целенаправленных теста.

**Ожидаемый результат:** рабочая функция и тесты для успешного результата, отсутствующего ключа, неподдерживаемого профиля и неправильного timeout.

**Критерии оценки:** проверка происходит до построения; возвращается полный замороженный объект; ошибки полезны и безопасны; `any`, `@ts-ignore` и непроверенные утверждения типа отсутствуют.

## 4. Частичное построение и очистка

Разберите код:

```ts
async function createRuntime() {
  const first = await acquireFirst();
  const second = await acquireSecond();

  registerCleanup(() => first.close());
  registerCleanup(() => second.close());
}
```

Объясните, что произойдёт, если `acquireSecond()` завершится ошибкой.

Перестройте алгоритм так, чтобы:

- очистка регистрировалась после каждого успешного получения ресурса;
- уже полученные ресурсы закрывались в обратном порядке;
- ошибка построения оставалась основной;
- ошибка очистки не терялась;
- повторный `close()` не считался безопасным без явного контракта.

Код можно выразить через `ResourceScope` главы 252 или эквивалентный минимальный механизм.

**Ожидаемый результат:** исправленный алгоритм и тест, моделирующий ошибку при получении второго ресурса.

**Критерии оценки:** первый ресурс не протекает; LIFO доказан; основная ошибка и ошибка очистки наблюдаемы; service locator и глобальный реестр очистки не появляются.

## 5. Области жизни ресурсов каркаса

Для каждой записи выберите test scope, worker scope или независимую от процесса внешнюю область жизни:

| Ресурс | Факты |
| --- | --- |
| `RuntimeConfig` | Неизменяемый снимок одного запуска |
| `FoundationContext` | Выдаётся конкретному smoke-тесту |
| `ResourceScope` | Владеет очисткой конкретного runtime |
| `.env.example` | Зафиксированный шаблон без значений секретов |
| Внешний SUT | Создан не framework и живёт независимо |
| Будущий browser context | Содержит изменяемое состояние теста |

Для каждой записи укажите владельца, допустимость совместного использования, момент очистки и риск неправильной области жизни.

Отдельно ответьте: означает ли worker scope автоматическую изоляцию бизнес-данных?

**Ожидаемый результат:** таблица жизненного цикла из шести строк и аргументированный ответ об изоляции.

**Критерии оценки:** внешний SUT не закрывается каркасом; изменяемый browser context не разделяется по умолчанию; область жизни следует из владения и изменяемости, а не только из стоимости.

## 6. Мини-проект: расширение проверок каркаса

Выполните:

```bash
npm run final-project:typecheck
npm run final-project:startup
npm run final-project:test
```

Затем добавьте один целенаправленный негативный тест для одного случая:

- URL содержит учётные данные;
- каталог артефактов является абсолютным;
- каталог артефактов содержит `..`;
- gRPC port выходит за диапазон;
- `QA_PROFILE=local` конфликтует с `CI=true`.

Тест должен:

- выполняться без браузера и внешней сети;
- проверять точный ключ конфигурации;
- не включать чувствительное необработанное значение в вывод проверки;
- не менять исполняемый код только ради теста;
- сохранять границу главы 253.

После изменения выполните:

```bash
npm run final-project:check
```

**Ожидаемый результат:** новый негативный тест сначала демонстрирует проверяемое правило, затем полная проверка каркаса завершается успешно.

**Критерии оценки:** тест детерминирован; компиляция TypeScript проходит; retries не используются; реализация UI, REST, gRPC или database не добавлена.
