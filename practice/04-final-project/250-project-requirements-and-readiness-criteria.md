## 1. Классификация утверждений

Классифицируйте каждое утверждение как требование, деталь реализации, архитектурное решение, критерий приёмки, задачу или доказательство.

1. Проект обязан обеспечивать запуск полного обязательного набора с двумя workers и `retries: 0`.

3. Выбран один pool на worker, потому что SUT ограничивает число соединений.

## 2. Проверка пригодности SUT

Команда рассматривает учебный SUT со следующими свойствами:

- UI и REST доступны в учебной среде;
- unary gRPC существует, но `.proto` команда не выдаёт;
- PostgreSQL доступен только для чтения;
- REST предоставляет разрешённое удаление созданных тестовых сущностей;
- среда выполнения GitHub Actions не может достичь сервиса gRPC;
- владелец системы разрешил автоматизацию учебной среды.

Определите статус каждой обязательной возможности и итоговое решение по SUT. Для каждого блокирующего условия укажите владельца, следующее действие и безопасное доказательство, необходимое для снятия блокировки.

**Ожидаемый результат:** матрица возможностей и решение `PASS`, `BLOCKED` или `FAIL`. Не предлагайте имитацию сервиса gRPC вместо обязательной интеграции.

5. Очистка должна быть хорошей.

Для каждого требования добавьте ID, главу-владельца, способ проверки, связанный сценарий или область проекта, ожидаемое доказательство и признак обязательности.

## 6. Мини-проект: решение о готовности

Подготовьте заключение о готовности выбранного SUT. Известно:

- учётные данные для UI и REST будут выданы владельцем через разрешённое хранилище секретов;
- gRPC `.proto` доступен;
- PostgreSQL schema неизвестна, но read access согласован;
- тестовые сущности имеют уникальные идентификаторы;
- операция очистки существует только для сущностей, созданных через REST;
- сущность, созданную через UI, пока нельзя удалить;
- все сервисы доступны локально;
- доступность из CI ещё не проверена;
- команда хочет начать Page Objects немедленно.

Составьте:

1. решение о пригодности SUT;
2. три главных риска;
3. блокирующие условия с владельцами и следующими действиями;
4. минимальное доказательство для снятия блокировок;
5. решение, можно ли переходить к главе 251;
6. условия, при которых решение изменится.

**Ожидаемый результат:** краткое заключение о готовности. Не предлагайте реализацию framework и не включайте настоящие учётные данные, адреса сервисов или разрушительные операции.
