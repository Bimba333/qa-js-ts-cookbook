## 2. Проверка пригодности SUT

### Ответ

| Возможность | Статус | Причина |
| --- | --- | --- |
| UI | PASS | Разрешённый доступ к учебной среде подтверждён |
| REST | PASS | Доступ и очистка подтверждены |
| unary gRPC | FAIL | Подтверждено, что команда не предоставляет обязательный `.proto` |
| PostgreSQL | PASS | Доступ для чтения есть, очистка разрешена через REST |
| Доступность из CI | FAIL | Среда выполнения не достигает обязательного сервиса gRPC |

Итоговое решение — `FAIL`: обязательный `.proto` подтверждённо недоступен, а CI не достигает обязательного сервиса. Владельцы: владелец сервиса для контракта и владелец платформы или сервиса для сетевого маршрута CI. Следующие действия: пересмотреть возможность предоставить версионируемый `.proto` и разрешённый сетевой маршрут; если это невозможно, выбрать другой SUT. Доказательства: безопасная запись решений и проверок доступа без учётных данных и закрытых адресов.

### Объяснение

Доступ к PostgreSQL только для чтения допустим, если обязательная операция очистки выполняется через API и подтверждена. Однако отсутствие `.proto` и доступа из CI нарушает обязательную спецификацию.

### Типичная ошибка

Заменять недоступный gRPC локальной имитацией и отмечать обязательную возможность как выполненную.

### Связь с Automation QA

Проверка пригодности останавливает дорогостоящую реализацию до того, как инфраструктурное ограничение обнаружится в конце проекта.

## 3. Аудит записи сценария

### Ответ

Проблемы: отсутствует короткое название; цель расплывчата; не указаны входные данные или бизнес-идентификатор; отсутствует владелец настройки; предусловие непроверяемо; ожидаемый результат неизмерим; способ очистки не определён; владелец очистки указан слишком общо; одного снимка экрана недостаточно для проверки базы данных; возможность запуска в CI неизвестна; `PASS` выставлен без доказательства; риск отсутствует.

Исправленный вариант:

| Поле | Значение |
| --- | --- |
| ID | `XL-02` |
| Название | Создание через UI сохраняется в PostgreSQL |
| Бизнес-цель | Подтвердить сохранение созданной пользователем test entity |
| Слои | Действие в UI → проверка в PostgreSQL |
| Предусловия | Разрешённая тестовая учётная запись и доступная учебная среда |
| Владелец настройки | Сценарий `XL-02`, данные принадлежат тесту |
| Тестовые данные | Уникальный бизнес-идентификатор, принадлежащий тесту |
| Действие | Создать сущность через разрешённый UI-сценарий |
| Ожидаемый результат | PostgreSQL содержит одну запись с тем же идентификатором и ожидаемым нормализованным статусом |
| Владелец очистки | Сценарий `XL-02`, владеющий тестовыми данными |
| Способ очистки | Разрешённая операция очистки через API либо иной согласованный механизм |
| Доказательство | Бизнес-идентификатор, снимок экрана UI при ошибке и очищенное сравнение с базой данных |
| Возможность запуска в CI | Требует подтверждённого доступа среды выполнения к UI и PostgreSQL |
| Риск | Очистка сущности, созданной через UI, ещё не подтверждена |
| Статус | BLOCKED до подтверждения очистки и доступа из CI |

### Объяснение

Сценарий становится проверяемым, когда действие, ожидаемый результат, владение и доказательство сформулированы независимо от будущей реализации.

### Типичная ошибка

Исправлять запись добавлением конкретного селектора или SQL-запроса вместо уточнения бизнес-результата.

### Связь с Automation QA

Точная запись заранее определяет, какие данные и доказательства обязан сохранить межслойный тест.

## 6. Мини-проект: решение о готовности

### Ответ

Проверка пригодности: UI, REST и unary gRPC предварительно доступны; доступ к PostgreSQL предварительно доступен; доступность из CI — `BLOCKED`; очистка сущности, созданной через UI, — `BLOCKED`, поскольку возможность пока не подтверждена. Итог — `BLOCKED`.

Главные риски: невозможность удалить данные, созданные через UI; недоступность сервисов из CI; неизвестная схема базы данных может исключить требуемую проверку сохранённого состояния.

Владельцы и действия: владелец SUT подтверждает разрешённую очистку сущности, созданной через UI; владелец платформы выполняет проверки доступа из CI; владелец базы данных предоставляет безопасное описание разрешённой схемы и контракта чтения. Доказательства: документированная проверка очистки, результаты проверок возможностей из CI и очищенная запись доступа к базе данных.

К главе 251 переходить нельзя. Решение изменится на `PASS`, когда все обязательные сервисы будут доступны из CI, очистка будет определена для каждой изменяемой сущности, а доступ к PostgreSQL позволит выполнить обязательную проверку без изменения рабочих данных. Если владелец подтвердит, что безопасная очистка невозможна, решение изменится на `FAIL` и потребуется другой SUT.

### Объяснение

Наличие учётных данных и `.proto` не компенсирует два блокирующих условия: очистку и доступность из CI. Начало Page Objects сейчас создаст невозвратные затраты до подтверждения выполнимости проекта.

### Типичная ошибка

Перейти к реализации и записать нерешённые обязательные блокирующие условия как будущие улучшения.

### Связь с Automation QA

Заключение о готовности защищает тестовую среду от остаточных данных, а команду — от framework, который невозможно завершить по Definition of Done.
