# Решения: tsconfig.json

## Концептуальные вопросы

### 1. Зачем TypeScript-проекту нужен `tsconfig.json`?

Ответ: чтобы задать правила и границы проекта для компилятора TypeScript.

Объяснение: компилятор TypeScript должен знать, какие файлы проверять и как генерировать JavaScript.

Типичная ошибка: запускать TypeScript без общего project contract.

Связь с Automation QA: framework должен проверяться единообразно.

### 2. Что описывает `compilerOptions`?

Ответ: правила проверки и генерации.

Объяснение: там задаются параметры вроде `target`, `module`, `strict`.

Типичная ошибка: думать, что `compilerOptions` только про output.

Связь с Automation QA: эти правила влияют на весь test project.

### 3. Чем `include` отличается от `exclude`?

Ответ: `include` добавляет файлы в project boundary, `exclude` убирает лишние.

Объяснение: вместе они помогают компилятору TypeScript понять состав проекта.

Типичная ошибка: включать все файлы без контроля.

Связь с Automation QA: reports и generated files обычно не должны проверяться как source.

### 4. Почему project boundary важен для большого Automation QA framework?

Ответ: без границ непонятно, какие части framework реально проверяются.

Объяснение: tests, helpers и config должны попадать в проверку осознанно.

Типичная ошибка: случайно оставить часть helpers вне TypeScript-проверки.

Связь с Automation QA: единые границы повышают надежность framework.

### 5. Почему generated files не должны случайно становиться исходными файлами проекта?

Ответ: они являются результатом работы tools, а не source of truth.

Объяснение: их проверка может создавать шум и ложные проблемы.

Типичная ошибка: включать `reports` или output-папки в `include`.

Связь с Automation QA: отчеты и артефакты тестов не должны смешиваться с исходным кодом.

## Чтение кода

Ответ: проект генерирует ES2022 modules, включает строгую проверку, проверяет `src/**/*.ts` и исключает `node_modules`.

Объяснение: `tsconfig.json` задает и правила, и границы.

Типичная ошибка: читать только `compilerOptions` и игнорировать `include`.

Связь с Automation QA: так можно описать source-код helpers и clients.

## Предскажите результат

Ответ: да, `src/helpers/retry.ts` входит в `src/**/*.ts`.

Объяснение: путь находится внутри `src` и заканчивается на `.ts`.

Типичная ошибка: думать, что glob относится только к файлам в корне `src`.

Связь с Automation QA: вложенные helpers должны попадать в проверку.

## Задание на отладку

Ответ: `**/*.ts` может захватить временные, generated или служебные файлы.

Объяснение: слишком широкая граница делает проект менее предсказуемым.

Типичная ошибка: считать широкий `include` безопасным по умолчанию.

Связь с Automation QA: generated reports или временные файлы не должны попадать в source boundary.

## Задание Automation QA

Ответ: обычно стоит включить source-код tests, helpers, pages, fixtures и API clients. Исключить стоит `node_modules`, reports и generated artifacts.

Объяснение: проверять нужно код проекта, а не зависимости и результаты выполнения.

Типичная ошибка: исключить `tests` и оставить проверку только helpers.

Связь с Automation QA: тесты тоже являются TypeScript-кодом проекта.

## Мини-проект

Ответ:

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ES2022",
    "strict": true
  },
  "include": ["src/**/*.ts", "tests/**/*.ts"],
  "exclude": ["node_modules", "reports"]
}
```

Объяснение: это минимальный договор проекта с компилятором TypeScript.

Типичная ошибка: добавлять много options до понимания базовых границ.

Связь с Automation QA: такая конфигурация отделяет source-код от отчетов и зависимостей.
