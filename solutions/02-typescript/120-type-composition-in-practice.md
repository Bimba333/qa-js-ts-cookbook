# Решения: Type Composition in Practice

## Концептуальные вопросы

### 1. Зачем делить модель на маленькие типы?

Ответ: чтобы каждая часть описывала одну идею и могла переиспользоваться.

Объяснение: большие типы быстро начинают дублировать свойства.

Типичная ошибка: складывать все поля в один огромный тип.

Связь с Automation QA: отчетные модели часто растут со временем.

### 2. Как литеральные типы помогают описывать состояние?

Ответ: они ограничивают статус конкретными значениями.

Объяснение: `status: 'passed'` точнее, чем `status: string`.

Типичная ошибка: оставлять статус слишком широким.

Связь с Automation QA: статус теста должен быть из известного набора.

### 3. Как union помогает описывать варианты результата?

Ответ: union перечисляет допустимые формы результата.

Объяснение: success и error могут иметь разные поля.

Типичная ошибка: делать все поля optional вместо явных вариантов.

Связь с Automation QA: API result может быть успешным или ошибочным.

### 4. Как intersection помогает добавить общие поля?

Ответ: intersection добавляет требования общей части к каждому варианту.

Объяснение: `TestBase & TestOutcome` требует и общие поля, и поля состояния.

Типичная ошибка: ожидать слияние объектов во время выполнения.

Связь с Automation QA: duration и title часто нужны для всех результатов.

### 5. Почему композиция типов не меняет объект во время выполнения?

Ответ: все типы исчезают после компиляции.

Объяснение: композиция типов помогает TypeScript проверять код, но не выполняет преобразования данных.

Типичная ошибка: считать типы конструкторами во время выполнения.

Связь с Automation QA: данные отчета нужно формировать обычным JavaScript-кодом.

Объяснение: `ReportEntry` — это intersection общей части и union вариантов.

Типичная ошибка: считать, что `ReportEntry` содержит сразу все поля всех вариантов.

Связь с Automation QA: отчетная запись имеет общую часть и конкретное состояние.

Типичная ошибка: забыть поле, которое относится к конкретному состоянию.

## Задание на отладку

Ответ:

```typescript
type TestStatus = 'passed' | 'failed';

const status: TestStatus = 'passed';
```

Объяснение: `'unknown'` не входит в union.

Типичная ошибка: использовать неописанный статус.

Связь с Automation QA: неизвестный статус ломает отчетность.

## Задание Automation QA

Ответ:

```typescript
type TestBase = {
  title: string;
  durationMs: number;
};

type TestOutcome =
  | { status: 'passed' }
  | { status: 'failed'; errorMessage: string };

type ReportEntry = TestBase & TestOutcome;
```

Объяснение: общие поля вынесены отдельно, варианты состояния описаны через union.

Типичная ошибка: сделать `errorMessage` optional для всех статусов.

Связь с Automation QA: сообщение об ошибке нужно только для failed.

## Мини-проект

Ответ:

```typescript
type RequestInfo = {
  endpoint: string;
};

type ApiResult =
  | { status: 'success'; statusCode: number }
  | { status: 'error'; message: string };

type ApiReport = RequestInfo & ApiResult;

const report: ApiReport = {
  endpoint: '/users',
  status: 'success',
  statusCode: 200,
};

console.log(report);
```

Объяснение: `ApiReport` объединяет endpoint и один из вариантов результата.

Типичная ошибка: смешать success и error поля без явного статуса.

Связь с Automation QA: API отчет должен отражать реальное состояние запроса.
