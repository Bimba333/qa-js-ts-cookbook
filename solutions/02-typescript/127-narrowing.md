# Решения: Narrowing

## Концептуальные вопросы

### Ответ

Union type нужно уточнять, потому что значение может быть любым из перечисленных вариантов. Narrowing не меняет само значение, а меняет знание TypeScript о значении в конкретной ветке. `return` помогает исключить вариант, потому что после завершенной ветки этот вариант больше не может попасть в дальнейший код.

### Объяснение

Если тип `string | number`, TypeScript разрешит только операции, которые безопасны для обоих вариантов. После проверки `typeof value === "string"` внутри ветки становится доступен API строки.

### Типичная ошибка

Считать, что union type автоматически разрешает методы каждого варианта.

### Связь с Automation QA

Результаты helpers часто бывают union types: успешный результат, ошибка, пропуск или отсутствие данных.

## Чтение кода

### Ответ

В первой ветке `value` имеет тип `string`. После `return` из первой ветки во второй части функции остается `number`.

### Объяснение

Проверка `typeof value === "string"` исключает число из первой ветки. Так как ветка возвращает результат, оставшийся код работает только с другим вариантом.

### Типичная ошибка

Не учитывать, что TypeScript анализирует поток выполнения, а не только одну строку.

### Связь с Automation QA

Так можно безопасно форматировать разные виды входных данных в helper-функциях.

## Предскажите результат проверки

### Ответ

Да, TypeScript разрешит `error.toUpperCase()` после `if`.

### Объяснение

Если `error === undefined`, функция завершилась через `return`. Значит, ниже `error` может быть только строкой.

### Типичная ошибка

Думать, что проверка работает только внутри фигурных скобок.

### Связь с Automation QA

Этот прием полезен для раннего выхода из функций обработки ошибок.

## Анализ типа

### Ответ

Код небезопасен, потому что `toUpperCase()` есть у `string`, но нет у `number`.

### Объяснение

Нужно сначала уточнить тип через `typeof`.

### Типичная ошибка

Ожидать, что TypeScript сам выберет подходящий вариант union type без условия.

### Связь с Automation QA

Такая ошибка часто встречается при обработке параметров конфигурации, которые могут быть строкой или числом.

## Задание на отладку

### Ответ

```ts
function normalize(value: string | number): string {
  if (typeof value === "string") {
    return value.trim();
  }

  return String(value);
}
```

### Объяснение

`trim()` вызывается только после доказательства, что значение является строкой.

### Типичная ошибка

Приводить все к строке заранее и терять смысл разных вариантов.

### Связь с Automation QA

Helpers для вывода отчетов часто нормализуют разные типы значений.

## Задание Automation QA

### Ответ

```ts
type LoginResult =
  | { status: "success"; userId: string }
  | { status: "failed"; reason: string };

function describeLogin(result: LoginResult): string {
  if (result.status === "success") {
    return `Пользователь: ${result.userId}`;
  }

  return `Ошибка входа: ${result.reason}`;
}
```

### Объяснение

Проверка `status` уточняет конкретный вариант результата.

### Типичная ошибка

Обращаться к `userId` до проверки статуса.

### Связь с Automation QA

Так можно моделировать результат логина без небезопасных optional-свойств.

## Мини-проект

### Ответ

```ts
type RunResult =
  | { status: "passed"; durationMs: number }
  | { status: "failed"; message: string }
  | { status: "skipped"; reason: string };

function report(result: RunResult): string {
  if (result.status === "passed") {
    return `passed: ${result.durationMs}ms`;
  }

  if (result.status === "failed") {
    return `failed: ${result.message}`;
  }

  return `skipped: ${result.reason}`;
}
```

### Объяснение

Каждая проверка убирает один вариант из union type.

### Типичная ошибка

Делать одно большое объектное описание с множеством optional-полей.

### Связь с Automation QA

Такой тип ближе к реальным статусам тестового отчета.
