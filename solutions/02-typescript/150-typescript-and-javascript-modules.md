# Решения: TypeScript and JavaScript Modules

## Концептуальные вопросы

### Ответ

`export` делает объявление частью публичного API модуля. TypeScript проверяет этот API, но runtime-поведение остается JavaScript-модульной системой. `interface` после компиляции исчезает.

### Объяснение

Модуль может экспортировать значения и типы. Значения остаются в JavaScript, а типы нужны только для проверки.

### Типичная ошибка

Считать экспортированный `interface` объектом, который можно прочитать во время выполнения.

### Связь с Automation QA

Так можно разделять report helpers, config models и builders по файлам.

## Чтение кода

### Ответ

`createReportLine` является runtime-экспортом. `ReportStatus` существует только для проверки типов.

### Объяснение

Функция попадает в сгенерированный JavaScript, а type alias стирается.

### Типичная ошибка

Пытаться импортировать `ReportStatus` как значение.

### Связь с Automation QA

Статусы тестов удобно ограничивать типом, а форматирование держать функцией времени выполнения.

## Предскажите результат проверки

### Ответ

TypeScript покажет ошибку: `"skipped"` не входит в `ReportStatus`.

### Объяснение

Импортированная функция сохраняет свою сигнатуру в другом модуле.

### Типичная ошибка

Думать, что после import параметры функции перестают проверяться.

### Связь с Automation QA

Это защищает отчеты от случайных статусов.

## Анализ типа

### Ответ

Экспорт по умолчанию не лучше автоматически. Именованные экспорты удобны, когда модуль открывает несколько явно названных частей API. Экспорт по умолчанию удобен, когда модуль имеет один главный экспорт.

### Объяснение

Выбор формы экспорта влияет на читаемость public API.

### Типичная ошибка

Использовать default export везде без причины.

### Связь с Automation QA

Для файла с несколькими helper-функциями именованные экспорты обычно читаются понятнее.

## Задание на отладку

### Ответ

```ts
import { createTitle } from "./title.js";

console.log(createTitle("smoke"));
```

### Объяснение

Именованный импорт должен совпадать с именованным экспортом.

### Типичная ошибка

Переименовать импорт без `as` и ожидать, что TypeScript найдет похожий экспорт.

### Связь с Automation QA

Явные имена экспортов помогают быстро находить helper-функцию в проекте.

## Задание Automation QA

### Ответ

```ts
export type CheckStatus = "passed" | "failed";

export function formatCheckStatus(status: CheckStatus): string {
  return status.toUpperCase();
}
```

### Объяснение

Тип ограничивает допустимые значения, функция остается runtime-экспортом.

### Типичная ошибка

Делать статус обычным `string` и терять проверку.

### Связь с Automation QA

Так можно стабилизировать формат статусов в отчетах.

## Мини-проект

### Ответ

```ts
// report-model.ts
export type ReportItem = {
  title: string;
  status: "passed" | "failed";
};
```

```ts
// report-format.ts
import { ReportItem } from "./report-model.js";

export function formatReportItem(item: ReportItem): string {
  return `${item.status}: ${item.title}`;
}
```

### Объяснение

Модель экспортирует тип, форматтер использует его для проверки входных данных.

### Типичная ошибка

Смешать модель данных и форматирование в одном большом файле.

### Связь с Automation QA

Так отчетные helper-функции остаются маленькими и проверяемыми.
