# Решения: strict mode

## Концептуальные вопросы

### 1. Что включает идея `strict mode`?

Ответ: более строгий набор проверок TypeScript.

Объяснение: `strict` заставляет явно описывать сомнительные места.

Типичная ошибка: воспринимать strict mode как наказание, а не как защиту.

Связь с Automation QA: строгие правила помогают не пропускать рискованные config и helper cases.

### 2. Почему мягкая проверка может скрывать риск?

Ответ: она допускает больше неопределенности.

Объяснение: неясное значение может дойти до runtime.

Типичная ошибка: считать меньшее количество диагностических сообщений признаком качества.

Связь с Automation QA: ошибка может проявиться только в CI.

### 3. Почему `strict` полезен для configuration?

Ответ: config часто содержит значения, которые могут отсутствовать или иметь неверную форму.

Объяснение: strict mode заставляет явно обработать такие случаи.

Типичная ошибка: считать environment values всегда заполненными.

Связь с Automation QA: `baseUrl`, credentials и timeouts часто зависят от окружения.

### 4. Почему нельзя просто отключать `strict`, чтобы ошибок стало меньше?

Ответ: ошибки не исчезают, они становятся менее видимыми.

Объяснение: runtime все равно столкнется с неверными значениями.

Типичная ошибка: путать отсутствие диагностических сообщений с надежностью.

Связь с Automation QA: отключенный strict может спрятать проблемы до запуска тестов.

### 5. Почему `strict` не заменяет runtime-проверки?

Ответ: strict работает до запуска, а runtime получает реальные внешние данные.

Объяснение: внешняя среда может вернуть неожиданные значения.

Типичная ошибка: ожидать от strict проверки API response.

Связь с Automation QA: strict и assertions решают разные задачи.

## Чтение кода

Ответ: `baseUrl` может быть `undefined`, но код вызывает `toLowerCase()`.

Объяснение: если значение отсутствует, runtime получит ошибку.

Типичная ошибка: игнорировать вариант отсутствующего значения.

Связь с Automation QA: `baseUrl` часто приходит из окружения и может быть не задан.

## Предскажите результат проверки

Ответ: да, код выглядит безопаснее.

Объяснение: функция явно требует две строки и использует их предсказуемо.

Типичная ошибка: искать nullability-риск там, где значения явно обязательны.

Связь с Automation QA: helper с ясным contract проще использовать в тестах.

## Задание на отладку

Ответ: `baseUrl` объявлен без явного начального значения и без ясного намерения.

Объяснение: strict mode помогает не оставлять такие места неясными.

Типичная ошибка: полагаться на последующее присваивание без явного contract.

Связь с Automation QA: config values должны быть понятны до запуска тестов.

## Задание Automation QA

Ответ: отсутствие `baseUrl` в CI должно быть обработано явно.

Объяснение: иначе тест может упасть далеко от причины, например при первом запросе или открытии страницы.

Типичная ошибка: искать проблему в Playwright test, хотя причина в configuration.

Связь с Automation QA: хорошая ошибка конфигурации экономит время диагностики.

## Мини-проект

Ответ:

* включать `strict` с начала нового проекта;
* сначала проверять config, helpers и test data;
* ожидать ошибки вокруг неясных значений и отсутствующих cases;
* не откладывать strict mode, потому что позже исправлять накопленные неясности дороже.

Объяснение: strict mode лучше работает как базовое правило проекта, а не как поздняя миграция.

Типичная ошибка: ждать, пока проект станет большим, и только потом включать strict.

Связь с Automation QA: ранний strict помогает держать framework предсказуемым с первых модулей.
