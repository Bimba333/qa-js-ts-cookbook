# Решения: Type Annotations and Type Inference

## Концептуальные вопросы

### 1. Что такое `type annotation`?

Ответ: это явная запись ожидаемого типа.

Объяснение: аннотация сообщает TypeScript и читателю, какое значение допустимо.

Типичная ошибка: писать аннотацию там, где тип уже очевиден.

Связь с Automation QA: явные типы полезны на границах helpers и config.

### 2. Что такое `type inference`?

Ответ: это автоматический вывод типа из значения или выражения.

Объяснение: TypeScript сам понимает тип, если значение достаточно очевидно.

Типичная ошибка: считать inference менее надежным, чем ручная аннотация.

Связь с Automation QA: локальные значения test metadata часто не требуют явной аннотации.

### 3. Почему не нужно аннотировать каждую локальную переменную?

Ответ: лишние аннотации создают шум и не добавляют новой информации.

Объяснение: если тип виден из значения, TypeScript уже знает его.

Типичная ошибка: превращать типизированный код в перегруженный текст.

Связь с Automation QA: читаемость helpers важна не меньше формальной строгости.

### 4. Почему параметры функций часто требуют явной аннотации?

Ответ: у параметра нет конкретного значения в момент объявления функции.

Объяснение: параметр является входной границей, поэтому договор лучше записать явно.

Типичная ошибка: оставлять параметры неописанными.

Связь с Automation QA: helper должен явно показывать, какие данные принимает.

### 5. Как аннотации помогают читать QA helpers?

Ответ: они показывают ожидаемый договор без запуска кода.

Объяснение: читатель сразу видит типы аргументов и результата.

Типичная ошибка: полагаться только на имя функции.

Связь с Automation QA: это упрощает рефакторинг общих helpers.

## Чтение кода

Ответ:

```typescript
const suiteName = 'smoke';
const retryCount = 2;
const enabled = true;
```

TypeScript выведет строку, число и boolean.

Объяснение: типы очевидны из присвоенных значений.

Типичная ошибка: добавлять лишние аннотации к каждому `const`.

Связь с Automation QA: такие значения часто встречаются в локальных настройках запуска.

## Предскажите результат проверки

Ответ: код согласован.

```typescript
function buildLabel(name: string, count: number): string {
  return `${name}: ${count}`;
}

buildLabel('api', 3);
```

Объяснение: аргументы соответствуют аннотациям параметров.

Типичная ошибка: забыть, что return type тоже является частью договора.

Связь с Automation QA: такие функции удобны для report labels.

## Задание на отладку

Ответ:

```typescript
function setRetries(count: number): void {
  console.log(count);
}

setRetries(3);
```

Объяснение: параметр `count` ожидает число, а не строку.

Типичная ошибка: считать строку `'3'` эквивалентной числу `3`.

Связь с Automation QA: retries и timeout должны иметь предсказуемые числовые типы.

## Задание Automation QA

Ответ:

```typescript
const defaultTimeout = 5000;

function waitForElement(selector: string, timeout: number): void {
  console.log(selector, timeout);
}
```

Объяснение: локальный `defaultTimeout` понятен через inference, а параметры helper являются границей и требуют annotation.

Типичная ошибка: оставлять параметры helper без договора.

Связь с Automation QA: общий helper должен быть понятен без просмотра всех вызовов.

## Мини-проект

Ответ:

```typescript
function buildSuiteTitle(
  suiteName: string,
  testCount: number,
  isSmoke: boolean,
): string {
  const suiteType = isSmoke ? 'smoke' : 'full';

  return `${suiteName} (${suiteType}): ${testCount} tests`;
}

console.log(buildSuiteTitle('checkout', 12, true));
```

Объяснение: параметры и результат являются договором функции.

Типичная ошибка: аннотировать локальный `suiteType`, хотя TypeScript выводит его сам.

Связь с Automation QA: такие helpers формируют понятные названия suites и отчетов.
