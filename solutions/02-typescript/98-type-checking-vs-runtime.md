# Решения: Type Checking vs Runtime

## Концептуальные вопросы

### 1. Чем compile time отличается от runtime?

Ответ: compile time — этап проверки и генерации, runtime — этап выполнения JavaScript.

Объяснение: TypeScript работает до запуска, JavaScript runtime работает во время запуска.

Типичная ошибка: ожидать TypeScript-проверки во время выполнения.

Связь с Automation QA: компилятор TypeScript может проверить test code, но запуск браузера происходит в runtime.

### 2. Что проверяет TypeScript во время type checking?

Ответ: согласованность значений, аргументов, возвращаемых данных и обращений в коде.

Объяснение: TypeScript анализирует то, что можно вывести из исходного кода.

Типичная ошибка: считать type checking проверкой всех возможных runtime-ситуаций.

Связь с Automation QA: TypeScript может проверить helper contracts.

### 3. Почему TypeScript не может гарантировать форму данных, пришедших из API?

Ответ: API response появляется только во время выполнения.

Объяснение: компилятор TypeScript не выполняет запрос и не видит реальные данные сервера.

Типичная ошибка: думать, что типы автоматически проверяют внешние данные.

Связь с Automation QA: API assertions остаются обязательными.

### 4. Почему runtime-ошибки не исчезают после перехода на TypeScript?

Ответ: runtime работает с реальными значениями, сетью, файлами, окружением и внешними системами.

Объяснение: TypeScript уменьшает часть рисков, но не контролирует все события выполнения.

Типичная ошибка: ожидать полного отсутствия ошибок после включения TypeScript.

Связь с Automation QA: нестабильный UI, сетевой сбой и некорректный response остаются runtime-рисками.

### 5. Где проходит граница ответственности TypeScript?

Ответ: TypeScript проверяет код до запуска, но не выполняет программу.

Объяснение: после компиляции остается JavaScript.

Типичная ошибка: переносить runtime-ответственность на TypeScript.

Связь с Automation QA: TypeScript помогает строить framework, но тесты проверяют продукт и окружение.

## Чтение кода

Ответ: функция ожидает `string`, но получает `number`.

Объяснение: `getStatusText(200)` нарушает ожидаемый contract.

Типичная ошибка: думать, что ошибка появится только при запуске.

Связь с Automation QA: статус теста или response status должен передаваться в ожидаемой форме.

## Предскажите результат

Ответ: JavaScript runtime выбросит ошибку, потому что у числа нет метода `toUpperCase()`.

Объяснение: JavaScript попытается выполнить метод на реальном значении `200`.

Типичная ошибка: ожидать, что JavaScript заранее остановит такой вызов.

Связь с Automation QA: такая ошибка может упасть уже внутри report helper.

## Задание на отладку

Объяснение: код выглядит типизированным вокруг функции, но источник данных остается внешним.

Типичная ошибка: считать результат `JSON.parse` безопасным без проверки.

Связь с Automation QA: API response нужно проверять assertions или validation-кодом.

## Задание Automation QA

Ответ: TypeScript проверит, что в `assertStatus` передается строка из TypeScript-кода. Runtime-риск остается, если статус пришел извне.

Объяснение: данные из API появляются после запуска.

Типичная ошибка: не проверять response перед передачей в helper.

Связь с Automation QA: тест должен проверить форму response, а не только полагаться на type checking.

## Мини-проект

Ответ:

| type checking | runtime |
| --- | --- |
| неверный аргумент функции | ошибка сети |
| несовпадение типа переменной | неожиданный JSON response |
|  | падение сервера |

Объяснение: TypeScript проверяет видимые договоренности кода, runtime сталкивается с реальными внешними событиями.

Типичная ошибка: помещать API response полностью в область compile time.

Связь с Automation QA: и type checking, и runtime assertions нужны вместе.
