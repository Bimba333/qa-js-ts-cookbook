# Решения: Maintaining Large TypeScript Test Projects

## Концептуальные вопросы

### Ответ

У типов должен быть владелец, чтобы было понятно, где их менять. Публичный типовой API должен быть небольшим, чтобы внутренние изменения не ломали весь проект. Слишком сложные типы вредны, если они не решают реальную инженерную проблему.

### Объяснение

Типы являются частью архитектуры проекта.

### Типичная ошибка

Экспортировать все типы без понимания, кто ими владеет.

### Связь с Automation QA

Большой тестовый проект быстро становится трудным для рефакторинга без понятных границ.

## Чтение кода

### Ответ

Публичные типы: `ReportStatus` и `ReportSummary`. Внутренний тип: `InternalReportLine`.

### Объяснение

`export` делает тип частью публичного API модуля.

### Типичная ошибка

Экспортировать внутренние типы на всякий случай.

### Связь с Automation QA

Модуль отчетности должен раскрывать только то, что нужно другим слоям.

## Предскажите результат проверки

### Ответ

TypeScript покажет ошибку: в объекте нет обязательного свойства `delayMs`.

### Объяснение

`RetryPolicy` требует оба поля.

### Типичная ошибка

Передавать неполную политику повторов.

### Связь с Automation QA

Retry policy влияет на стабильность тестов, поэтому ее форма должна быть полной.

## Анализ типа

### Ответ

Если `UserRole` меняется, TypeScript показывает места, где старые значения больше не подходят. Это помогает безопаснее рефакторить связанные слои.

### Объяснение

Компилятор проверяет зависимости от типа по всему проекту.

### Типичная ошибка

Менять строковые значения в одном месте и не искать остальные зависимости.

### Связь с Automation QA

Роли пользователей часто используются в тестовых данных, телах API-запросов и проверках.

## Задание на отладку

### Ответ

```ts
type InternalRetryState = {
  attempt: number;
  startedAt: number;
};

export type RetryPolicy = {
  maxAttempts: number;
  delayMs: number;
};
```

### Объяснение

Другим модулям нужны правила повторов, а не внутреннее состояние выполнения.

### Типичная ошибка

Раскрывать внутреннее состояние модуля через export.

### Связь с Automation QA

Так вспомогательную функцию повторов можно менять внутри, не ломая внешний API.

## Задание Automation QA

### Ответ

- Типы конфигурации должны жить рядом с модулем конфигурации.
- Типы ответов API должны жить рядом с API-клиентом.
- Типы Page Object должны жить рядом с UI-слоем.
- Типы сводки отчета должны жить рядом с модулем отчетности.

### Объяснение

Владелец типа должен совпадать с областью, где этот тип имеет смысл.

### Типичная ошибка

Создать один общий файл для всех типов проекта.

### Связь с Automation QA

Разделение владельцев помогает поддерживать большой фреймворк.

## Мини-проект

### Ответ

```ts
export type ReportStatus = "passed" | "failed" | "skipped";

export type ReportSummary = {
  suiteName: string;
  status: ReportStatus;
  durationMs: number;
};

type InternalReportLine = {
  text: string;
  level: "info" | "warning";
};

function formatLine(line: InternalReportLine): string {
  return `${line.level}: ${line.text}`;
}

export function createReportText(summary: ReportSummary): string {
  return formatLine({
    text: `${summary.suiteName}: ${summary.status}`,
    level: "info",
  });
}
```

### Объяснение

Модуль экспортирует только статус, summary и функцию. Внутренняя строка отчета остается деталью реализации.

### Типичная ошибка

Делать внутренние типы частью публичного API.

### Связь с Automation QA

Так граница отчетности остается устойчивой при изменении внутреннего форматирования.
