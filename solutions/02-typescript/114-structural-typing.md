# Решения: Structural Typing

## Концептуальные вопросы

### 1. Что означает structural typing?

Ответ: совместимость определяется структурой объекта.

Объяснение: TypeScript смотрит на свойства и методы, а не только на имя типа.

Типичная ошибка: ожидать сравнение по названию interface.

Связь с Automation QA: разные logger-объекты могут иметь один договор.

### 2. Почему TypeScript сравнивает форму, а не имя?

Ответ: это соответствует JavaScript-модели объектов.

Объяснение: JavaScript работает со свойствами объекта, а TypeScript проверяет эти свойства заранее.

Типичная ошибка: думать, что объект обязан быть создан из конкретного класса.

Связь с Automation QA: helper может принимать любой совместимый объект.

### 3. Что должно быть у объекта, чтобы он подходил под interface?

Ответ: нужные свойства и методы совместимых типов.

Объяснение: если interface требует `log(message: string): void`, объект должен иметь такой метод.

Типичная ошибка: использовать другое имя метода.

Связь с Automation QA: logger должен иметь ожидаемый публичный метод.

### 4. Почему лишние свойства в свежем object literal могут быть ошибкой?

Ответ: TypeScript пытается поймать опечатки и неверную форму свежего объекта.

Объяснение: excess property checking применяется строже к свежему object literal. Это не универсальный запрет на дополнительные свойства.

Типичная ошибка: думать, что TypeScript использует exact object types.

Связь с Automation QA: тестовые данные с лишними полями могут скрывать ошибку сценария.

### 5. Как structural typing помогает QA helpers?

Ответ: helper может зависеть от формы, а не от конкретной реализации.

Объяснение: это делает код гибче без потери проверки.

Типичная ошибка: привязывать helper к конкретному объекту без необходимости.

Связь с Automation QA: можно заменить logger или reporter, если сохранен договор.

## Задание на отладку

Ответ:

```typescript
interface Logger {
  log(message: string): void;
}

const logger: Logger = {
  log(message: string): void {
    console.log(message);
  },
};
```

Объяснение: interface требует `log`, а не `write`.

Типичная ошибка: считать похожее имя метода совместимым.

Связь с Automation QA: helper вызывает конкретный публичный метод.

## Задание Automation QA

Ответ: оба logger-объекта подходят под один interface, если у каждого есть метод `log(message: string): void`.

Объяснение: TypeScript проверяет форму, а не происхождение объекта.

Типичная ошибка: думать, что объект должен быть создан одним конструктором.

Связь с Automation QA: можно иметь console logger и file logger с одним договором.

## Мини-проект

Ответ:

```typescript
interface StepLogger {
  log(message: string): void;
}

const consoleStepLogger = {
  log(message: string): void {
    console.log(`[console] ${message}`);
  },
};

const reportStepLogger = {
  log(message: string): void {
    console.log(`[report] ${message}`);
  },
};

function runStep(logger: StepLogger): void {
  logger.log('open checkout page');
}

runStep(consoleStepLogger);
runStep(reportStepLogger);
```

Объяснение: оба объекта совместимы со `StepLogger` по структуре.

Типичная ошибка: привязывать функцию к одному конкретному объекту.

Связь с Automation QA: это помогает менять реализацию logging без изменения helper.
