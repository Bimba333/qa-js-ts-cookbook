# Решения: Проверка контрактов во время выполнения

## Задача 1. Концептуальные вопросы
### Ответ
Типы TypeScript исчезают после компиляции и не проверяют входящий JSON. Проверка контракта во время выполнения подтверждает форму данных на границе, а проверка бизнес-правила проверяет смысл этих данных в сценарии.
### Объяснение
Валидная структура ещё не гарантирует правильного бизнес-значения.
### Типичная ошибка
Считать interface валидатором времени выполнения.
### Связь с Automation QA
Граница API требует явной проверки внешних данных.

## Задача 2. Анализ границы
### Ответ
Проверка `as Profile` доверяет серверу без проверки. Значение следует принять как `unknown`, проверить форму объекта и типы полей, а затем использовать как `Profile`.
### Объяснение
`unknown` заставляет доказать контракт перед доступом к полям.
### Типичная ошибка
Заменить `as Profile` на `as unknown as Profile`.
### Связь с Automation QA
Валидатор локализует расхождение контракта на входной границе.

## Задача 3. Предскажите результат
### Ответ
Нет. Type assertion не преобразует `7` в строку и `"yes"` в boolean и не создаёт проверку во время выполнения. Ошибка проявится только в поведении кода или при явной валидации.
### Объяснение
Статическое обещание разработчика не меняет значение.
### Типичная ошибка
Путать автодополнение после type assertion с доказанной формой ответа.
### Связь с Automation QA
Непроверенное тело данных может привести к неочевидному падению позже.

## Задача 4. Поиск ошибки
### Ответ
Если контракт допускает дополнительные поля, валидатор должен проверять обязательные свойства и разрешать остальные. Точная проверка всех полей оправдана только при явном запрете дополнительных полей.
### Объяснение
Строгость должна следовать контракту, а не удобству валидатора.
### Типичная ошибка
Считать любое новое поле несовместимым изменением.
### Связь с Automation QA
Проверка, совместимая с будущими расширениями, снижает число ложных падений клиентов.

## Задача 5. Automation QA
### Ответ
Ошибка должна указывать путь `active`, ожидаемый тип `boolean`, фактический тип `string` и безопасно представленное значение `"yes"`. Полный ответ и секреты выводятся только согласно политике диагностики.
### Объяснение
Точный путь к полю ускоряет поиск расхождения контракта.
### Типичная ошибка
Сообщать только `невалидный ответ`.
### Связь с Automation QA
Отчёт сразу показывает владельцу API нарушенную границу.

## Задача 6. Мини-проект
### Ответ
```ts
import { expect, test } from "@playwright/test";
import { startLocalApi } from "./support/local-api.js";

type Profile = { id: string; active: boolean };

function isProfile(value: unknown): value is Profile {
  if (typeof value !== "object" || value === null) return false;
  return "id" in value
    && typeof value.id === "string"
    && "active" in value
    && typeof value.active === "boolean";
}

test("проверяет контракт во время выполнения", async ({ request }) => {
  const api = await startLocalApi();
  try {
    const value: unknown = await (await request.get(`${api.baseURL}/contracts/profile`)).json();
    expect(isProfile(value)).toBe(true);
    if (!isProfile(value)) throw new Error("Контракт Profile нарушен");
    expect(value.active).toBe(true);

    const invalid: unknown = await (await request.get(
      `${api.baseURL}/contracts/profile`,
      { params: { variant: "invalid" } },
    )).json();
    expect(isProfile(invalid)).toBe(false);
  } finally {
    await api.close();
  }
});
```
### Объяснение
Type guard проверяет внешнее значение до проверки бизнес-правила.
### Типичная ошибка
Обращаться к полям `unknown` через принудительный type assertion без проверки.
### Связь с Automation QA
Расхождение контракта отделён от неверного бизнес-результата.
