# Решения: Совместные UI и API-сценарии

## Задача 1. Концептуальные вопросы
### Ответ
API уместен для быстрой подготовки данных, которые не являются предметом UI-проверки, и для надёжной очистки. Пользовательское действие, ради которого существует тест, остаётся выполненным через UI.
### Объяснение
Каждый слой получает ясную роль в сценарии.
### Типичная ошибка
Заменить через API именно то действие, которое должен доказать UI-тест.
### Связь с Automation QA
Сценарий остаётся быстрым без потери целевого покрытия.

## Задача 2. Анализ идентификатор
### Ответ
Неуникальный `title` может связать UI с чужим ресурсом. Нужно передать назначенный сервером ID из подготовки через API в URL, locator или другое наблюдаемое поле и проверить тот же ID.
### Объяснение
Межслойная проверка требует единого идентификатора.
### Типичная ошибка
Использовать текст как идентификатор только потому, что он виден пользователю.
### Связь с Automation QA
Явная связь устраняет возможность ложноположительного результата при параллельном выполнении.

## Задача 3. Предскажите результат
### Ответ
Очистка должна находиться в `finally` или завершающей части fixture и использовать сохранённый ID. Тогда падение UI-проверки не оставит ресурс.
### Объяснение
Владелец созданных данных отвечает за их жизненный цикл независимо от результата проверки.
### Типичная ошибка
Передавать очистку следующему тесту.
### Связь с Automation QA
Гарантированная очистка сохраняет окружение воспроизводимым.

## Задача 4. Поиск ошибки
### Ответ
Fixture предоставляет готовые клиенты и управляет жизненным циклом вспомогательных объектов. Сам тест явно вызывает подготовку, выполняет действие через UI и содержит ключевые проверки; очистка остаётся в понятном `finally` или завершающей части fixture.
### Объяснение
Абстракция не должна скрывать проверяемое поведение.
### Типичная ошибка
Сделать тест одной строкой без видимого предмета проверки.
### Связь с Automation QA
Читаемый сценарий облегчает review и расследование.

## Задача 5. Automation QA
### Ответ
В первом сценарии API создаёт ресурс и возвращает ID, UI открывает и проверяет этот ID, а владелец подготовки удаляет ресурс. Во втором UI создаёт ресурс и показывает ID, API читает его, а тест удаляет ресурс по тому же ID в `finally`.
### Объяснение
Идентификатор и очистка следуют за источником созданных данных.
### Типичная ошибка
Искать созданный UI ресурс по последней записи коллекции.
### Связь с Automation QA
Оба направления проверяют интеграцию слоёв без неоднозначности.

## Задача 6. Мини-проект
### Ответ
```ts
import { expect, test } from "@playwright/test";
import { startLocalApi } from "./support/local-api.js";

test("связывает действие через UI и проверку через API", async ({ page, request }) => {
  const api = await startLocalApi();
  let taskId: string | undefined;
  try {
    await page.goto(`${api.baseURL}/app`);
    await page.getByRole("button", { name: "Создать задачу" }).click();
    const output = page.locator("output");
    await expect(output).toHaveText(/^task-\d+$/);
    taskId = await output.textContent() ?? undefined;
    if (taskId === undefined) throw new Error("UI не показал ID созданной задачи");
    const response = await request.get(`${api.baseURL}/tasks/${taskId}`);
    expect(response.status()).toBe(200);
    expect(await response.json()).toMatchObject({ id: taskId, title: "Создано из UI" });
  } finally {
    if (taskId) await request.delete(`${api.baseURL}/tasks/${taskId}`);
    await api.close();
  }
});
```
### Объяснение
ID из UI связывает пользовательское действие с проверкой через API.
### Типичная ошибка
Читать API до завершения UI-запроса.
### Связь с Automation QA
Сценарий проверяет реальную интеграцию и сохраняет детерминированную очистку.
