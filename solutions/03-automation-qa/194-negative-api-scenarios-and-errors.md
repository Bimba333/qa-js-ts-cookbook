# Решения: Негативные API-сценарии и ошибки

## Задача 1. Концептуальные вопросы
### Ответ
Ожидаемый `4xx` — полученный HTTP-ответ с бизнес- или клиентской причиной отказа. Транспортная ошибка означает, что пригодного ответа не получено из-за сети, TLS, DNS или разрыва соединения.
### Объяснение
Эти результаты требуют разных проверок и разной диагностики.
### Типичная ошибка
Считать любой отклонённый запрос корректным негативным сценарием.
### Связь с Automation QA
Тест должен доказать контролируемый отказ системы, а не случайную недоступность.

## Задача 2. Анализ кодов
### Ответ
Обычно отсутствующий token — `401`, недостаточная роль — `403`, неизвестный ID — `404`, дублирующийся ресурс — `409`, неподдерживаемый тип содержимого — `415`. Источником истины остаётся контракт конкретного API.
### Объяснение
Код выражает категорию отказа, но не заменяет тело ошибки.
### Типичная ошибка
Навязывать общее соглашение вопреки документированному контракту.
### Связь с Automation QA
Ожидание фиксируется вместе со стабильным кодом ошибки.

## Задача 3. Предскажите результат
### Ответ
Нет. `422` подтверждает отказ, но появившийся ресурс доказывает недопустимый побочный эффект. Нужно сравнить состояние до и после или выполнить GET по известному идентификатору.
### Объяснение
Негативная операция должна сохранять обещанные инварианты.
### Типичная ошибка
Останавливать проверку после кода состояния.
### Связь с Automation QA
Проверка побочного эффекта обнаруживает частично выполненные операции.

## Задача 4. Поиск ошибки
### Ответ
Ожидайте точный код состояния, стабильный машиночитаемый код ошибки и релевантное поле ошибки. Затем подтвердите отсутствие изменения состояния.
### Объяснение
Диапазон `4xx` скрывает неверную маршрутизацию, аутентификацию и валидацию.
### Типичная ошибка
Проверять только текст сообщения, который предназначен человеку.
### Связь с Automation QA
Точная причина делает регрессионный тест устойчивым и полезным.

## Задача 5. Automation QA
### Ответ
Набор на основе рисков: отсутствующее обязательное поле, недопустимое значение и дублирующийся идентификатор. Для каждого проверяются конкретные код состояния, код ошибки и неизменность коллекции или отсутствие ресурса.
### Объяснение
Выбор основан на риске нарушения данных, а не на переборе всех строк.
### Типичная ошибка
Создавать много эквивалентных невалидных тел данных без новой проверяемой границы.
### Связь с Automation QA
Набор покрывает разные правила валидации и побочные эффекты.

## Задача 6. Мини-проект
### Ответ
```ts
import { expect, test } from "@playwright/test";
import { startLocalApi } from "../../examples/03-automation-qa/support/local-api.js";

test("отклоняет невалидное тело без эффекта", async ({ request }) => {
  const api = await startLocalApi();
  try {
    const before: unknown = await (await request.get(`${api.baseURL}/tasks`)).json();
    if (!Array.isArray(before)) throw new Error("Коллекция задач должна быть массивом");
    const response = await request.post(`${api.baseURL}/tasks`, { data: { title: "" } });
    expect(response.status()).toBe(422);
    expect(await response.json()).toMatchObject({ code: "TITLE_REQUIRED" });
    const after: unknown = await (await request.get(`${api.baseURL}/tasks`)).json();
    if (!Array.isArray(after)) throw new Error("Коллекция задач должна быть массивом");
    expect(after).toHaveLength(before.length);
  } finally {
    await api.close();
  }
});
```
### Объяснение
Сценарий проверяет отказ и сохранение состояния сервера.
### Типичная ошибка
Считать стабильный код ошибки достаточным без проверки эффекта.
### Связь с Automation QA
Так обнаруживается частичная запись при ошибке валидации.
