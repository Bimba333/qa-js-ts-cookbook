# Решения: Жизненный цикл данных в сценариях между слоями

## 1. Entity identity
### Ответ
Один ID связывает создание, действие, проверку и точное удаление одной entity.
### Объяснение
Смена identity между слоями делает результат неоднозначным.
### Типичная ошибка
Искать запись по неуникальному title.
### Связь с Automation QA
Parallel tests не удаляют данные друг друга.

## 2. Выбор слоя
### Ответ
HTTP validation error проверяется через API: status, error contract и отсутствие side effect. UI и database не нужны без отдельного требования.
### Объяснение
Ближайший слой даёт точный и дешёвый сигнал.
### Типичная ошибка
Открывать UI только для подтверждения `400`.
### Связь с Automation QA
Негативный тест остаётся быстрым и локализуемым.

## 3. Cleanup order
### Ответ
Сначала удаляется child, затем parent, потому что child зависит от parent в этом lifecycle.
### Объяснение
Обратный порядок сохраняет ограничения зависимостей. Для независимых ресурсов или внешнего API порядок может определяться другим контрактом.
### Типичная ошибка
Удалять parent первым и скрывать foreign-key failure.
### Связь с Automation QA
Cleanup остаётся воспроизводимым в database scenarios.

## 4. Failure-safe cleanup
### Ответ
Идентификатор можно подготовить заранее, но cleanup регистрируется только после успешного создания, до действия и assertions. Если create упал, cleanup не планируется; если упало последующее действие, teardown всё равно удаляет entity.
### Объяснение
Любое последующее падение всё равно проходит через cleanup.
### Типичная ошибка
Регистрировать удаление после последней проверки.
### Связь с Automation QA
Повторный запуск не наследует residue.

## 5. Automation QA-задача
### Ответ
API создаёт entity с unique id, cleanup owner сразу регистрирует `remove(id)`, UI изменяет её, API читает тот же id, затем teardown удаляет запись.
### Объяснение
Каждый слой выполняет отдельную роль, а cleanup owner один.
### Типичная ошибка
Удалять все записи с общим prefix.
### Связь с Automation QA
Сценарий безопасен при parallel execution.

## 6. Мини-проект: cross-layer lifecycle
### Ответ
Используйте локальный store и четыре узких adapters. После успешного create scope хранит точный `remove(id)`. Fixture закрывает scope после success и failure; при успешном cleanup исходная error не заменяется. После close и повторного idempotent cleanup `find(id)` возвращает `null`, а остаточное состояние равно нулю.
### Объяснение
Локальная реализация проверяет orchestration без внешней нестабильности.
### Типичная ошибка
Подавить cleanup exception и вернуть test как passed.
### Связь с Automation QA
Модель переносится на API, UI и database clients без изменения ownership.
