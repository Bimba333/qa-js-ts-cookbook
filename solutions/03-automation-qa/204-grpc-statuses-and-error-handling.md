# Решения: Статусы gRPC и обработка ошибок

## Задача 1. Концептуальные вопросы
### Ответ
`code` классифицирует завершение, `details` содержит стабильное описание, metadata передаёт служебный контекст ошибки. Бизнес-отказ означает ожидаемое нарушение контракта, а недоступность service — инфраструктурную невозможность выполнить вызов.
### Объяснение
Одинаково отклонённый Promise может представлять принципиально разные причины.
### Типичная ошибка
Считать любой `ServiceError` ошибкой проверки бизнес-правила.
### Связь с Automation QA
Классификация определяет полезную проверку и диагностику.

## Задача 2. Анализ статуса
### Ответ
Пустой `title` — `INVALID_ARGUMENT`; неизвестный ID — `NOT_FOUND`; повторяющийся `title` — `ALREADY_EXISTS`; отсутствующий token — `UNAUTHENTICATED`; read-only token — `PERMISSION_DENIED`; истёкший deadline — `DEADLINE_EXCEEDED`.
### Объяснение
Каждый status описывает отдельное условие контракта.
### Типичная ошибка
Использовать `INTERNAL` для ожидаемых бизнес-отказов.
### Связь с Automation QA
Матрица status становится исполняемой спецификацией негативного поведения.

## Задача 3. Предскажите результат
### Ответ
Наблюдается транспортная ошибка, обычно `UNAVAILABLE`, а не `NOT_FOUND`.
### Объяснение
RPC method не смог обратиться к service, поэтому поиск ресурса не выполнялся.
### Типичная ошибка
Ожидать status бизнес-отказа при недоступном server.
### Связь с Automation QA
Различие ускоряет triage инфраструктурных падений.

## Задача 4. Поиск ошибки
### Ответ
Нужно проверить, что ошибка является `ServiceError`, затем сравнить стабильные `code` и `details`; metadata проверяется только в том случае, если входит в контракт.
### Объяснение
Проверка на truthy-значение не сообщает, правильная ли причина отказа.
### Типичная ошибка
Сравнивать весь объект ошибки или нестабильный stack trace.
### Связь с Automation QA
Точные свойства дают полезный отчёт о падении.

## Задача 5. Automation QA
### Ответ
Таблица содержит отдельные строки для невалидного request, отсутствующего и повторяющегося ресурса, ошибок аутентификации и недостаточных прав. Для изменяющих состояние calls добавляется последующая проверка, что отклонённая операция не изменила состояние.
### Объяснение
Status и побочный эффект вместе описывают полный контракт негативного сценария.
### Типичная ошибка
Переиспользовать состояние между строками таблицы.
### Связь с Automation QA
Независимые строки безопасны для повторного и параллельного запуска.

## Задача 6. Мини-проект
### Ответ
```ts
await callUnary((callback) =>
  client.createTask({ title: "duplicate" }, callback));

const cases = [
  { request: { title: "" }, code: status.INVALID_ARGUMENT, details: "title is required" },
  { request: { title: "duplicate" }, code: status.ALREADY_EXISTS, details: "task title already exists" },
];

for (const item of cases) {
  await expect(callUnary((callback) =>
    client.createTask(item.request, callback)))
    .rejects.toMatchObject({ code: item.code, details: item.details });
}

await expect(callUnary((callback) =>
  client.getTask({ id: "missing" }, callback)))
  .rejects.toMatchObject({ code: status.NOT_FOUND });
```
### Объяснение
Сценарии проверяют точный контракт протокола, а не внутреннюю форму ошибки.
### Типичная ошибка
Делать `details` единственным критерием классификации.
### Связь с Automation QA
Табличный набор негативных сценариев легко расширять без потери читаемости.
