# Решения: Поля protobuf-сообщений

## Задача 1. Концептуальные вопросы
### Ответ
Скалярное поле получает значение вроде `false` по умолчанию даже без явной передачи. Присутствие `optional`-поля позволяет отличить отсутствие поля. Repeated требует проверки коллекции, enum — допустимой семантики, а вложенное message — собственной структуры.
### Объяснение
Семантика protobuf шире типа свойства TypeScript.
### Типичная ошибка
Считать пустое значение доказательством явной передачи.
### Связь с Automation QA
Точные проверки предотвращают ошибки интерпретации присутствия поля.

## Задача 2. Анализ message
### Ответ
Тест видит пустую коллекцию и неопределённое значение enum. Без бизнес-контракта нельзя заключить, допустимы ли они; можно проверить только фактические значения protobuf.
### Объяснение
Корректное для protobuf message не обязательно соответствует бизнес-правилам.
### Типичная ошибка
Автоматически трактовать нулевое значение enum как низкий приоритет.
### Связь с Automation QA
Проверки бизнес-правил дополняют проверки контракта.

## Задача 3. Предскажите результат
### Ответ
`description` останется отсутствующим и не получит признак присутствия. `completed` будет `false` при параметре loader `defaults: true`.
### Объяснение
`Optional`-поле и обычное скалярное поле имеют разную семантику присутствия.
### Типичная ошибка
Сравнивать оба случая только через truthy/falsy.
### Связь с Automation QA
Проверка должна различать «не передано» и `false`.

## Задача 4. Поиск ошибки
### Ответ
Нужно использовать `toMatchObject({ id, priority, owner: { id, name } })` и отдельные проверки бизнес-полей. Остальные сгенерированные значения по умолчанию не входят в предмет теста.
### Объяснение
Выбранные проверки устойчивее полного снимка объекта.
### Типичная ошибка
Фиксировать внутренние детали реализации loader.
### Связь с Automation QA
Падение показывает нарушенное поле.

## Задача 5. Automation QA
### Ответ
`Labels` сравниваются по ожидаемому порядку или составу, `priority` — с конкретным enum, `description` — по присутствию и значению, `owner` — по обязательным вложенным полям.
### Объяснение
Каждый вид поля требует подходящей проверки.
### Типичная ошибка
Использовать одну глубокую проверку снимка объекта.
### Связь с Automation QA
Диагностика становится точечной.

## Задача 6. Мини-проект
### Ответ
```ts
const task = await callUnary<Task__Output>((callback) => client.createTask({
  title: "Fields",
  labels: ["api", "critical"],
  priority: "TASK_PRIORITY_HIGH",
  description: "Visible presence",
  owner: { id: "user-1", name: "QA" },
}, callback));
expect(task.labels).toEqual(["api", "critical"]);
expect(task.description).toBe("Visible presence");
expect(task.owner).toEqual({ id: "user-1", name: "QA" });
```
### Объяснение
Request покрывает все назначенные главе виды полей.
### Типичная ошибка
Не проверять вложенные значения после успешного call.
### Связь с Automation QA
Пример связывает семантику protobuf с бизнес-результатом.
