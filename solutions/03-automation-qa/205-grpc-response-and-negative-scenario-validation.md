# Решения: Проверка gRPC-ответов и негативных сценариев

## Задача 1. Концептуальные вопросы
### Ответ
Status call показывает результат протокола, response message — возвращённые данные, бизнес-инварианты — допустимый смысл этих данных, состояние server — фактический побочный эффект операции.
### Объяснение
Один успешный или отклонённый call не доказывает корректность остальных уровней.
### Типичная ошибка
Ограничиваться проверкой status.
### Связь с Automation QA
Многоуровневая проверка обнаруживает частичные нарушения контракта.

## Задача 2. Анализ ложного успеха
### Ответ
Service правильно отклонил request с точки зрения status, но нарушил атомарность: отклонённая команда изменила состояние. Нужен последующий call list или get.
### Объяснение
Response с ошибкой не гарантирует отсутствие побочного эффекта.
### Типичная ошибка
Заканчивать негативный тест сразу после отклонения Promise.
### Связь с Automation QA
Проверка состояния обнаруживает опасные бизнес-дефекты.

## Задача 3. Предскажите результат
### Ответ
Нарушен бизнес-инвариант: новая задача должна начинаться с `completed: false`. Структура сгенерированного объекта остаётся корректной.
### Объяснение
Статический тип не выражает все допустимые бизнес-значения.
### Типичная ошибка
Считать типобезопасный response автоматически правильным.
### Связь с Automation QA
Проверки дополняют бизнес-правила protobuf-контракта.

## Задача 4. Поиск ошибки
### Ответ
После create нужно проверить `title`, `completed`, `labels` и `owner` согласно контракту, затем выполнить get по возвращённому ID и сравнить устойчивые бизнес-поля.
### Объяснение
Непустой ID подтверждает только часть результата.
### Типичная ошибка
Сравнивать снимок всего сгенерированного объекта.
### Связь с Automation QA
Последующее чтение подтверждает сохранённое состояние.

## Задача 5. Automation QA
### Ответ
Каждая последовательность запускает собственный локальный server либо создаёт уникальные данные. Позитивная последовательность выполняет create и get. Негативная получает list до невалидного create, проверяет `INVALID_ARGUMENT`, затем сравнивает list после call.
### Объяснение
Сценарий не зависит от порядка других тестов.
### Типичная ошибка
Использовать ресурс, созданный соседним тестом.
### Связь с Automation QA
Изоляция поддерживает повторные попытки и параллельное выполнение.

## Задача 6. Мини-проект
### Ответ
```ts
const created = await callUnary<Task__Output>((callback) =>
  client.createTask({ title: "Validate", labels: ["grpc"] }, callback));

expect(created).toMatchObject({
  title: "Validate",
  completed: false,
  labels: ["grpc"],
});

const before = await callUnary<ListTasksResponse__Output>((callback) =>
  client.listTasks({}, callback));

await expect(callUnary((callback) =>
  client.createTask({ title: "" }, callback)))
  .rejects.toMatchObject({ code: status.INVALID_ARGUMENT });

const after = await callUnary<ListTasksResponse__Output>((callback) =>
  client.listTasks({}, callback));
expect(after.tasks).toEqual(before.tasks);
```
### Объяснение
Позитивные проверки охватывают message и инварианты, негативные — status и отсутствие изменений.
### Типичная ошибка
Сравнивать только количество, если контракт допускает замену ресурса.
### Связь с Automation QA
Последовательность покрывает наблюдаемый результат целиком.
