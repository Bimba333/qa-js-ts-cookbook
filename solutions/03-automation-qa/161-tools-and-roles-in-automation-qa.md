# Решения: Инструменты и роли в Automation QA

## Задача 1. Концептуальные вопросы

### Ответ

Фреймворк согласует систему; тестовый раннер запускает тесты; система проверок сравнивает значения; CI воспроизводимо запускает команды; приложение под тестированием реализует проверяемое поведение. Один продукт может совмещать возможности, но причины падения и владельцы остаются разными.

### Объяснение

Логические роли не обязаны совпадать с границами пакетов.

### Типичная ошибка

Называть фреймворком любой используемый инструмент.

### Связь с Automation QA

Различение ролей сокращает расследование падения.

## Задача 2. Матрица ответственности

### Ответ

Инструмент автоматизации браузера открывает страницу; система проверок сравнивает статус; API-клиент выполняет HTTP-запрос; средство отчётности сохраняет отчёт; CI запускает команду; приложение под тестированием реализует бизнес-правило.

### Объяснение

Действия распределяются по основной ответственности.

### Типичная ошибка

Назначать CI владельцем качества проверок.

### Связь с Automation QA

Матрица показывает, где искать изменение или дефект.

## Задача 3. Предскажите результат выполнения кода

### Ответ

`runner -> assertions -> reporting`. Порядок элементов — только строковое представление и не передаёт владение.

### Объяснение

Архитектурное отношение определяется контрактами, а не позицией в массиве.

### Типичная ошибка

Делать вывод о зависимостях по визуальному соседству.

### Связь с Automation QA

Средство отчётности получает результат, но не обязано запускать сценарий.

## Задача 4. Диагностика ответственности

### Ответ

Система проверок обнаружила несовпадение, CI организовал запуск, средство отчётности представило падение.

### Объяснение

Одно падение проходит через несколько ролей.

### Типичная ошибка

Обвинять отчёт в причине тестового падения.

### Связь с Automation QA

Так определяется правильный владелец расследования.

## Задача 5. Automation QA

### Ответ

Инструмент автоматизации браузера управляет UI, но не SQL; API-клиент владеет HTTP-взаимодействием, но не UI; слой доступа к базе данных владеет запросами, но не намерением теста; окружение предоставляет сервисы, но не проектирует тесты.

### Объяснение

Явная не-обязанность защищает границу.

### Типичная ошибка

Давать клиенту ответственность за весь жизненный цикл проекта.

### Связь с Automation QA

Слои можно заменять независимо при стабильных API.

## Задача 6. Мини-проект

### Ответ

Один допустимый набор ролей: тестовый раннер, автоматизация UI, система проверок, конфигурация и окружение, жизненный цикл тестовых данных, диагностика и отчётность. Фреймворк связывает их: раннер запускает сценарий, UI выполняет регистрацию, проверка сравнивает результат, механизм жизненного цикла очищает данные, а отчётность сохраняет диагностические данные.

### Объяснение

Это роли, а не требование шести отдельных пакетов.

### Типичная ошибка

Выбирать библиотеки до определения обязанностей.

### Связь с Automation QA

Владение остаётся понятным при смене конкретного инструмента.
