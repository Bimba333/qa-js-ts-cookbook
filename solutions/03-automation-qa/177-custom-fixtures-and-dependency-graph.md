# Решения: Custom fixtures и граф зависимостей

## Задача 1. Концептуальные вопросы
### Ответ
`test.extend()` добавляет типизированные fixtures. Код до `use()` выполняет подготовку, `use(value)` передаёт значение потребителю, код после него освобождает ресурсы. Механизм привязан к жизненному циклу Playwright Test, поэтому не является универсальным контейнером зависимостей.
### Объяснение
Граф fixtures решает подготовку зависимостей теста, а не произвольную композицию объектов приложения.
### Типичная ошибка
Скрыть весь сценарий внутри fixtures.
### Связь с Automation QA
Управляемые зависимости делают подготовку и освобождение ресурсов воспроизводимыми.

## Задача 2. Анализ графа
### Ответ
Подготовка: `orderId` → `page` и `ordersPage` → тест. Освобождение: `ordersPage` → `orderId`; жизненный цикл built-in fixture `page` завершается test runner с учётом собственного графа.
### Объяснение
Зависимость всегда готова раньше потребителя, освобождение ресурсов идёт в обратном порядке.
### Типичная ошибка
Ожидать освобождение ресурсов в порядке подготовки.
### Связь с Automation QA
Обратный порядок защищает вложенные ресурсы.

## Задача 3. Предскажите результат
### Ответ
`orderId` будет создан как зависимость `ordersPage`. Независимая `reporter` не запустится, если её никто не запросил и она не объявлена автоматической.
### Объяснение
Test runner разрешает только востребованный участок графа.
### Типичная ошибка
Считать все объявленные fixtures обязательными.
### Связь с Automation QA
Ленивая подготовка уменьшает лишнюю стоимость тестов.

## Задача 4. Поиск ошибки
### Ответ
Изменяемый массив разделяется всеми тестами worker и создаёт зависимость от порядка. Нужен test scope либо неизменяемый сервис с worker scope без данных отдельных тестов внутри.
### Объяснение
Область жизни fixture должна соответствовать области жизни изменяемого состояния.
### Типичная ошибка
Выбирать worker scope только ради скорости.
### Связь с Automation QA
Общие изменяемые тестовые данные являются частым источником нестабильности.

## Задача 5. Automation QA
### Ответ
`caseId` создаётся отдельно для теста. `casePage` зависит от `page` и `caseId`, подготавливает UI и удаляет данные, созданные fixture.
### Объяснение
Зависимость и освобождение ресурсов находятся рядом с местом, которое ими владеет.
### Типичная ошибка
Оставить удаление данных случайному `afterAll`.
### Связь с Automation QA
Каждый тест получает уникальное обращение без зависимости от порядка.

## Задача 6. Мини-проект
### Ответ
```ts
import { expect, type Locator, test as base } from "@playwright/test";

type Fixtures = {
  events: string[];
  profilePage: Locator;
};

const test = base.extend<Fixtures>({
  events: async ({}, use) => {
    await use([]);
  },
  profilePage: async ({ page, events }, use) => {
    events.push("setup");
    await page.setContent("<h1>Профиль</h1>");
    await use(page.getByRole("heading"));
    expect(events).toEqual(["setup", "test"]);
    events.push("teardown");
  },
});

test("использует подготовленную страницу", async ({ events, profilePage }) => {
  await expect(profilePage).toHaveText("Профиль");
  events.push("test");
});
```
### Объяснение
Проверка после `use()` доказывает, что тело теста завершилось до освобождения fixture.
### Типичная ошибка
Проверять освобождение fixture из тела теста, которое выполняется раньше него.
### Связь с Automation QA
Тот же шаблон подходит для ресурсов с обязательным освобождением.
