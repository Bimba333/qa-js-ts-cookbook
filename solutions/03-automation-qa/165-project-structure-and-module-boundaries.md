# Решения: Структура проекта и границы модулей

## Задача 1. Концептуальные вопросы

### Ответ

Внутренняя согласованность связывает элементы одной ответственностью, связанность показывает зависимость между модулями, публичный API доступен потребителям, а внутреннее устройство скрыто. Папки не контролируют импорты и владение автоматически.

### Объяснение

Архитектура проявляется в потоке зависимостей.

### Типичная ошибка

Считать красивое дерево доказательством границ.

### Связь с Automation QA

Тесты могут обходить слой даже при наличии нужной папки.

## Задача 2. Сравнение структур

### Ответ

Организация по слоям облегчает поиск технической реализации, но разносит одну функциональность. Организация по функциональности держит бизнес-контекст рядом, но может дублировать общую инфраструктуру.

### Объяснение

Выбор зависит от основных причин изменения.

### Типичная ошибка

Объявлять один вариант универсальным.

### Связь с Automation QA

Размер команды и набора тестов влияет на компромисс.

## Задача 3. Предскажите результат выполнения кода

### Ответ

`order-42: created`. Потребитель знает только операцию `read` и возвращаемую строку, но не способ хранения данных.

### Объяснение

Публичный контракт ограничивает знания потребителя.

### Типичная ошибка

Раскрывать обработчик и транспортную модель.

### Связь с Automation QA

Внутреннюю реализацию можно заменить без изменения тестов.

## Задача 4. Найдите скрытую связанность

### Ответ

Тесты зависят от внутреннего обработчика ответа. API-модуль должен экспортировать `readOrder(id): Promise<OrderSummary>`, а обработчик оставить внутренним.

### Объяснение

Публичная операция возвращает модель предметной области.

### Типичная ошибка

Экспортировать внутреннюю функцию ради удобного импорта.

### Связь с Automation QA

Изменение формата ответа затронет только API-модуль.

## Задача 5. Automation QA

### Ответ

Загрузчик конфигурации принадлежит модулю конфигурации; SQL-запросы — слою доступа к базе данных; генератор email — модулю тестовых данных; форматирование отчёта — модулю диагностики и отчётности. Несколько связанных функций могут оставаться в одном модуле.

### Объяснение

Владельцы определяются ответственностью, а не числом файлов.

### Типичная ошибка

Переименовать `helpers` без изменения импортов.

### Связь с Automation QA

По владельцу понятно, где менять поведение.

## Задача 6. Мини-проект

### Ответ

Один допустимый вариант — гибридная структура: функциональные модули `orders` и `users` экспортируют бизнес-операции UI и REST; общие модули владеют конфигурацией, тестовыми данными и диагностикой; тесты зависят от публичных API функциональных модулей и общего жизненного цикла, а функциональные модули — от общей конфигурации и диагностики.

### Объяснение

Бизнес-контекст остаётся рядом, общая инфраструктура не дублируется.

### Типичная ошибка

Разрешить функциональным модулям импортировать тесты или внутренние детали соседней функциональности.

### Связь с Automation QA

Такая структура поддерживает оба способа взаимодействия без универсального шаблона.
