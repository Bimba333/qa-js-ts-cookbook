# Решения: Проверка API-ответов и бизнес-правил

## Задача 1. Концептуальные вопросы
### Ответ
HTTP-контракт отвечает на вопрос, корректны ли код состояния и заголовки. Проверка формы ответа подтверждает обязательную структуру и типы. Проверка бизнес-правила подтверждает смысл конкретного сценария.
### Объяснение
Три уровня дают разную диагностическую информацию.
### Типичная ошибка
Считать валидный JSON доказательством корректного поведения.
### Связь с Automation QA
Падение сразу указывает на транспортный контракт, границу структуры данных или бизнес-правило.

## Задача 2. Анализ проверок
### Ответ
`201` и `Location` относятся к HTTP-контракту. Тип ID — к форме ответа. Совпадение сохранённого `title` с отправленным значением — к проверке бизнес-правила.
### Объяснение
Один ответ содержит признаки нескольких уровней.
### Типичная ошибка
Смешивать все проверки в одно неинформативное сравнение.
### Связь с Automation QA
Разделение улучшает отчёт о причине дефекта.

## Задача 3. Предскажите результат
### Ответ
`toEqual` упадёт из-за нового поля, хотя проверяемое бизнес-правило могло сохраниться. Следует сравнивать обязательный контракт и целевые поля, если точное совпадение объекта не является договорённостью.
### Объяснение
Строгость проверки должна соответствовать риску.
### Типичная ошибка
Превращать случайную форму ответа в жёсткий контракт.
### Связь с Automation QA
Точные проверки уменьшают ложные регрессии.

## Задача 4. Поиск ошибки
### Ответ
Проверьте `201`, `Location`, обязательный строковый ID и равенство сохранённого title отправленному значению. При необходимости отдельно прочитайте ресурс по ID.
### Объяснение
`ok()` допускает несколько кодов состояния и ничего не говорит о теле.
### Типичная ошибка
Добавить снимок всего ответа вместо целевых проверок.
### Связь с Automation QA
Минимальный набор покрывает транспортный результат и смысл операции.

## Задача 5. Automation QA
### Ответ
Сообщения должны называть уровень: `ожидался код состояния 201`, `Location должен оканчиваться созданным ID`, `сохранённый title должен совпадать с отправленным значением`. Учётные данные и лишнее тело ответа в них не выводятся.
### Объяснение
Диагностика должна помогать локализовать нарушение, не раскрывая секреты.
### Типичная ошибка
Использовать одинаковое сообщение `Ошибка API` для всех проверок.
### Связь с Automation QA
Понятные сообщения ускоряют разбор неуспешных запусков.

## Задача 6. Мини-проект
### Ответ
```ts
import { expect, test } from "@playwright/test";
import { startLocalApi } from "../../examples/03-automation-qa/support/local-api.js";

test("проверяет три уровня ответа", async ({ request }) => {
  const api = await startLocalApi();
  try {
    const payload = { title: "Контракт ответа" };
    const response = await request.post(`${api.baseURL}/tasks`, { data: payload });
    expect(response.status()).toBe(201);
    const body: unknown = await response.json();
    if (
      typeof body !== "object"
      || body === null
      || !("id" in body)
      || typeof body.id !== "string"
      || !("title" in body)
      || typeof body.title !== "string"
    ) {
      throw new Error("Ответ создания не соответствует обязательной форме");
    }
    expect(response.headers().location).toBe(`/tasks/${body.id}`);
    expect(body.title).toBe(payload.title);
    const stored = await request.get(`${api.baseURL}/tasks/${body.id}`);
    expect(stored.status()).toBe(200);
  } finally {
    await api.close();
  }
});
```
### Объяснение
Каждая проверка отвечает на отдельный вопрос об ответе.
### Типичная ошибка
Проверять тело до подтверждения ожидаемого кода состояния.
### Связь с Automation QA
Сценарий даёт точную диагностику при каждом типе нарушения.
