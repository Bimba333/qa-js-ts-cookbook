# Решения: HTTP и REST для API-тестирования

## Задача 1. Концептуальные вопросы
### Ответ
HTTP задаёт протокол обмена сообщениями, REST — архитектурные ограничения взаимодействия с ресурсами. Ресурсом является задача, а JSON — одно из её представлений.
### Объяснение
Один ресурс может иметь разные представления, а JSON API не обязательно реализует REST полностью.
### Типичная ошибка
Называть REST отдельным транспортным протоколом.
### Связь с Automation QA
Это различие помогает проверять HTTP-контракт без ложных требований к именованию маршрутов.

## Задача 2. Анализ метода
### Ответ
После обоих PUT ресурс должен иметь одинаковое желаемое состояние. Идемпотентность не гарантирует одинаковые идентификаторы запросов, временные метки, записи в журналах или коды состояния каждого вызова.
### Объяснение
Свойство относится к итоговому эффекту операции.
### Типичная ошибка
Требовать побайтово одинаковые ответы.
### Связь с Automation QA
Идемпотентную подготовку легче безопасно повторять после сбоя.

## Задача 3. Предскажите результат
### Ответ
Нет. Первый DELETE может вернуть 204, второй — 404, но итоговое состояние остаётся одинаковым: ресурс отсутствует.
### Объяснение
Ответ и состояние являются разными наблюдаемыми уровнями.
### Типичная ошибка
Считать разные коды состояния доказательством неидемпотентности.
### Связь с Automation QA
Очистка может оставаться безопасно повторяемой при разных допустимых ответах.

## Задача 4. Поиск ошибки
### Ответ
Stateless означает отсутствие скрытой клиентской сессии между запросами, а не отсутствие серверных ресурсов. Каждый тест должен создавать уникальные данные и удалять их либо получать новый экземпляр сервера.
### Объяснение
Состояние протокольного взаимодействия и состояние домена различаются.
### Типичная ошибка
Создавать новый APIRequestContext вместо очистки сервера.
### Связь с Automation QA
Явное владение данными устраняет зависимость от порядка.

## Задача 5. Automation QA
### Ответ
Чтение — GET, создание с назначением ID сервером — обычно POST, полное желаемое представление — PUT, удаление — DELETE. Контракт конкретного маршрута определяет код состояния, тело ответа и ожидаемый эффект.
### Объяснение
Метод выражает намерение, но не определяет всю бизнес-семантику.
### Типичная ошибка
Считать POST обязательным только для создания.
### Связь с Automation QA
Тесты проверяют договорённость сервиса, а не только общие соглашения HTTP.

## Задача 6. Мини-проект
### Ответ
```ts
import { expect, test } from "@playwright/test";
import { startLocalApi } from "../../examples/03-automation-qa/support/local-api.js";

test("повторяет PUT", async ({ request }) => {
  const api = await startLocalApi();
  try {
    const data = { title: "Отчёт", completed: false };
    await request.put(`${api.baseURL}/tasks/task-7`, { data });
    const response = await request.put(`${api.baseURL}/tasks/task-7`, { data });
    expect(response.status()).toBe(200);
    expect(await response.json()).toEqual({ id: "task-7", ...data });
  } finally {
    await api.close();
  }
});
```
### Объяснение
Каждый тест получает отдельное состояние сервера и повторяет одну операцию.
### Типичная ошибка
Использовать фиксированный порт и не закрывать сервер.
### Связь с Automation QA
Сценарий проверяет идемпотентный итог детерминированно.
