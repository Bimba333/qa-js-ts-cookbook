# Решения: Пользовательские проверки и soft assertions

## 1. Граница custom matcher
### Ответ
Matcher оправдан, когда одно предметное правило повторяется и требует одинаковой диагностики ожидаемого и фактического значений.
### Объяснение
Простое совпадение синтаксиса ещё не создаёт правило.
### Типичная ошибка
Скрывать разные проверки под общим `toBeValid`.
### Связь с Automation QA
Имя matcher выражает бизнес-условие.

## 2. Предскажите результат
### Ответ
Контрольный флаг изменится, потому что выполнение продолжится после `expect.soft()`, но итоговый статус теста будет `failed`.
### Объяснение
Мягкий режим накапливает ошибку, а не игнорирует её.
### Типичная ошибка
Считать мягкую проверку предупреждением.
### Связь с Automation QA
Можно собрать независимые расхождения одного объекта.

## 3. Диагностика опасной мягкой проверки
### Ответ
После отсутствующего ID нельзя выполнять зависимый запрос; здесь нужна обычная блокирующая проверка.
### Объяснение
Продолжение использует уже нарушенную предпосылку.
### Типичная ошибка
Делать все проверки soft.
### Связь с Automation QA
Изменяющая операция не получает некорректный идентификатор.

## 4. Реализация matcher
### Ответ
Matcher сравнивает `id/status`, возвращает `pass` и `message` с сериализованными ожидаемым и фактическим значениями без побочных эффектов. `message` проверяет `this.isNot` и отдельно объясняет запрещённое совпадение для `.not`.
### Объяснение
Проверка остаётся чистой и диагностируемой.
### Типичная ошибка
Выполнять дополнительный запрос API из matcher или использовать одно сообщение для обычной и negated-проверки.
### Связь с Automation QA
Одинаковое предметное правило применяется к разным сценариям.

## 5. Безопасное attachment
### Ответ
Можно приложить синтетический ID, status и ответ с замаскированными чувствительными данными; token, cookie, password и персональные данные исключаются.
### Объяснение
Attachment является частью сохраняемого отчёта.
### Типичная ошибка
Прикладывать все заголовки запроса.
### Связь с Automation QA
Диагностика остаётся полезной без утечки секрета.

## 6. Мини-проект: предметные проверки
### Ответ
Три независимых поля проверяются через `expect.soft()`, целостная краткая модель задачи — через matcher, а attachment содержит JSON только с разрешёнными полями. Ошибки мягких проверок сохраняются и приводят к итоговому падению теста.
### Объяснение
Мягкие проверки собирают детали, matcher выражает общее правило.
### Типичная ошибка
Продолжать изменяющие операции после неуспешной мягкой проверки предпосылки.
### Связь с Automation QA
Отчёт показывает и предметное расхождение, и безопасный контекст.
