# Решения: gRPC Client в Automation Framework

## Задача 1. Концептуальные вопросы
### Ответ
Сгенерированный client знает RPC methods и типы messages. Обёртка ресурса предоставляет предметные операции. Configuration задаёт endpoint и безопасные значения по умолчанию. Fixture управляет жизненным циклом ресурсов. Тест выражает сценарий и проверки.
### Объяснение
Каждый слой получает одну причину для изменения.
### Типичная ошибка
Переносить проверки внутрь транспортной обёртки.
### Связь с Automation QA
Разделение сохраняет понятное направление зависимостей framework.

## Задача 2. Анализ ответственности за ресурсы
### Ответ
Singleton channel создаёт скрытое глобальное состояние и усложняет изоляцию. Закрытие channel внутри `get()` делает client непригодным для следующей операции. Создавать и закрывать его должна fixture.
### Объяснение
Управление жизненным циклом принадлежит границе потребителя, а не отдельному RPC method.
### Типичная ошибка
Смешивать операцию с ресурсом и его освобождение.
### Связь с Automation QA
Явная ответственность предотвращает взаимное влияние тестов.

## Задача 3. Предскажите результат
### Ответ
Параллельные тесты могут отправить token или correlation ID другого теста. Область worker не делает изменяемые metadata безопасными.
### Объяснение
Channel client можно переиспользовать, но контекст каждого call должен оставаться отдельным.
### Типичная ошибка
Хранить изменяемые metadata в поле обёртки.
### Связь с Automation QA
Новые metadata для каждого call сохраняют изоляцию тестов.

## Задача 4. Поиск ошибки
### Ответ
Fixture должна предоставить обёртку и выполнить только подготовку и освобождение ресурсов. Create и проверки остаются в теле теста, а очистка данных регистрируется отдельно или выполняется после `use()`.
### Объяснение
Fixture управляет ресурсами, но не скрывает смысл сценария.
### Типичная ошибка
Превращать fixture в готовый end-to-end тест.
### Связь с Automation QA
Читаемое тело теста остаётся исполняемой спецификацией.

## Задача 5. Automation QA
### Ответ
Fixture на уровне теста запускает локальный server, создаёт сгенерированный client и типизированную обёртку, передаёт обёртку тесту, затем закрывает channel и server. REST и gRPC clients остаются разными зависимостями; сценарий сравнивает только общий бизнес-результат.
### Объяснение
Общая абстракция не должна скрывать возможности конкретного протокола.
### Типичная ошибка
Создавать единый `TransportClient` с потерей status и metadata.
### Связь с Automation QA
Контекстное сравнение сохраняет диагностику обоих протоколов.

## Задача 6. Мини-проект
### Ответ
```ts
type GrpcFixture = {
  tasksGrpc: TasksGrpcClient;
};

const test = base.extend<GrpcFixture>({
  tasksGrpc: async ({}, use) => {
    const server = await startLocalGrpcServer();
    const generated = createTaskServiceClient(server.endpoint);
    const tasksGrpc = new TasksGrpcClient(generated);

    try {
      await use(tasksGrpc);
    } finally {
      generated.close();
      await server.close();
    }
  },
});

test("creates a task", async ({ tasksGrpc }) => {
  const task = await tasksGrpc.create({ title: "Fixture-owned" });
  expect(task.title).toBe("Fixture-owned");
});
```
### Объяснение
Fixture отвечает за инфраструктурные ресурсы, обёртка — за операции с ресурсом, тест — за проверки.
### Типичная ошибка
Оставлять локальный server открытым при упавшей проверке.
### Связь с Automation QA
`finally` гарантирует освобождение ресурсов при любом исходе теста.
