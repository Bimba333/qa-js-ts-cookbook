# Решения: PostgreSQL в Automation QA

## 1. Граница проверки базы данных
### Ответ
Строка подтверждает сохранённое состояние выбранной сущности, но не доказывает корректность UI, контракта HTTP/gRPC или пользовательского текста.
### Объяснение
Каждая граница наблюдает собственный результат. Проверка базы данных дополняет, а не заменяет автоматически проверку транспортного контракта.
### Типичная ошибка
Считать наличие строки доказательством успешного пользовательского сценария.
### Связь с Automation QA
Межслойный тест сохраняет основную проверку на проверяемом интерфейсе.

## 2. Предскажите результат
### Ответ
`SELECT` может вернуть пустой результат или чужое состояние; новое подключение увидит ту же общую базу данных.
### Объяснение
Подключение изолирует сеанс, но не создаёт новую базу данных.
### Типичная ошибка
Пытаться устранить проблему общих данных пересозданием клиента.
### Связь с Automation QA
Уникальные ID и явное владение устраняют зависимость от порядка выполнения.

## 3. Диагностика неверной границы
### Ответ
Потеряна проверка наблюдаемого результата UI: пользователь может видеть неверный статус при правильной строке.
### Объяснение
Сохранение данных и их отображение являются разными обязанностями.
### Типичная ошибка
Проверять внутреннюю реализацию вместо цели теста.
### Связь с Automation QA
База данных полезна как дополнительная проверка или источник диагностики.

## 4. Реализация проверки
### Ответ
```ts
const result = await client.query<{ id: string; title: string }>(
  "SELECT id, title FROM tasks WHERE id = $1",
  [taskId],
);
expect(result.rows).toEqual([{ id: taskId, title: expectedTitle }]);
```
### Объяснение
Стабильный ID выбирает одну строку, а явный список столбцов ограничивает связанность со схемой.
### Типичная ошибка
Использовать `SELECT *` и сравнивать технические колонки.
### Связь с Automation QA
Проверяются только бизнес-поля, относящиеся к сценарию.

## 5. Сценарий Automation QA
### Ответ
Прямое создание данных подходит, когда оно не является предметом проверки; чтение базы данных — для проверки сохранения и локализации расхождения.
### Объяснение
Роль базы данных определяется целью теста.
### Типичная ошибка
Всегда создавать исходные данные напрямую в базе данных.
### Связь с Automation QA
Если создание является целью API-теста, данные должны создаваться через API.

## 6. Мини-проект: владение данными
### Ответ
```ts
const id = `task-${crypto.randomUUID()}`;
try {
  await client.query("INSERT INTO tasks (id, title, priority) VALUES ($1, $2, $3)", [id, title, "low"]);
  const row = await client.query("SELECT title FROM tasks WHERE id = $1", [id]);
  expect(row.rows[0]?.title).toBe(title);
} finally {
  await client.query("DELETE FROM tasks WHERE id = $1", [id]);
}
```
### Объяснение
Один сценарий владеет идентификатором от создания до очистки.
### Типичная ошибка
Удалять все строки таблицы.
### Связь с Automation QA
Точная очистка безопасна для повторных запусков.
