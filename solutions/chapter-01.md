# Решения. Глава 1. Как пользоваться курсом

## Проверка понимания

### 1. Почему чтение без запуска примеров дает слабый результат

Чтение создает ощущение узнавания. Пример кажется понятным, пока его не нужно выполнить, изменить или объяснить.

Запуск кода проверяет модель. Если ожидание совпало с результатом, модель можно закрепить. Если не совпало, нужно найти неверное предположение.

### 2. Почему порядок глав важен

Следующие темы используют модели из предыдущих глав. Если пропустить раннюю тему, поздняя тема может стать набором правил без причины.

Например, функции труднее понимать без переменных, а асинхронность труднее понимать без функций и порядка выполнения кода.

### 3. Что сделать перед запуском примера

Перед запуском нужно предсказать результат и записать ожидание.

Это превращает запуск в проверку гипотезы. Без предсказания результат просто наблюдается, но модель не проверяется.

### 4. Почему решения читают после попытки

Решение полезно только тогда, когда есть собственный ответ для сравнения.

Если открыть решение сразу, можно понять текст решения, но не проверить, как вы рассуждали бы самостоятельно.

### 5. Для чего используется `playground/`

`playground/` используется для маленьких экспериментов:

* запуск примеров;
* проверка гипотез;
* намеренное изменение кода;
* изучение сообщений об ошибках.

### 6. Чем заметка отличается от копии главы

Копия главы повторяет текст. Заметка фиксирует личную модель понимания.

Хорошая заметка содержит механизм, минимальный пример, типичную ошибку и связь с Automation QA.

### 7. Как возвращаться к сложной теме

Нужно сформулировать конкретный вопрос, вернуться к нужному разделу, запустить минимальный пример и переписать объяснение своими словами.

Широкая формулировка вроде "я не понял JavaScript" не помогает. Лучше писать конкретно: "я не понимаю, почему функция изменила внешний объект".

### 8. Почему нужна связь с тестовым кодом

Курс ориентирован на Automation QA. Если не связывать тему с тестами, helper-функциями, fixtures, API-клиентами и проверками, знание останется учебным и хуже перенесется в рабочие задачи.

## Анализ кода

Код:

```javascript
let retryCount = 0;

function increaseRetryCount() {
  retryCount = retryCount + 1;
}

increaseRetryCount();

console.log(retryCount);
```

В консоль будет выведено:

```text
1
```

Строка, которая изменила значение:

```javascript
retryCount = retryCount + 1;
```

Функция была вызвана один раз, поэтому значение увеличилось с `0` до `1`.

Возможные маленькие эксперименты:

* вызвать функцию два раза;
* изменить начальное значение на `3`;
* убрать вызов функции;
* добавить второй `console.log` до вызова функции.

Каждый эксперимент проверяет одну небольшую гипотезу.

## Написание кода

Один из возможных вариантов:

```text
Ожидаемый результат: в консоль будет выведено active.
```

```javascript
const userStatus = 'active';

console.log(userStatus);
```

Проверка в `playground/`:

1. Создать временный файл.
2. Вставить код.
3. Запустить файл.
4. Сравнить фактический вывод с ожидаемым.
5. Изменить значение `userStatus` и повторить запуск.

Пример проверяет одну идею: переменная хранит значение, которое можно вывести в консоль.

## Поиск ошибок

Неверная часть подхода:

```text
Если решение понятно, значит тему можно считать изученной.
```

Понятность готового решения не доказывает, что читатель смог бы построить это решение самостоятельно.

Ощущение понятности часто возникает из-за узнавания знакомых слов и структуры. Но понимание проверяется тогда, когда нужно предсказать результат, написать код или объяснить ошибку без подсказки.

Исправленный процесс:

```text
Прочитать главу
│
▼
Предсказать результаты примеров
│
▼
Запустить и изменить код
│
▼
Выполнить практику
│
▼
Записать сомнения
│
▼
Открыть решения
│
▼
Сравнить ход рассуждения
```

## QA-задачи

### Задача 1

Возможные применения функций:

UI-тесты:

```text
Функция openProfilePage(page) открывает страницу профиля.
```

API-тесты:

```text
Функция createUser(apiClient, userData) отправляет запрос на создание пользователя.
```

Подготовка тестовых данных:

```text
Функция buildUserData() возвращает объект с данными тестового пользователя.
```

### Задача 2

Пример цикла анализа flaky-теста:

Ожидание:

```text
Helper должен подготовить данные пользователя, не изменяя общий объект.
```

Фактический результат:

```text
После вызова helper общий объект изменился, и следующий тест получил неверные данные.
```

Гипотеза для `playground/`:

```text
Проверить, изменяет ли функция объект, который получила на вход.
```

Минимальный эксперимент:

```javascript
const baseUser = {
  email: 'qa@example.com'
};

function updateEmail(user) {
  user.email = 'changed@example.com';
}

updateEmail(baseUser);

console.log(baseUser.email);
```

Вывод в заметки:

```text
Если helper получает объект и меняет его свойства, исходный объект тоже меняется.
QA-риск: общий объект тестовых данных может повлиять на другие тесты.
```

## Мини-проект

Один из возможных шаблонов:

```text
Глава:

Главная идея:

Механизм:

Минимальный пример:

Ожидаемый результат:

Фактический результат:

Почему результат именно такой:

Типичная ошибка:

QA-применение:

Вопрос для повторения:
```

Почему такой шаблон полезен:

* он заставляет выделить главную идею;
* отделяет ожидание от фактического результата;
* требует объяснить механизм;
* связывает тему с Automation QA;
* оставляет вопрос для будущего повторения.

## Типичные ошибки

### Ошибка 1. Делать шаблон слишком большим

Если заметка требует слишком много полей, ее перестают заполнять. Лучше использовать короткий шаблон, который реально применяется после каждой главы.

### Ошибка 2. Записывать только результат

Результат без объяснения не показывает понимание. Нужно фиксировать причину.

### Ошибка 3. Не записывать QA-применение

Без QA-применения тема остается отдельной учебной единицей. Для этого курса важно связывать механизм с тестовым кодом.

## Возможные улучшения

После выполнения практики можно:

* создать один файл с шаблоном заметок;
* заполнить шаблон для первой главы;
* добавить в заметки раздел "ошибка недели";
* раз в несколько глав возвращаться к старым заметкам и уточнять формулировки.
