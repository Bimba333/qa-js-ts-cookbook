# Решения: Event Loop

## Концептуальные вопросы

### 1. Зачем нужен Event Loop?

Ответ: чтобы координировать возвращение готовых отложенных задач в выполнение JavaScript.

Объяснение: Event Loop связывает Call Stack, очереди и среду выполнения.

Распространённая ошибка: считать Event Loop исполнителем JavaScript-кода.

Связь с Automation QA: он объясняет, когда выполнится генерация отчета или уведомление.

### 2. Почему Event Loop нельзя считать JavaScript Engine?

Ответ: JavaScript Engine выполняет код, а Event Loop координирует порядок возвращения задач.

Объяснение: это разные части модели выполнения.

Типичная ошибка: смешивать Engine, Runtime и Event Loop.

Связь с Automation QA: такое различение помогает читать порядок логов.

### 3. Что должно произойти с Call Stack перед выполнением отложенного кода?

Ответ: текущий Call Stack должен освободиться.

Объяснение: отложенная задача не выполняется посреди текущей синхронной функции.

Распространённая ошибка: ожидать выполнение таймера внутри текущего синхронного блока.

Связь с Automation QA: отчет не загрузится до завершения текущей синхронной части раннера.

### 4. Почему асинхронность не означает параллельное выполнение JavaScript-кода?

Ответ: отложенная работа может ждать в среде выполнения, но JavaScript-обратный вызов выполняется позже в Call Stack.

Объяснение: Event Loop возвращает задачу в обычное выполнение.

Частое заблуждение: считать, что два JavaScript-обработчика выполняются одновременно.

Связь с Automation QA: два лога из JavaScript-обработчиков все равно имеют определенный порядок.

### 5. Как Event Loop помогает объяснять порядок логов в тестовом фреймворке?

Ответ: он показывает, почему синхронные логи идут раньше отложенных задач.

Объяснение: сначала завершается текущий Call Stack, потом возвращаются готовые задачи.

Распространённая ошибка: объяснять порядок только расположением строк в файле.

Связь с Automation QA: это помогает разбирать задержанную генерацию отчета.

## Чтение кода

Ответ: `report: generated` выводится после `runner: finish`.

Объяснение: `setTimeout()` планирует задачу, а текущий синхронный код завершается первым.

Распространённая ошибка: считать нулевую задержку немедленным выполнением.

Связь с Automation QA: генерация отчета может быть запланирована сейчас, но выполниться позже.

## Предскажите результат выполнения

Ответ:

```text
A
C
B
```

Объяснение: `A` и `C` — синхронные строки. `B` выполняется как отложенная задача.

Распространённая ошибка: ожидать `A B C`.

Связь с Automation QA: синхронные шаги раннера завершаются до отложенной работы.

## Отладка

Ответ: `setTimeout(..., 0)` не выполняется между синхронными строками.

Объяснение: задача попадает в очередь и ждет освобождения Call Stack.

Типичная ошибка: воспринимать `0` как выполнение "прямо сейчас".

Связь с Automation QA: загрузка отчета не прерывает выполнение тестов.

## Задание Automation QA

Ответ:

```javascript
console.log('runner: start');
console.log('test: executed');

setTimeout(function generateReport() {
  console.log('report: generated');
}, 0);
```

Объяснение: первые две строки синхронные, отчет выполняется позже.

Распространённая ошибка: ожидать генерацию отчета до завершения синхронного кода.

Связь с Automation QA: это базовая модель отложенной отчетности.

## Мини-проект

Ответ:

```text
prepareEnvironment()
executeTests()
notifyCompletion() как Promise-обработчик
generateReport() как таймер
```

Объяснение: синхронные функции выполняются первыми. Promise-обработчик будет разобран подробнее в главе про Microtasks и обычно идет раньше таймера.

Частое заблуждение: считать все отложенные задачи одинаковыми.

Связь с Automation QA: порядок уведомления и отчета зависит от типа очереди.
