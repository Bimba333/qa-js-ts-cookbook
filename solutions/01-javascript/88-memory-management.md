# Решения: Memory Management

## Концептуальные вопросы

### 1. Почему memory leak возможен при наличии Garbage Collector?

Ответ: потому что объект может оставаться reachable, хотя логически уже не нужен.

Объяснение: Garbage Collector не удаляет reachable-объекты.

Типичная ошибка: считать Garbage Collector защитой от любых проблем с памятью.

Связь с Automation QA: старые логи могут оставаться в памяти, если их хранит общий буфер.

### 2. Что такое long-lived reference?

Ответ: ссылка, которая живет долго и удерживает объект в памяти.

Объяснение: глобальный массив, Map или объект состояния могут удерживать данные весь запуск процесса.

Типичная ошибка: хранить временные данные в долгоживущих структурах без очистки.

Связь с Automation QA: общий cache тестовых данных может расти после каждого теста.

### 3. Как closure может удерживать объект?

Ответ: внутренняя функция может сохранять доступ к переменным внешней функции.

Объяснение: если внешняя переменная содержит большой объект, closure может сделать его reachable.

Типичная ошибка: думать, что завершение внешней функции всегда освобождает все ее данные.

Связь с Automation QA: callback отчета может удерживать большой объект с логами.

### 4. Почему timers могут продлевать жизнь данных?

Ответ: timer удерживает callback, а callback может ссылаться на внешние данные.

Объяснение: пока timer активен, связанные данные могут оставаться reachable.

Типичная ошибка: запускать timers и забывать очищать их, когда они больше не нужны.

Связь с Automation QA: retry-таймер может удерживать данные старого теста.

### 5. Почему cache должен иметь правило очистки?

Ответ: без очистки cache продолжает удерживать старые значения.

Объяснение: для Garbage Collector значения внутри cache остаются reachable.

Типичная ошибка: добавлять данные в cache, но не удалять их после теста.

Связь с Automation QA: test data cache должен очищаться после завершения сценария.

## Чтение кода

Объяснение: `logBuffer` является долгоживущим массивом и хранит ссылки на объекты логов.

Типичная ошибка: считать, что объект внутри функции исчезает после завершения функции, даже если он добавлен в внешний массив.

Связь с Automation QA: общий буфер логов нужно очищать или ограничивать.

## Предскажите результат

Ответ: код выведет `false`.

Объяснение: `cache.delete('T-1')` удаляет запись из Map, поэтому cache больше не содержит ключ `T-1`.

Связь с Automation QA: очистка cache после теста помогает не удерживать старые test data.

Типичная ошибка: смотреть только на область видимости, где был создан объект, и не учитывать возвращенную функцию.

Связь с Automation QA: функция печати отчета может удерживать отчетные данные дольше ожидаемого.

## Задание Automation QA

Ответ:

```text
logs              -> logBuffer
screenshots       -> массив артефактов или отчет
cached test data  -> Map / объект cache
temporary reports -> currentReport / history
```

Объяснение: каждую группу данных удерживает конкретная ссылка или коллекция.

Типичная ошибка: очищать только одну переменную и забывать про кэш или историю.

Связь с Automation QA: после теста важно очищать все временные структуры, которые больше не нужны.

## Мини-проект

Ответ:

```javascript
const testDataCache = new Map();

function saveTestData(testId, data) {
  testDataCache.set(testId, data);
}

function getTestData(testId) {
  return testDataCache.get(testId);
}

function clearTestData(testId) {
  testDataCache.delete(testId);
}

function clearAllTestData() {
  testDataCache.clear();
}
```

Объяснение: методы очистки удаляют ссылки из Map, после чего объекты могут стать кандидатами на сборку, если других ссылок нет.

Типичная ошибка: реализовать только `save` и `get`, но забыть операции очистки.

Связь с Automation QA: такой cache безопаснее использовать в тестовом фреймворке, потому что у данных есть понятный жизненный цикл.
