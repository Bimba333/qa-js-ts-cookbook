# Решения: Почему появился TypeScript

## Концептуальные вопросы

### 1. Почему JavaScript остается фундаментом для TypeScript?

Ответ: TypeScript строится поверх JavaScript.

Объяснение: после проверки TypeScript-код все равно превращается в JavaScript для выполнения.

Типичная ошибка: думать, что TypeScript отменяет механизмы JavaScript.

Связь с Automation QA: async/await, modules, objects и errors работают по JavaScript-модели.

### 2. Какая проблема возникает из-за dynamic typing в больших проектах?

Ответ: форма данных может не совпасть с ожиданием функции.

Объяснение: JavaScript не всегда обнаруживает это до запуска конкретного участка кода.

Типичная ошибка: считать, что если код запускается, все договоренности между модулями корректны.

Связь с Automation QA: test data может не совпасть с request builder.

### 3. Почему late error detection дорого обходится Automation QA framework?

Ответ: ошибка может проявиться только в CI или в длинном end-to-end сценарии.

Объяснение: чем позже найдена ошибка, тем дороже понять ее источник.

Типичная ошибка: замечать проблему только после failed test, хотя ее можно было поймать раньше.

Связь с Automation QA: неверный payload может пройти через helper, API client и assertion.

### 4. Почему refactoring сложнее без дополнительных проверок?

Ответ: переименование поля или изменение формы объекта может сломать удаленные участки кода.

Объяснение: без дополнительных проверок разработчик должен вручную помнить все связи.

Типичная ошибка: переименовать поле в одном месте и забыть request builder.

Связь с Automation QA: refactoring Page Objects и helpers часто затрагивает десятки тестов.

### 5. Почему TypeScript не заменяет good JavaScript practices?

Ответ: TypeScript помогает проверять договоренности, но не проектирует архитектуру сам.

Объяснение: clear naming, small functions и single responsibility остаются обязанностью разработчика.

Типичная ошибка: ожидать, что TypeScript исправит хаотичный код.

Связь с Automation QA: типы помогают, но плохие helpers и дублирование все равно останутся проблемой.

Объяснение: JavaScript создаст payload с `name: undefined`.

Типичная ошибка: заметить проблему только после API failure.

Связь с Automation QA: такие ошибки часто возникают между test data и request builders.

Объяснение: объект содержит `name`, но функция читает `title`.

Типичная ошибка: ожидать ошибку вместо `undefined`.

Связь с Automation QA: report может получить пустое поле и сломаться позже.

Объяснение: ошибка формы данных может стать видимой только после отправки request или проверки response.

Типичная ошибка: искать проблему в API client, хотя источник в test data.

Связь с Automation QA: TypeScript в будущем должен помогать видеть такие несовпадения раньше.

## Задание Automation QA

Ответ:

```text
test data
│
▼
request builder
│
▼
api client
│
▼
assertion
```

Ошибка формы данных становится дорогой, если проходит несколько слоев и проявляется только в assertion.

Объяснение: чем дальше ошибка проходит, тем сложнее найти root cause.

Типичная ошибка: исправлять assertion вместо проверки входных данных.

Связь с Automation QA: большие frameworks нуждаются в ранней проверке договоренностей между слоями.

## Мини-проект

Ответ:

```text
неправильная форма test data
│
неверные параметры helper-функции
│
небезопасный refactoring
│
ошибки между modules
```

Объяснение: TypeScript должен помочь находить такие проблемы до запуска сценария.

Типичная ошибка: ждать от TypeScript проверки бизнес-логики вместо проверки форм данных и договоренностей.

Связь с Automation QA: следующий раздел покажет, как сделать framework безопаснее при росте проекта.
