# Решения: JavaScript Modules

## Концептуальные вопросы

### 1. Почему большой файл становится сложным для поддержки?

Ответ: в нем смешиваются разные ответственности.

Объяснение: конфигурация, логирование, проверки и отчеты меняются по разным причинам. Если они находятся в одном файле, любое изменение требует читать слишком много несвязанного кода.

Типичная ошибка: думать, что проблема большого файла только в количестве строк.

Связь с Automation QA: один большой runner быстро становится узким местом фреймворка.

### 2. Что означает "ответственность модуля"?

Ответ: модуль должен отвечать за одну понятную часть системы.

Объяснение: `config.js` хранит настройки, `logger.js` логирует, `reporter.js` создает отчет.

Типичная ошибка: создавать файл `utils.js`, куда попадает все подряд.

Связь с Automation QA: понятные модули проще переиспользовать между UI, API и подготовительным кодом.

### 3. Чем `export` отличается от `import`?

Ответ: `export` отдает значение наружу, `import` получает значение из другого модуля.

Объяснение: экспорт формирует public API файла, импорт создает зависимость от этого API.

Типичная ошибка: пытаться импортировать значение, которое не было экспортировано.

Связь с Automation QA: runner может импортировать config, logger и assertions только если они явно экспортированы.

### 4. Когда удобен named export?

Ответ: когда модуль отдает несколько именованных значений.

Объяснение: например, `baseUrl`, `retries` и `timeout` удобно экспортировать как named exports.

Типичная ошибка: использовать default export для набора несвязанных значений.

Связь с Automation QA: конфигурационный модуль часто содержит несколько именованных настроек.

### 5. Когда удобен default export?

Ответ: когда у модуля есть один главный экспорт.

Объяснение: например, `logger.js` может экспортировать одну основную функцию логирования.

Типичная ошибка: использовать default export там, где файл отдает много равноправных функций.

Связь с Automation QA: модуль логирования или API-клиент часто воспринимаются как главный результат файла.

### 6. Что показывает dependency graph?

Ответ: какие модули от каких модулей зависят.

Объяснение: если `runner.js` импортирует `config.js`, между ними есть зависимость.

Типичная ошибка: не замечать циклические или слишком плотные связи между файлами.

Связь с Automation QA: dependency graph помогает понять, почему изменение одного вспомогательного модуля может влиять на раннер.

Ответ:

```text

```

Объяснение: `runner.js` импортирует default export из `logger.js` и вызывает функцию `log`.

Типичная ошибка: ожидать, что имя default import обязательно должно совпадать с именем функции.

Связь с Automation QA: logger можно импортировать в разные части фреймворка.

## Отладка

Ответ: `baseUrl` не экспортирован из `config.js`.

Объяснение: переменная объявлена внутри модуля, но без `export` она не входит в public API.

Типичная ошибка: забыть `export` перед значением, которое нужно использовать в другом файле.

Связь с Automation QA: runner не сможет прочитать настройки окружения, если config их не экспортирует.

## Задание Automation QA

Ответ:

```text
config.js     -> настройки окружения
logger.js     -> вывод сообщений
assertions.js -> функции проверок
reporter.js   -> создание отчетов
runner.js     -> сборка сценария запуска
```

Объяснение: каждый файл имеет одну причину для изменения.

Типичная ошибка: оставить проверки и отчеты внутри `runner.js`.

Связь с Automation QA: такая структура делает фреймворк расширяемым.

## Мини-проект

Ответ:

```text
runner.js
│
├── config.js
├── logger.js
├── reporter.js
└── assertions.js
```

Объяснение: `runner.js` собирает систему, а остальные модули не должны зависеть от него.

Типичная ошибка: сделать `logger.js` зависимым от `runner.js`.

Связь с Automation QA: инфраструктурные модули должны быть переиспользуемыми.
