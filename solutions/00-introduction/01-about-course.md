# Решения. Глава 0. О курсе

## Проверка понимания

### 1. Почему курс начинается с JavaScript

TypeScript и Playwright строятся поверх JavaScript.

TypeScript проверяет типы до выполнения программы, но после компиляции выполняется JavaScript. Playwright предоставляет API для автоматизации браузера, но тесты все равно используют функции, объекты, Promise, `async / await`, модули и ошибки JavaScript.

Если не понимать JavaScript, сложные ошибки в автотестах будут выглядеть как поведение инструмента, хотя причина часто находится в языке.

### 2. Что означает принцип "понимание важнее запоминания"

Запоминание дает готовую формулировку. Понимание дает модель, которую можно применить в новой ситуации.

Например, можно запомнить, что `const` запрещает переназначение. Но важно понимать, что `const` защищает binding переменной, а не делает объект неизменяемым.

### 3. Почему TypeScript не заменяет runtime-проверки

TypeScript-типы существуют на этапе проверки и компиляции. В runtime они не проверяют реальные данные автоматически.

Если API вернул JSON неправильной формы, TypeScript не остановит программу сам по себе. Для этого нужны assertions, validators или contract tests.

### 4. Чем отличается синтаксис от механизма

Синтаксис показывает, как записать конструкцию.

Механизм объясняет, почему конструкция работает именно так: что происходит в памяти, как ищется переменная, когда выполняется callback, почему Promise переходит в определенное состояние.

### 5. Почему QA-инженеру нужны Stack, Heap, References и Event Loop

Эти темы напрямую влияют на стабильность автотестов.

Stack помогает понимать порядок вызовов и ошибки выполнения. Heap и References помогают понимать изменение объектов и тестовых данных. Event Loop помогает понимать асинхронность, Promise и причины flaky-поведения.

### 6. Как связаны директории репозитория

`docs/` содержит главы с объяснениями.

`examples/` содержит минимальные примеры кода.

`practice/` содержит задания без ответов.

`solutions/` содержит решения, объяснения, типичные ошибки и возможные улучшения.

### 7. Почему решения нужно смотреть после попытки

Решения полезны только тогда, когда уже есть собственная гипотеза. Если сразу открыть ответ, можно узнать правильную формулировку, но не проверить собственную модель понимания.

## Анализ кода

Код:

```javascript
const testUser = {
  email: 'qa@example.com'
};

const userFromHelper = testUser;

userFromHelper.email = 'changed@example.com';

console.log(testUser.email);
```

В консоль будет выведено:

```text
changed@example.com
```

`testUser` и `userFromHelper` указывают на один и тот же объект. Переменная `userFromHelper` не создает копию объекта. Она получает ту же ссылку.

Модель:

```text
testUser ───────┐
                ├──► Object in Heap
userFromHelper ─┘    {
                      email: 'changed@example.com'
                    }
```

В Automation QA такая ситуация опасна, если helper изменяет общий объект тестовых данных. Один тест может подготовить данные, второй получит уже измененный объект, и падение будет выглядеть случайным.

## Написание кода

Один из возможных вариантов:

```javascript
let currentStatus = 'created';
currentStatus = 'paid';

const order = {
  status: 'created'
};

order.status = 'paid';
```

В первой части происходит переназначение переменной `currentStatus`.

Во второй части переменная `order` остается связанной с тем же объектом, но изменяется свойство объекта.

Если попытаться переназначить `order`, будет ошибка:

```javascript
const order = {
  status: 'created'
};

order = {
  status: 'paid'
};
```

Причина: `const` запрещает переназначить binding переменной.

## Поиск ошибок

Неверная часть рассуждения:

```text
Если объект описан TypeScript-типом, значит API точно вернет объект такой формы.
```

TypeScript не управляет сервером и не проверяет реальный JSON автоматически. Тип описывает ожидание в коде, но данные приходят извне.

В API-тест стоит добавить runtime-проверки:

```typescript
const user = await response.json();

expect(typeof user.id).toBe('string');
expect(typeof user.email).toBe('string');
expect(user.email).toContain('@');
```

Позже такие проверки можно вынести в отдельный validation helper.

## QA-задача

Если тест падает после изменения общего объекта с тестовыми данными, в первую очередь нужно изучить References, Stack и Heap.

Вопросы для анализа:

* где создается объект с тестовыми данными;
* передается ли он в helper по ссылке;
* изменяет ли helper исходный объект;
* переиспользуется ли объект между тестами;
* запускаются ли тесты параллельно;
* есть ли копирование данных перед изменением.

Снизить риск можно несколькими способами:

* не изменять общий объект внутри helper-функций;
* создавать новый объект на основе старого;
* использовать factory-функции для тестовых данных;
* явно отделять исходные данные от данных, подготовленных для конкретного теста;
* добавлять тесты на helper-функции, которые проверяют отсутствие побочных изменений.

## Мини-проект

Пример возможного плана:

```text
1. Читать одну главу за один учебный подход.
2. После главы запускать все примеры локально.
3. Каждый пример объяснять письменно в 3-5 предложениях.
4. Выполнять практику без решений.
5. Открывать решения только после собственной попытки.
6. Ошибки фиксировать в отдельном файле: тема, неверное ожидание, правильная модель.
7. После каждой темы записывать, где она встречается в Automation QA.
```

Такой план полезен, потому что он проверяет не только факт прочтения главы, но и способность объяснить механизм.

## Типичные ошибки

### Ошибка 1. Переписать ответ из решения

Это не формирует понимание. Лучше сначала дать собственный ответ, даже если он неполный, а затем сравнить его с решением.

### Ошибка 2. Ограничиться синтаксисом

Если после задания остается только знание "как написать", но нет ответа "почему это работает", тему нужно перечитать.

### Ошибка 3. Не связывать тему с QA

Курс построен для Automation QA. После каждой темы полезно задавать вопрос: где это появится в тестах, helper-функциях, fixtures, API-клиентах или framework architecture.

## Возможные улучшения

После выполнения практики можно дополнительно:

* переписать ответы через неделю и сравнить формулировки;
* найти похожий пример в своем рабочем проекте;
* составить список JavaScript-тем, которые сейчас вызывают больше всего вопросов;
* добавить к личному плану конкретное расписание занятий.
