# Решения. Глава 3. Рабочее окружение

## Проверка понимания

### 1. Почему окружение нужно подготовить заранее

Если окружение не готово, ошибки запуска будут мешать изучению JavaScript. Читатель будет тратить внимание на проблемы команд, путей и файлов вместо темы главы.

Готовое окружение снижает шум: файл создается в нужной папке, команда запускается предсказуемо, результат виден в терминале.

### 2. Зачем нужен Node.js

Node.js нужен, чтобы запускать JavaScript-файлы вне браузера.

В рамках этой главы достаточно понимать Node.js как инструмент, который выполняет файл `.js` по команде:

```bash
node file.js
```

### 3. Что такое npm

npm — это инструмент для работы с JavaScript-пакетами.

В этой главе npm нужен только на базовом уровне: проверить, что он установлен и доступен командой:

```bash
npm -v
```

### 4. Почему VS Code удобен

VS Code объединяет редактор файлов, встроенный терминал, подсветку кода, расширения и удобную навигацию по проекту.

Для курса это важно, потому что читатель постоянно переключается между `docs/`, `practice/`, `solutions/` и `playground/`.

### 5. Для чего используется `playground/`

`playground/` используется для экспериментов:

* создать временный файл;
* запустить минимальный пример;
* проверить гипотезу;
* прочитать ошибку;
* изменить одну деталь и повторить запуск.

### 6. Почему важна текущая папка

Команды в терминале выполняются относительно текущей папки.

Если файл находится в `playground/hello.js`, команда из корня проекта будет:

```bash
node playground/hello.js
```

Если терминал уже открыт внутри `playground/`, команда будет:

```bash
node hello.js
```

### 7. Чем ошибка окружения отличается от ошибки в коде

Ошибка окружения связана с инструментами, путями, установкой или текущей папкой.

Ошибка в коде возникает, когда файл найден и запущен, но его содержимое не может быть выполнено правильно.

Пример ошибки окружения:

```text
Cannot find module
```

если файл указан неверно или не существует.

### 8. Почему решения открывают после попытки

Собственная попытка проверяет мышление. Решение нужно для сравнения рассуждений.

Если открыть решение сразу, диагностика не тренируется: читатель узнает ответ, но не проверяет, смог бы сам найти причину.

## Чтение кода

Код:

```javascript
console.log('Environment is ready');
```

На уровне результата файл выводит строку:

```text
Environment is ready
```

Если файл сохранен как `playground/environment-check.js`, запуск из корня проекта:

```bash
node playground/environment-check.js
```

Если файл не запускается, сначала нужно проверить:

* существует ли файл;
* правильно ли написано имя;
* есть ли расширение `.js`;
* из какой папки запущена команда;
* установлен ли Node.js.

## Предскажите результат перед запуском

Код:

```javascript
console.log('First run');
console.log('Second run');
```

Ожидаемый вывод:

```text
First run
Second run
```

Объяснение:

В файле две строки вывода. Node.js выполняет файл сверху вниз, поэтому сначала появляется `First run`, затем `Second run`.

Глубокие правила выполнения JavaScript будут изучаться позже. Здесь достаточно увидеть порядок вывода.

## Написание небольшого кода

Файл:

```text
playground/qa-message.js
```

Код:

```javascript
console.log('QA environment is ready');
```

Запуск из корня проекта:

```bash
node playground/qa-message.js
```

Ожидаемый вывод:

```text
QA environment is ready
```

Объяснение:

Файл содержит одну строку, которая выводит текст в терминал. Если вывод совпал, Node.js доступен, путь указан правильно, файл создан корректно.

## Задача на отладку

Команда:

```bash
node playground/missing-file.js
```

Ошибка:

```text
Cannot find module
```

Эта ошибка означает, что Node.js не смог найти файл по указанному пути.

Первые проверки:

1. Проверить, существует ли файл `playground/missing-file.js`.
2. Проверить, правильно ли написано имя файла.
3. Проверить, из какой папки запущена команда.

Не нужно сразу менять JavaScript-код, потому что проблема может быть не в содержимом файла. Если файл не найден, Node.js даже не дошел до выполнения кода.

## QA-задачи

### Задача 1

Automation QA Engineer должен фиксировать команду запуска тестов, потому что результат зависит от контекста запуска.

Команда может определять:

* какие тесты запускаются;
* какое окружение используется;
* какие переменные переданы;
* какой reporter включен;
* локальный это запуск или CI.

Без команды сложно воспроизвести ошибку.

### Задача 2

Пример checklist:

```text
1. Выполнить node -v.
2. Выполнить npm -v.
3. Выполнить pwd и проверить текущую папку.
4. Проверить, что файл находится в playground/.
5. Проверить расширение .js.
6. Запустить node playground/hello.js.
7. Если ошибка, прочитать тип ошибки и путь к файлу.
```

Объяснение:

Checklist идет от окружения к файлу и только потом к коду. Это снижает риск случайно менять правильный код при ошибке пути или установки.

## Мини-проект

Один из возможных вариантов.

Файл:

```text
playground/my-environment-check.js
```

Код:

```javascript
console.log('My environment is ready');
```

Ожидаемый результат:

```text
My environment is ready
```

Команда:

```bash
node playground/my-environment-check.js
```

Фактический результат должен совпасть с ожидаемым.

Если возникла ошибка `Cannot find module`, возможная гипотеза:

```text
Файл создан не в playground/ или имя указано неверно.
```

Проверка:

```bash
ls playground
```

Объяснение:

Мини-проект проверяет полный цикл: создать файл, предсказать результат, запустить, прочитать вывод, при ошибке сформулировать гипотезу и проверить ее.

## Типичные ошибки

### Ошибка 1. Проверять код до проверки пути

Если ошибка говорит, что файл не найден, сначала нужно проверить путь и имя файла.

### Ошибка 2. Не записывать ожидаемый результат

Без ожидаемого результата запуск превращается в наблюдение. Предсказание делает запуск проверкой понимания.

### Ошибка 3. Игнорировать текущую папку

Одна и та же команда может работать или не работать в зависимости от того, из какой папки она запущена.

## Возможные улучшения

После выполнения практики можно:

* оставить в `playground/` файл проверки окружения;
* добавить в личные заметки команды `node -v`, `npm -v`, `pwd`, `ls`;
* записать типичные ошибки запуска и способы проверки;
* повторить запуск после перезапуска терминала.
