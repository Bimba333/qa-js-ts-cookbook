# STYLE_GUIDE.md

# Руководство по написанию материалов курса

> Версия: 1.0
> Статус: Active

---

# 1. Назначение документа

Этот документ определяет единый стиль написания всего курса.

Любой новый раздел книги должен соответствовать данному документу.

Цель — добиться того, чтобы независимо от того, когда была написана глава, она выглядела как часть одного цельного учебника.

---

# 2. Главный принцип

Курс объясняет механизмы.

Не синтаксис.

Если приходится выбирать между:

* объяснить внутренний механизм;
* показать больше конструкций языка,

всегда выбирается объяснение механизма.

---

# 3. Стиль изложения

Материал должен быть:

* инженерным;
* спокойным;
* последовательным;
* максимально понятным;
* без художественных отступлений;
* без мотивационных вставок;
* без воды.

Текст должен быть плотным, но легко читаемым.

---

# 4. Язык

Основной язык курса — русский.

Общепринятые технические термины остаются на английском языке.

Примеры:

* Execution Context
* Call Stack
* Event Loop
* Promise
* Closure
* Runtime
* Heap
* Stack
* Garbage Collector

Не использовать искусственные переводы, если они не применяются в профессиональной среде.

---

# 5. Правило объяснения

Каждая новая тема объясняется строго в следующем порядке.

## Шаг 1

Какая проблема существовала.

---

## Шаг 2

Почему появилась рассматриваемая конструкция.

---

## Шаг 3

Как она работает внутри.

---

## Шаг 4

Как выглядит синтаксис.

---

## Шаг 5

Простейший пример.

---

## Шаг 6

Практический пример.

---

## Шаг 7

Реальный пример из Automation QA.

---

## Шаг 8

Типичные ошибки.

---

## Шаг 9

Практические задания.

---

# 6. Правило "Почему?"

Каждое объяснение должно отвечать на вопрос:

> Почему это работает именно так?

Недостаточно написать:

> `const` запрещает переназначение.

Необходимо объяснить:

* почему такое ограничение появилось;
* какую проблему оно решает;
* почему это не делает значение неизменяемым.

---

# 7. Правило "Что происходит внутри?"

Для каждой важной темы необходимо объяснять внутреннюю модель работы языка.

Например:

* создание Execution Context;
* работа стека вызовов;
* размещение объектов в Heap;
* поиск переменных через Scope Chain;
* создание замыканий;
* работа Event Loop.

Если механизм нельзя объяснить полностью, необходимо объяснить максимально близкую к реальности модель.

---

# 8. Ментальные модели

Каждая сложная тема должна содержать хотя бы одну ментальную модель.

Пример.

Closure — это функция, которая "несет с собой рюкзак" со своим лексическим окружением.

Execution Context — это рабочее место, которое JavaScript создает перед выполнением функции.

Heap — это склад объектов.

Stack — это стопка рабочих задач.

Ментальная модель должна помогать понимать поведение языка, а не заменять точное объяснение.

---

# 9. Код

Все примеры должны быть:

* минимальными;
* понятными;
* рабочими;
* аккуратно оформленными.

Запрещается использовать бессмысленные имена переменных.

Плохо:

```javascript
const a = 10;
const b = 20;
```

Хорошо:

```javascript
const userAge = 30;
const orderTotal = 1200;
```

Исключение — математические примеры и алгоритмы.

---

# 10. Размер примеров

Один пример должен объяснять одну идею.

Если пример начинает объяснять несколько новых механизмов одновременно, его необходимо разделить.

---

# 11. Демонстрация ошибок

Ошибки являются обязательной частью обучения.

Каждая ошибка должна состоять из четырех частей:

1. Неправильный код.
2. Что произошло.
3. Почему это произошло.
4. Исправленный вариант.

---

# 12. Связь с предыдущими главами

Каждая глава должна явно указывать, какие знания из предыдущих глав используются.

Это помогает читателю строить целостную картину языка.

---

# 13. Связь с будущими главами

В конце главы необходимо кратко показать, какая тема будет изучаться следующей и почему она логически продолжает текущую.

---

# 14. Связь с Automation QA

Если тема может использоваться в реальной автоматизации, необходимо показать это.

Предпочтительные примеры:

* Playwright;
* REST API;
* gRPC;
* PostgreSQL;
* сравнение ответов API и БД;
* helper-функции;
* assertions;
* fixtures;
* конфигурация окружения.

---

# 15. Диаграммы

Там, где текст становится менее понятным, используются ASCII-диаграммы.

Например:

```text
Global Scope
│
├── Function Scope
│   ├── Block Scope
│   └── Block Scope
│
└── Function Scope
```

Или:

```text
Stack
│
├── main()
├── login()
└── validate()
```

Диаграммы должны помогать пониманию, а не украшать текст.

---

# 16. Практика

Каждая глава должна содержать обязательные блоки практики.

* Проверка понимания.
* Анализ кода.
* Написание кода.
* Поиск ошибок.
* QA-задачи.
* Мини-проект.

Практика хранится отдельно от текста главы.

---

# 17. Решения

Решения никогда не размещаются внутри файла с практикой.

Каждое решение должно содержать:

* код;
* объяснение;
* разбор ошибок;
* возможные улучшения.

---

# 18. Запрещено

Запрещается использовать:

* TODO;
* пустые разделы;
* заглушки;
* ссылки вида "объясним позже" без указания конкретной главы;
* необъясненный код;
* большие примеры без предварительного разбора;
* бессмысленные задачи.

---

# 19. Definition of Done

Глава считается завершенной только если:

* объяснена теория;
* объяснен внутренний механизм;
* приведены примеры;
* разобраны ошибки;
* показано применение в Automation QA;
* подготовлена практика;
* подготовлены решения;
* обновлено оглавление;
* отсутствуют пустые разделы и незавершенные мысли.

---

# 20. Главное правило

Любой материал должен помогать читателю самостоятельно понимать поведение JavaScript и TypeScript, а не запоминать готовые шаблоны.
