> Версия: 1.0

---

# Назначение документа

Этот документ хранит все важные архитектурные решения проекта.

Если в ходе разработки принимается решение, которое влияет на структуру курса, последовательность тем или стиль обучения, оно фиксируется здесь.

Документ является журналом решений (Architecture Decision Log).

---

# Правила оформления

Каждое решение оформляется по следующему шаблону.

```markdown
## ADR-0001

Дата:

Статус:

Контекст

Проблема

Решение

Причины

Последствия
```

Статусы:

* Proposed
* Accepted
* Deprecated
* Superseded

# ADR-0001

Дата:

2026-06-25

Статус:

Accepted

## Контекст

Необходимо определить последовательность разработки проекта.

## Проблема

Начинать писать главы без общей архитектуры рискованно.

Позже может оказаться, что темы расположены неправильно или отсутствуют важные разделы.

## Решение

Сначала полностью проектируется архитектура проекта.

Последовательность разработки:

1. PROJECT.md
2. STYLE_GUIDE.md
3. ROADMAP.md
4. AGENTS.md
5. README.md
6. SUMMARY.md
7. Только после этого начинается написание книги.

## Причины

Архитектура должна быть стабильной.

Главы не должны требовать последующей перестройки.

## Последствия

После начала написания книги изменение ROADMAP допускается только в исключительных случаях.

# ADR-0002

Дата:

2026-06-25

Статус:

Accepted

## Контекст

Необходимо определить основной принцип обучения.

## Проблема

Большинство курсов концентрируются на синтаксисе языка.

Это приводит к поверхностному пониманию.

## Решение

Основной принцип курса:

Сначала механизм.

Потом синтаксис.

## Причины

Понимание внутренних механизмов позволяет самостоятельно выводить поведение языка без запоминания большого количества правил.

## Последствия

Во всех главах сначала объясняется устройство языка, затем показывается синтаксис.

# ADR-0003

Дата:

2026-06-25

Статус:

Accepted

## Контекст

Нужно определить роль TypeScript в курсе.

## Проблема

Многие разработчики воспринимают TypeScript как отдельный язык.

## Решение

TypeScript изучается только после построения прочного фундамента JavaScript.

## Причины

Во время выполнения работает JavaScript.

TypeScript добавляет только статическую проверку.

## Последствия

Все разделы TypeScript будут ссылаться на ранее изученные механизмы JavaScript.

# ADR-0004

Дата:

2026-06-25

Статус:

Accepted

## Контекст

Необходимо определить роль Automation QA.

## Проблема

Практика часто отделяется от изучения языка.

## Решение

Каждая глава должна содержать связь с реальной автоматизацией тестирования.

## Причины

Читатель курса является Automation QA инженером.

## Последствия

Во всех главах по возможности используются примеры из:

* Playwright;
* REST API;
* gRPC;
* PostgreSQL;
* проверки данных;
* архитектуры тестового фреймворка.

# ADR-0005

Дата:

2026-06-25

Статус:

Accepted

## Контекст

Необходимо определить стратегию развития проекта.

## Проблема

По мере роста курса возникает риск потери единого стиля.

## Решение

Архитектурные документы считаются основой проекта и изменяются только при наличии серьезных причин.

## Причины

Стабильная архитектура обеспечивает единый стиль всех последующих глав.

## Последствия

Новые главы не должны менять ранее принятые архитектурные решения.

---

# Правило обновления документа

Каждое новое архитектурное решение должно быть добавлено в этот документ.

Существующие решения не переписываются.

Если решение устарело, ему присваивается статус `Deprecated` или `Superseded`, а новое решение оформляется отдельной записью.

Таким образом сохраняется полная история развития проекта.
