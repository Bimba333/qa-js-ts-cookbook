# 1. Назначение проекта

Данный репозиторий представляет собой полноценную образовательную программу по JavaScript, TypeScript и Automation QA.

Это не набор заметок.

Это не конспект.

Это не краткое руководство.

Это инженерный учебник, который объединяет:

* фундаментальную теорию;
* практические задания;
* реальные задачи из Automation QA;
* проекты;
* примеры кода;
* решения;
* архитектурные рекомендации.

Основная цель проекта — сформировать глубокое понимание языка и научить применять его в промышленной автоматизации тестирования.

# 2. Миссия проекта

Создать лучший русскоязычный открытый курс по JavaScript и TypeScript для Automation QA.

Под "лучший" понимается не объем материала, а его качество.

После прохождения курса читатель должен понимать язык настолько хорошо, чтобы самостоятельно:

* проектировать архитектуру тестового фреймворка;
* понимать ошибки, а не искать готовые решения.

Проект строится на следующих принципах.

---

## Принцип 2

Каждая новая тема строится только на уже изученных знаниях.

---

## Принцип 3

Никакой магии.

Если используется новый механизм, он должен быть объяснен.

---

## Принцип 4

Все примеры должны запускаться.

Если пример содержит ошибку, она должна быть намеренной и подробно разобранной.

Исключение: часть файлов в `examples/` может быть намеренно невалидным JavaScript-кодом.

Такие файлы используются как учебный материал для демонстрации syntax errors, invalid code и debugging-сценариев.

Если файл содержит marker:

```javascript
// INTENTIONAL SYNTAX ERROR
```

или:

```javascript
// EDUCATIONAL INVALID EXAMPLE
```

то он:

* не должен исправляться автоматически;
* не должен удаляться;
* не должен проверяться через `node --check`;
* должен рассматриваться как documentation material.

Project validation must exclude intentionally invalid examples.

`node --check` применяется только к:

* `examples/**/valid/**`;
* файлам без intentional-error marker.

Файлы, отмеченные как intentional invalid examples, являются частью teaching system.

# 14. Обязательные правила ROADMAP и SCOPE compliance для Codex

Этот раздел обязателен для всех будущих задач по генерации, изменению и редактуре учебного контента.

Репозиторий использует:

* `.meta/ROADMAP.md` для архитектуры курса;
* `.meta/TYPESCRIPT_SCOPE.md` и другие scope-документы для границ разделов;
* `.meta/CHANGE_POLICY.md` для контролируемых изменений после freeze.

## 14.1 ROADMAP.md — источник истины

`.meta/ROADMAP.md` является единственным источником истины для структуры образовательного контента.

Перед созданием или изменением любого учебного материала Codex обязан прочитать `.meta/ROADMAP.md` и проверить, что задача совпадает с roadmap по следующим пунктам:

* номер главы;
* название главы;
* модуль;
* учебная цель;
* prerequisites;
* разрешенный scope.

## 14.2 Обязательное условие остановки

Если запрос пользователя конфликтует с `.meta/ROADMAP.md`, Codex обязан остановиться.

В этом случае запрещено:

* создавать файлы;
* изменять файлы;
* переименовывать главы;
* переносить темы;
* добавлять отсутствующие главы;
* менять порядок глав;
* менять порядок модулей.

Вместо выполнения задачи Codex должен сообщить:

1. Ожидаемую структуру по roadmap.
2. Запрошенную структуру задачи.
3. Точное расхождение.
4. Возможные варианты решения.

После этого Codex должен дождаться подтверждения перед продолжением.

## 14.3 Защита scope

Перед созданием контента Codex обязан проверить задачу по scope-документу текущего раздела.

Для TypeScript используется:

```text
.meta/TYPESCRIPT_SCOPE.md
```

Для других разделов используются соответствующие scope-документы, если они существуют.

Codex не должен вводить:

* исключенные технологии;
* темы будущих разделов;
* framework-specific материал, если он не относится к текущему разделу;
* дублирование материала из предыдущих разделов.

Если найден scope conflict, Codex обязан остановиться и сообщить о конфликте.

## 14.4 Обязательный workflow создания главы

Перед написанием главы Codex обязан:

1. Прочитать `.meta/ROADMAP.md`.
2. Прочитать scope-документ текущего раздела.
3. Подтвердить, что глава существует в roadmap.
4. Подтвердить цель главы.
5. Подтвердить prerequisites.

Только после этой проверки разрешено создавать:

* `docs`;
* `examples`;
* `practice`;
* `solutions`.

## 14.5 Запрет самостоятельных архитектурных изменений

Codex не имеет права самостоятельно:

* вставлять главы;
* удалять главы;
* объединять главы;
* разделять главы;
* переименовывать главы;
* менять порядок глав;
* менять порядок модулей.

Даже если обнаружена более удачная структура, Codex должен только сообщить об архитектурной проблеме и дождаться одобрения.

## 14.6 Консистентность будущих глав

Каждая новая глава должна сохранять:

* нумерацию roadmap;
* границы модулей;
* терминологию;
* стиль обучения;
* assumptions о знаниях из предыдущих глав.

Глава не должна обучать концепциям, которые назначены будущим главам.

## 14.7 Финальная проверка перед завершением задачи

Перед завершением любой задачи по созданию главы Codex обязан проверить:

* созданная глава существует в roadmap;
* `SUMMARY.md` может быть обновлен корректно;
* prerequisites удовлетворены;
* roadmap drift не появился;
* scope expansion не появился.

# 15. Educational SUT финального проекта

Репозиторий предоставляет собственный учебный System Under Test для default
пути финального проекта.

Governance boundary:

* domain: **Educational Work Items**;
* application infrastructure размещается в отдельной границе `sut/`;
* `examples/04-final-project/` остаётся Automation QA Framework читателя;
* SUT и test framework используют один root package и один lockfile без
  обязательного workspace;
* SUT предоставляет реальные UI, REST, unary gRPC и PostgreSQL process
  boundaries;
* test framework обращается только к public transports и restricted database
  verification boundary;
* tests не импортируют внутренние модули SUT;
* локальная воспроизводимость строится вокруг Docker Compose;
* future CI integration обязана сохранять те же публичные contracts;
* educational SUT не предназначен и не одобрен для production use.

Ненумерованный milestone **SUT-0 — Educational SUT Infrastructure Milestone**
является обязательной предпосылкой между главами 252 и 253. Его реализация
выполняется по фазам и decision gates, зафиксированным в
`.meta/ROADMAP.md` и `.meta/FINAL_PROJECT_SUT_SPEC.md`.

SUT-0 предоставляет инфраструктуру, но не забирает teaching ownership:

* глава 253 владеет UI Layer;
* глава 254 владеет REST API Layer;
* глава 255 владеет gRPC Layer;
* глава 256 владеет Database Layer;
* глава 257 владеет cross-layer scenarios;
* глава 258 владеет diagnostics, parallel execution и CI;
* глава 259 владеет final audit и scoring.

Другой SUT может использоваться только через отдельно одобренный compatibility
path. Default и единственный гарантированно поддерживаемый путь курса использует
repository-owned Educational Work Items SUT.
