# Educational Work Items SUT

Учебная система под тестирование: PostgreSQL, REST API, server-rendered веб-UI
и unary gRPC в одном стенде, который поднимается одной командой.

SUT существует только для того, чтобы против него писали автотесты. Он не
является production-приложением и не предназначен для развёртывания вне
локальной машины.

## Предупреждение

Учётные данные лежат в репозитории намеренно. Они защищают одноразовые
локальные данные, не являются production secrets и не должны
переиспользоваться. Внешние PostgreSQL hosts, внешний bind и production mode
не поддерживаются: конфигурация отказывается стартовать с такими значениями.

## Быстрый старт

```bash
npm run sut:up      # собрать образ, поднять базу, применить миграции и seed, запустить SUT
npm run sut:smoke   # сквозная проверка всех слоёв
npm run sut:logs    # логи приложения
npm run sut:down    # остановить стенд (данные сохраняются)
```

Полная очистка вместе с томом базы:

```bash
npm run sut:down:clean
```

## Что поднимается

| Компонент | Адрес | Назначение |
| --- | --- | --- |
| Веб-UI | http://127.0.0.1:4310 | Браузерные сценарии |
| REST API | http://127.0.0.1:4310/api/v1 | API-сценарии |
| gRPC | 127.0.0.1:4311 | Unary-вызовы |
| Health | http://127.0.0.1:4310/health/ready | Готовность стенда |
| PostgreSQL | 127.0.0.1:55432 | Проверка состояния из тестов |

Порядок запуска задан условиями Compose: база становится healthy → миграции
завершаются успешно → seed завершается успешно → стартует приложение.
Состояние `running` само по себе готовностью не считается, а приложение
никогда не применяет миграции самостоятельно.

## Данные

Seed детерминирован: одинаковые идентификаторы, timestamps и распределение
полей при каждом запуске. В базе 248 задач с распределением по всем
комбинациям статуса и приоритета, чего достаточно для фильтров, пагинации и
SQL-задач.

Отдельно заданы строки с заранее известными свойствами:

- заголовок минимальной длины в один символ;
- заголовок максимальной длины в 120 символов;
- Unicode: эмодзи, диакритика, лигатура;
- заголовок с HTML-разметкой и кавычками (проверка экранирования в UI);
- терминальные статусы `DONE` и `CANCELLED` для недопустимых переходов;
- задача другого владельца;
- описание максимальной длины в 2000 символов.

Seed-записи защищены от изменения и удаления: их бережёт и проверка в
приложении, и триггер базы. Поэтому набор данных остаётся стабильным между
запусками тестов.

## Модель и правила

Допустимые переходы статуса:

- `NEW` → `IN_PROGRESS` или `CANCELLED`;
- `IN_PROGRESS` → `DONE` или `CANCELLED`;
- `DONE` и `CANCELLED` терминальные.

Обновление требует `expectedVersion`. Успешное изменение повышает версию
ровно на единицу, а устаревшая версия даёт конфликт и не меняет строку.
Владелец и автор выводятся из аутентифицированного пользователя: назначить
запись другому через публичный API нельзя.

## Изоляция параллельных запусков

Выдача токена или вход в UI создаёт **test run** на стороне сервера. Всё, что
создаётся в этом запуске, помечается его идентификатором. Клиент не может
выбрать чужой run: параметра для этого нет.

Очистка удаляет строго свой запуск:

```
DELETE /api/v1/test-runs/current/work-items
```

Seed при этом не затрагивается, а факт очистки попадает в `audit_events` —
таблицу, которую тест может прочитать через read-only роль.

## REST

| Endpoint | Назначение |
| --- | --- |
| `POST /api/v1/auth/token` | Bearer token и новый test run |
| `GET /api/v1/me` | Текущий принципал |
| `POST /api/v1/work-items` | Создание |
| `GET /api/v1/work-items` | Список: `status`, `priority`, `ownerId`, `limit`, `offset` |
| `GET /api/v1/work-items/:id` | Чтение |
| `PATCH /api/v1/work-items/:id` | Обновление с `expectedVersion` |
| `DELETE /api/v1/work-items/:id` | Удаление |
| `DELETE /api/v1/test-runs/current/work-items` | Очистка текущего запуска |

Ошибка всегда имеет одну форму:

```json
{
  "code": "VERSION_CONFLICT",
  "message": "Ожидалась версия 1, актуальная версия 2",
  "field": "expectedVersion",
  "correlationId": "..."
}
```

`correlationId` связывает ответ, запись audit trail и строку лога. Тело
ошибки не содержит stack trace, SQL или credential material.

Заголовок `x-creator-test-id` помечает записи идентификатором конкретного
теста. Если его не передать, используется значение `manual` — чтобы изучение
API через `curl` не упиралось в обязательный заголовок.

Пример:

```bash
TOKEN=$(curl -s -X POST http://127.0.0.1:4310/api/v1/auth/token \
  -H 'content-type: application/json' \
  -d '{"login":"educational_tester","password":"educational-tester-password"}' \
  | node -pe 'JSON.parse(require("fs").readFileSync(0)).accessToken')

curl -s "http://127.0.0.1:4310/api/v1/work-items?status=NEW&limit=3" \
  -H "authorization: Bearer $TOKEN"
```

## UI

| Маршрут | Страница |
| --- | --- |
| `/login`, `/logout` | Вход и выход |
| `/work-items` | Список с фильтрами, пагинацией и пустым состоянием |
| `/work-items/new` | Создание |
| `/work-items/:id` | Карточка |
| `/work-items/:id/edit` | Изменение с ожидаемой версией |
| `/work-items/:id/delete` | Подтверждение удаления |
| `/playground` | Учебная площадка: фрейм, вкладка, диалоги, файлы |
| `/playground/frame` | Документ внутри фрейма |
| `/playground/popup` | Страница, открываемая в новой вкладке |
| `/playground/upload` | Приём файла: показывает имя и размер |
| `/playground/download` | Отдаёт файл с `Content-Disposition` |

HTML рендерится сервером, SPA-runtime нет. Исключение — `/playground`:
там есть небольшой встроенный скрипт, потому что диалоги браузера иначе не
вызвать. Площадка ничего не хранит: загруженный файл не сохраняется, в ответ
уходят только его имя и размер. Все изменяющие формы защищены
CSRF-токеном и проверкой `Origin`, cookie сессии имеет `HttpOnly` и
`SameSite=Lax`, а успешный вход ротирует идентификатор сессии.

Селекторы выбираются в порядке: доступная роль и имя → label → устойчивый
видимый текст → `data-testid`. Селекторы по вёрстке и выбор по индексу
использовать не нужно: у каждого значимого элемента есть смысловой якорь.

## gRPC

Пакет `qa.educational.workitems.v1`, контракт в
`sut/contracts/proto/work_items.proto`.

- `WorkItemService.GetWorkItem`
- `WorkItemService.SearchWorkItems`
- `WorkItemService.TransitionWorkItem`
- `grpc.health.v1.Health.Check`

Аутентификация передаётся в metadata `authorization`, рядом идут
`correlation-id` и `creator-test-id`. Идентификатор запуска сервер выводит из
токена и не принимает от клиента. Клиент обязан задавать deadline.

| Ситуация | Status |
| --- | --- |
| Некорректное поле | `INVALID_ARGUMENT` |
| Нет или недействительная аутентификация | `UNAUTHENTICATED` |
| Роль не разрешает действие | `PERMISSION_DENIED` |
| Запись отсутствует | `NOT_FOUND` |
| Устаревшая версия или недопустимый переход | `FAILED_PRECONDITION` |
| Истёк deadline | `DEADLINE_EXCEEDED` |

`INTERNAL` не используется для известных ошибок валидации, доступа, домена и
конкурентности: он остаётся признаком настоящего сбоя.

## Роли базы данных

| Роль | Права |
| --- | --- |
| `sut_migrator` | Владелец схемы, применяет миграции и seed |
| `sut_app` | Права на уровне колонок, ровно под нужды транспортов |
| `sut_reader` | Только чтение: этой ролью тесты проверяют состояние |

Подключение для проверки состояния из тестов:

```
host=127.0.0.1 port=55432 dbname=educational_work_items
user=sut_reader password=educational_reader_only
```

## Обслуживание

```bash
npm run sut:migrate     # применить миграции (идемпотентно)
npm run sut:seed        # применить seed (идемпотентно)
npm run sut:reset       # удалить данные запусков и восстановить seed
npm run sut:health      # проверка готовности из командной строки
npm run sut:test:db     # интеграционные тесты против реальной базы
npm run sut:typecheck   # проверка типов
```

Миграции иммутабельны: каждая записывается в ledger вместе с SHA-256 от
содержимого, а изменение уже применённого файла останавливает запуск с
ошибкой расхождения. Новая миграция добавляется следующим номером без
пропусков.

## Границы

Test framework обращается только к публичным границам: браузер, REST, gRPC и
read-only подключение к базе. Импортировать внутренние модули SUT из тестов
нельзя — это скрыло бы поломку контракта за прямым доступом к реализации.

В scope не входят production deployment, микросервисы, платежи, файловые
вложения, streaming gRPC и SPA-фреймворки.
