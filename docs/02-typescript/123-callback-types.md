# Типы обратных вызовов

## Связь с предыдущей главой

Мы научились описывать параметры самой функции.

Теперь функция станет аргументом другой функции.

## Главный вопрос

> Как типизировать функцию, которую передают в другую функцию?

Короткий ответ: тип обратного вызова описывает сигнатуру функции, которую вызывающий код передаёт как аргумент.

## Мотивация

В QA-коде часто есть обработчики результатов, фильтры, логгеры и функции повторной попытки.

Если callback принимает неправильные данные или возвращает не тот результат, ошибка может проявиться далеко от места передачи функции.

TypeScript делает договор callback явным.

## Теория

### Обратный вызов — договор на будущий вызов

Тип колбэка описывает функцию, которую вызовут позже:

```typescript
type ResultHandler = (message: string) => void;

function handleResult(message: string, handler: ResultHandler): void {
  handler(message);
}
```

Читается с позиции вызывающего: «когда я вызову эту функцию, я передам строку и результат использовать не буду».

### `void` в результате означает «результат не нужен»

Это не запрет что-то возвращать. Функция вправе вернуть значение — оно будет проигнорировано:

```typescript
const items: number[] = [];

[1, 2, 3].forEach((value) => items.push(value));   // push возвращает число
```

Если бы `void` означал «не возвращай ничего», такой код пришлось бы писать в фигурных скобках. Подробно правило разобрано в главе 105.

### Меньше параметров — тоже подходит

Колбэк не обязан принимать всё, что ему передают:

```typescript
[10, 20].map((value) => value * 2);            // индекс не нужен
[10, 20].map((value, index) => value + index); // а здесь нужен
```

Лишние аргументы игнорируются — это поведение JavaScript, и система типов ему следует. Благодаря этому колбэки остаются короткими.

### Контекстная типизация избавляет от аннотаций

Параметры колбэка обычно не аннотируют: их тип приходит из места использования.

```typescript
const codes = [200, 404];
codes.filter((code) => code >= 400);   // code: number, выведено из filter
```

Ручная аннотация здесь не только избыточна, но и вредна: она может разойтись с контекстом и заглушить полезную ошибку.

### Метод или свойство-функция

Когда колбэк объявляется полем объекта, способ записи влияет на строгость проверки:

```typescript
type A = { onResult(value: string): void };      // метод — мягче
type B = { onResult: (value: string) => void };  // свойство — строже
```

Для колбэков предпочтительнее вторая запись: при `strictFunctionTypes` она поймает несовместимые параметры. Разбор — в главе 112.

### Асинхронный колбэк

Если колбэк возвращает `Promise`, это нужно отразить в типе:

```typescript
type AsyncHandler = (message: string) => Promise<void>;
```

Иначе вызывающий код не дождётся завершения. Особенно важно в тестовых хелперах: колбэк типа `() => void`, внутри которого стоит `await`, приведёт к тому, что проверка завершится раньше самой операции.

### Слишком широкий колбэк бесполезен

`(value: any) => void` формально принимает что угодно и не даёт ни подсказок, ни проверок. Если тип аргумента действительно неизвестен — `unknown` и сужение внутри.

Договор колбэка проверяется в точке передачи:

```mermaid

    A["функция принимает<br/>(item: T) => void"] --> B["колбэк может брать<br/>меньше параметров"]
    B --> C["контекстная типизация:<br/>аннотации не нужны"]
    A --> D{"результат объявлен void?"}
    D -- "да" --> E["возвращённое значение<br/>игнорируется"]

```

## Внутренний механизм

TypeScript проверяет обратный вызов как обычное вызываемое значение.

Он проверяет его параметры и то, как вызывающий код использует результат.

Во время выполнения обратный вызов остаётся обычной функцией JavaScript и выполняется только тогда, когда его вызывает код программы.

### Компилятор выводит типы параметров обратного вызова

```ts
items.filter(item => item.status === "NEW");
//            ^ item выведен как WorkItem, аннотация не нужна
```

Контекстная типизация работает от ожидаемого типа к функции: сигнатура `filter`
известна, поэтому тип параметра выводится. Аннотировать его вручную не нужно и
вредно — при изменении типа коллекции аннотация устареет молча.

### Тип результата обратного вызова решает многое

```ts
items.filter(item => item.tags);          // ошибка при strict: не boolean
items.map(async item => create(item));    // тип Promise<…>[], НЕ разрешается
```

Вторая строка — самая частая ошибка в тестах, которая не падает: компилятор
честно выводит массив промисов, и если результат присвоен переменной без
аннотации, никто этого не заметит до сравнения значений.

Аннотация ожидаемого типа результата ловит это сразу:

```ts
const ids: string[] = await Promise.all(items.map(async i => (await create(i)).id));
```

### `void` в типе результата разрешает возврат

```ts
type Each = (item: WorkItem) => void;

const e: Each = item => list.push(item);   // разрешено, хотя push даёт number
```

`void` означает «результат не используется», а не «функция обязана ничего не
вернуть». Именно поэтому короткая стрелочная форма работает с `forEach` и
подобными.

## Главная ментальная модель

Тип обратного вызова — это договор для функции, которую вызывают позже.

Он говорит: "когда я вызову эту функцию, я передам такие данные и буду ожидать такой результат".

## Automation QA

Тип обратного вызова полезен для обработчиков журнала:

```typescript
type LogHandler = (message: string) => void;
```

Так вспомогательная функция знает, какие данные она передаст обработчику.

### `void` в результате обратного вызова

Тип `void` здесь означает «результат не используется», а не «функция обязана
ничего не возвращать». Поэтому обработчик может возвращать значение — оно
просто будет проигнорировано.

```typescript
type LogHandler = (message: string) => void;

const collected: string[] = [];

// push возвращает число, и это допустимо.
const collect: LogHandler = message => collected.push(message);
```

Без этого правила самая короткая запись сборщика сообщений не компилировалась
бы, и пришлось бы оборачивать её в фигурные скобки ради выброшенного значения.

### Асинхронный обработчик — отдельный контракт

Если обработчик может быть асинхронным, это должно быть в типе. Иначе
вызывающий код не станет дожидаться его завершения, и запись в журнал уйдёт
после того, как тест закончится.

```typescript
type AsyncLogHandler = (message: string) => Promise<void>;
```

Это прямое следствие главы 167: незавершённая операция в тесте не падает, она
просто теряется.

## Распространённые ошибки

### Ошибка 1. Думать, что обратный вызов выполняется на этапе проверки

TypeScript проверяет сигнатуру, но не выполняет обратного вызова.

### Ошибка 2. Путать `void` и запрет на возврат значения

Если тип обратного вызова возвращает `void`, вызывающий код просто не использует результат.

### Ошибка 3. Делать обратный вызов слишком широким

Если он принимает `any`, TypeScript перестаёт помогать с параметрами.

## Распространённые мифы

**Миф: колбэк с типом `void` не может возвращать значение.**
Может: результат будет проигнорирован.

**Миф: колбэк обязан принимать все передаваемые аргументы.**
Функция с меньшим числом параметров совместима.

**Миф: параметры колбэка нужно аннотировать.**
Их тип обычно приходит из контекста; ручная аннотация может с ним разойтись.

**Миф: асинхронный колбэк можно описать как `() => void`.**
Тогда вызывающий код не дождётся его завершения. Нужен `Promise<void>`.

## Частые вопросы

**Почему `forEach(x => arr.push(x))` компилируется?**
`void` в результате означает «значение не используется», а не «его не должно быть».

**Как описать колбэк, результат которого важен?**
Указать конкретный тип результата вместо `void` — тогда компилятор проверит, что функция его возвращает.

**Что делать, если тип аргумента колбэка заранее неизвестен?**
Использовать `unknown` и сузить внутри. `any` отключает проверку целиком.

**Почему колбэк в тесте завершается раньше времени?**
Частая причина — асинхронный колбэк, объявленный как `() => void`: вызывающий код не ждёт `Promise`.

## Проверьте себя

1. Что означает `void` в позиции результата колбэка?
2. Почему колбэк с одним параметром подходит там, где передают три?
3. Откуда берётся тип параметра колбэка, если он не аннотирован?
4. Чем запись свойства-функции лучше метода для колбэка?
5. Чем опасен асинхронный колбэк с типом результата `void`?

### Ответы

1. Что возвращённое значение не будет использовано. Это не запрет возвращать что-либо — реализация вправе вернуть значение.
2. Лишние аргументы игнорируются, как и в JavaScript. Функция, которой нужен только первый параметр, полностью пригодна.
3. Из контекста — сигнатуры принимающей функции. Это контекстная типизация.
4. Оно проверяется строго при включённом `strictFunctionTypes`, тогда как метод допускает двунаправленную проверку параметров.
5. Возвращённый промис никто не ожидает: ошибки внутри теряются, а порядок выполнения перестаёт быть предсказуемым. Поэтому асинхронные шаги передают туда, где результат действительно ожидается.

## Краткие итоги

Главное:

* тип обратного вызова описывает функцию-аргумент;
* его параметры должны соответствовать месту вызова;
* обратный вызов-предикат обычно возвращает булево значение;
* `void` означает, что результат игнорируется;
* обратный вызов выполняется только во время работы программы.
