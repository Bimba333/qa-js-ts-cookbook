## Связь с предыдущей главой

Теперь нужно понять обратную сторону этой модели.

Если объект остается reachable, Garbage Collector не может считать его мусором.

## Главный вопрос

> Если в JavaScript есть Garbage Collector, почему memory leaks все еще происходят?

Короткий ответ: memory leak возникает, когда программа продолжает удерживать ссылки на объекты, которые логически уже не нужны.

## Мотивация

Представим тестовый раннер, который сохраняет логи каждого теста:

```javascript
const logBuffer = [];

function saveLog(testName, messages) {
  logBuffer.push({
    testName,
    messages,
  });
}
```

Если буфер никогда не очищается, старые логи остаются reachable.

```mermaid
flowchart TD
    N1["logBuffer"]
    N2["report #1"]
    N3["report #2"]
    N4["report #3"]
    N5["report #4"]
    N1 --> N2
    N1 --> N3
    N1 --> N4
    N1 --> N5
```

Для Garbage Collector это не мусор.

```mermaid
flowchart TD
    N1["ссылка существует"]
    N2["объект reachable"]
    N3["память удерживается"]
    N1 --> N2
    N2 --> N3
```

Логически старые данные могут быть уже не нужны. Но технически программа все еще держит ссылку.

## Теория

Memory management в JavaScript — это не ручное освобождение памяти.

Это аккуратное управление временем жизни ссылок.

```mermaid
flowchart TD
    N1["ссылка существует"]
    N2["объект reachable"]
    N3["память удерживается"]
    N4["ссылка удалена"]
    N5["объект может быть собран"]
    N1 --> N2
    N2 --> N3
    N3 --> N4
    N4 --> N5
```

Memory leak — это ситуация, когда объект больше не нужен бизнес-логике, но остается reachable.

Типичные источники:

* long-lived references;
* случайные глобальные ссылки;
* closures, удерживающие большие объекты;
* event listeners;
* timers;
* caches.

Все эти механизмы нормальны сами по себе. Проблема появляется только тогда, когда ссылка живет дольше, чем должен жить объект.

### Пять источников утечек и как они выглядят

Memory leak — это ситуация, когда объект больше не нужен бизнес-логике, но остаётся reachable. Типичные источники стоит разобрать по отдельности, потому что чинятся они по-разному:

| Источник | Как возникает | Чем закрывается |
| --- | --- | --- |
| долгоживущий массив | результаты складывают «на всякий случай» | ограничить объём или не накапливать |
| случайная глобальная ссылка | значение положили в общий объект | локальная переменная или явная очистка |
| замыкание | функция удерживает большой объект | замыкать только нужные поля |
| обработчик события | подписались и не отписались | снимать подписку при завершении |
| таймер | `setInterval` без отмены | `clearInterval` в завершении |

Последние два — самые частые в тестовом коде: подписка и таймер живут дольше сценария, если их никто не остановил.

### Замыкание удерживает окружение целиком

Тонкость, которая делает утечки через замыкания незаметными. Функция сохраняет доступ к окружению, а не к отдельным переменным — как показано в главе 65.

```javascript
function createHandler(hugeResponse) {
  const id = hugeResponse.id;
  return () => id;        // но окружение всё ещё содержит hugeResponse
}
```

Пока жив обработчик, жив и весь контекст его создания. Если из большого объекта нужен только идентификатор, безопаснее не передавать объект в фабрику вовсе, а передать уже извлечённое значение.

### Накопление в тестовом прогоне

Для автотестов характерен свой сценарий: набор из сотен тестов складывает данные в общий массив — логи, ответы, скриншоты в памяти. Каждый отдельный тест ведёт себя корректно, а прогон целиком постепенно растёт.

Признаки, по которым это распознают:

- потребление памяти растёт монотонно и не возвращается между тестами;
- падения начинаются ближе к концу прогона, а не в начале;
- одиночный запуск теста проходит, а в наборе — нет.

Лечение то же, что и для данных на стенде: у накопленного должен быть владелец и момент освобождения.

### Освобождать — значит убирать ссылку

В JavaScript нет ручного освобождения памяти. Всё управление сводится к одному действию: **убрать последнюю ссылку**, когда объект больше не нужен.

```javascript
clearInterval(timer);          // таймер перестаёт удерживать колбэк
element.removeEventListener('click', handler);
cache.clear();                 // коллекция перестаёт удерживать значения
results.length = 0;
```

Каждая строка не «освобождает память» напрямую — она делает объекты недостижимыми, а дальше работает механизм из главы 87.

### Чего не стоит делать

Две крайности одинаково вредны.

Преждевременная борьба за память усложняет код без измеримой пользы: обнуление всех переменных в конце функции ничего не даёт, потому что её контекст и так исчезает.

Полное игнорирование темы приводит к прогонам, падающим по памяти через час работы. Разумная середина — знать пять источников из таблицы и закрывать их там, где ресурс действительно долгоживущий.

### Long-lived references

Долгоживущая коллекция может удерживать объекты слишком долго:

```mermaid
flowchart TD
    N1["глобальный cache"]
    N2["test data #1"]
    N3["test data #2"]
    N4["test data #3"]
    N1 --> N2
    N1 --> N3
    N1 --> N4
```

Пока cache существует и хранит ссылки, данные reachable.

### Accidental globals

Если значение случайно попадает в глобальную область, оно может жить дольше ожидаемого.

### Closures

Closure может удерживать объект через доступ к внешней переменной:

Это не ошибка само по себе. Ошибка начинается, когда такой доступ больше не нужен, но продолжает существовать.

### Event listeners

Подписка может удерживать обработчик, а обработчик — данные.

### Timers

Таймер может удерживать функцию, а функция — объекты из окружающего кода.

Таймер не является memory leak сам по себе. Риск появляется, когда таймер или его callback живут дольше нужного сценария.

### Caches

Cache полезен, пока есть правило очистки.

Cache не является плохой практикой. Плохой становится cache без понятного правила удаления старых данных.

## Главная ментальная модель

Главная модель главы показывает, где именно появляется memory leak: не в движке и не в сборщике, а в коде, который продолжает держать ссылку на ненужный объект.

Garbage Collector не исправляет неправильное время жизни ссылок. Он только очищает то, что стало недостижимым.

## Пример Automation QA

Кэш тестовых данных может быть полезен:

```javascript
const testDataCache = new Map();

function saveTestData(testId, data) {
  testDataCache.set(testId, data);
}
```

Но если кэш никогда не очищается, данные всех старых запусков остаются reachable.

Практичнее явно определять время жизни:

```javascript
function clearTestData(testId) {
  testDataCache.delete(testId);
}
```

## Распространённые мифы

**Миф: утечка — это когда память не освобождается движком.**
Утечка — это когда объект остаётся достижимым, хотя больше не нужен.

**Миф: замыкание удерживает только использованные переменные.**
Оно сохраняет доступ к окружению целиком.

**Миф: обнуление переменных в конце функции помогает.**
Контекст функции исчезает сам. Пользы нет.

**Миф: утечки — проблема только долгоживущих приложений.**
Прогон из сотен тестов — тоже долгоживущий процесс.

**Миф: память освобождают явной командой.**
Её освобождает сборщик. Разработчик убирает последнюю ссылку.

## Частые вопросы

**Как распознать утечку в тестовом прогоне?**
Память растёт монотонно, падения ближе к концу, одиночный запуск теста проходит.

**Почему замыкание удерживает большой объект?**
Оно хранит доступ ко всему окружению создания, а не к отдельным переменным.

**Что делать с подписками и таймерами?**
Снимать и отменять при завершении сценария — это самый частый источник в тестах.

**Помогает ли `delete` от утечки?**
Только если это была последняя ссылка на объект.

**Стоит ли заранее оптимизировать память?**
Нет. Достаточно закрывать известные источники там, где ресурс долгоживущий.

## Распространённые ошибки

### Ошибка 1. Считать, что Garbage Collector предотвращает любые memory leaks

Garbage Collector освобождает недостижимые объекты. Он не знает, какие reachable-объекты вам логически уже не нужны.

### Ошибка 2. Хранить временные данные в долгоживущих коллекциях

Если массив, Map или объект живет весь процесс, все значения внутри тоже остаются reachable.

### Ошибка 3. Не очищать listeners, timers и caches

Подписки, таймеры и кэши часто становятся причиной удержания старых данных.

Важно: они не являются ошибкой сами по себе. Ошибка — оставить их жить после завершения сценария, которому они принадлежали.

## Краткие итоги

Memory management в JavaScript — это управление ссылками и временем жизни данных.

Главное:

* Garbage Collector работает только с недостижимыми объектами;
* memory leak возникает, когда ненужный объект остается reachable;
* долгоживущие ссылки удерживают память;
* closures, listeners, timers и caches могут продлевать жизнь объектов;
* в Automation QA важно очищать временные логи, отчеты, screenshots и test data;
* хорошая практика — заранее понимать, кто владеет объектом и когда ссылка должна исчезнуть.
