# Debugging

## Связь с предыдущей главой

Предыдущая глава показала инженерный подход к performance:

Debugging строится на похожей дисциплине. Ошибку нельзя надежно исправить догадкой. Сначала виден только symptom. Его нужно воспроизвести, сузить область поиска, найти root cause, исправить и проверить результат.

## Главный вопрос

> Как профессиональные разработчики находят bugs?

Короткий ответ: они не угадывают. Они систематически воспроизводят symptom, проверяют предположения, уменьшают область поиска и находят root cause.

В Automation QA ошибка часто выглядит так:

## Теория

Bug — это расхождение между ожидаемым поведением и фактическим поведением.

Первый шаг — воспроизведение. Если проблему нельзя повторить, ее трудно проверить после исправления.

Второй шаг — изоляция. Нужно понять, где именно возникает расхождение:

* входные данные;
* состояние объекта;
* вызов функции;
* результат API-запроса;
* selector;
* assertion;
* порядок выполнения.

Третий шаг — проверка предположений. Хороший debugging постоянно задает вопросы:

* что я считаю истинным?
* где это можно проверить?
* какие данные реально пришли?
* какая функция была вызвана?
* какой путь выполнения привел к ошибке?

`console.log()` полезен, если он проверяет конкретное предположение.

Плохо:

```javascript
console.log('here');
```

Лучше:

```javascript
console.log('current status:', testResult.status);
```

Breakpoint по смыслу делает то же самое: останавливает выполнение в выбранной точке, чтобы проверить состояние программы.

Stack trace — это стартовая точка расследования.

Он показывает цепочку вызовов, которая привела к ошибке.

Но stack trace не всегда автоматически указывает root cause: причина может быть в данных, состоянии или более раннем вызове.

### Отладка — это проверка гипотез, а не чтение кода

Три шага выше складываются в цикл, знакомый по расследованию падений в тестах: воспроизвести, сузить, проверить предположение. Пока гипотеза не проверена, она остаётся догадкой — даже если код «явно» содержит ошибку.

Практический признак плохой отладки: несколько изменений сразу. Если после них всё заработало, причина осталась неизвестной и вернётся.

### Инструменты по возрастанию точности

| Инструмент | Что даёт | Когда уместен |
| --- | --- | --- |
| `console.log` | значение в конкретной точке | быстрая проверка одного предположения |
| `console.table` | структурированный вывод массива объектов | сравнение набора данных |
| отладчик с точкой останова | состояние всех переменных и стек | непонятно, где именно расходится |
| условная точка останова | останов только при нужном условии | ошибка на одной итерации из тысячи |

`console.log()` полезен, если он проверяет конкретное предположение. Вывод «сюда дошли» почти бесполезен; вывод значения, которое должно быть одним, а оказалось другим, — закрывает вопрос.

### Что читать в трассировке

Стек ошибки из главы 62 — главный источник для изоляции: сверху место возникновения, ниже путь к нему. Полезная привычка — перед чтением кода прочитать трассировку целиком и отметить границу между вашим кодом и чужим.

Ошибка, возникшая в библиотеке, почти всегда означает неверные данные, переданные из вашего кода, — и искать нужно в последнем «своём» кадре.

### Отладка асинхронного кода

Здесь стек короче и обрывается на границе очереди: продолжение выполняется отдельно от того места, где операция была запущена. Поэтому в асинхронных сценариях особенно ценны:

- идентификатор операции в журнале, связывающий начало и завершение;
- вывод состояния до и после `await`, а не только в конце;
- проверка того, что `await` действительно стоит там, где ожидается.

Последний пункт — прямая связь с главой 79: забытый `await` даёт ошибку, которая появляется не там, где возникла.
## Внутренний механизм

Во время выполнения JavaScript проходит по конкретному пути.

Debugging пытается найти первое место, где ожидание расходится с реальностью. Именно там symptom начинает превращаться в объяснимую root cause.

Пример:

```javascript
function getFailedTests(results) {
  return results.filter((result) => result.status === 'failed');
}

const testResults = [
  { id: 'T-1', status: 'passed' },
  { id: 'T-2', status: 'fail' },
];

console.log(getFailedTests(testResults));
```

Код выводит пустой массив, хотя второй тест логически failed. Проблема не в `filter()`. Проблема в данных: статус записан как `'fail'`, а код ожидает `'failed'`.

## Пример Automation QA

Представим падающий Playwright-тест:

```text
expected status: paid
actual status: pending
```

Плохой путь: поменять несколько мест сразу, увидеть зелёный результат и закрыть задачу, не узнав причины.

Инженерный путь:

Если API возвращает `pending`, а UI показывает `pending`, bug может быть не в selector. Если API возвращает `paid`, но UI показывает `pending`, нужно смотреть обновление состояния на странице или ожидание нужного условия. Так область поиска становится меньше.

## Распространённые мифы

**Миф: отладка — это внимательное чтение кода.**
Это проверка гипотез. Непроверенная догадка остаётся догадкой, даже если код выглядит подозрительно.

**Миф: несколько исправлений сразу экономят время.**
После них неизвестно, что именно помогло, и причина возвращается.

**Миф: `console.log('сюда дошли')` помогает.**
Полезен вывод значения, которое проверяет конкретное предположение.

**Миф: ошибка в библиотеке означает дефект библиотеки.**
Чаще это неверные данные из вашего кода. Искать нужно в последнем своём кадре стека.

**Миф: отладчик нужен только для сложных случаев.**
Точка останова часто быстрее серии выводов в консоль.

## Частые вопросы

**С чего начинать, если ошибка не воспроизводится?**
С фиксации условий: окружение, данные, порядок шагов. Без воспроизведения нельзя проверить исправление.

**Что выводить в консоль?**
Значение, от которого зависит предположение, вместе с его именем.

**Почему стек асинхронной ошибки такой короткий?**
Продолжение выполняется отдельно от места запуска операции.

**Как отлаживать ошибку на одной итерации из тысячи?**
Условной точкой останова по нужному значению.

**Когда можно считать причину найденной?**
Когда удаётся вызвать ошибку и устранить её, управляя одним условием.

## Распространённые ошибки

### Ошибка 1. Исправлять до воспроизведения

Если проблема не воспроизведена, трудно доказать, что исправление действительно помогло.

### Ошибка 2. Менять несколько вещей сразу

После нескольких одновременных изменений непонятно, что именно повлияло на результат.

### Ошибка 3. Использовать `console.log()` без вопроса

Логи полезны, когда проверяют конкретное предположение.

### Ошибка 4. Игнорировать stack trace

Stack trace часто показывает не только место ошибки, но и путь вызовов.

### Ошибка 5. Маскировать flaky test через retry

Retry может быть временной защитой, но он не объясняет причину нестабильности.

## Краткие итоги

Debugging — это системный процесс поиска причины.

Главное:

* сначала нужно воспроизвести проблему;
* затем уменьшить область поиска;
* `console.log()` должен проверять предположение;
* breakpoint помогает остановиться и изучить состояние;
* stack trace — стартовая точка расследования, но не готовый ответ;
* исправление нужно проверить тем же сценарием, где ошибка проявлялась;
* в Automation QA важно отличать проблему теста, данных, API и UI.
