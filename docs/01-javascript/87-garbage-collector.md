# Garbage Collector

Теперь мы возвращаемся к выполнению программы. Модули создают объекты, функции, отчеты, логи и временные данные. Эти значения занимают память.

```mermaid

    N2 --> N3
```

## Главный вопрос

> Почему JavaScript со временем не занимает всю память?

Короткий ответ: JavaScript использует автоматическое управление памятью. Garbage Collector может освободить память, занятую объектами, которые стали недостижимыми.

## Мотивация

Тестовый раннер создает много временных объектов:

```javascript
function createReport() {
  const report = {
    testName: 'login test',
    status: 'passed',
    logs: ['start', 'assert', 'finish'],
  };

  return report;
}
```

Пока отчет нужен, объект должен оставаться в памяти.

Но после завершения теста старый отчет может быть больше не нужен.

```mermaid
flowchart TD
    N1["запуск теста"]
    N2["создан объект отчета"]
    N3["отчет используется"]
    N4["отчет больше не нужен"]
    N1 --> N2
    N2 --> N3
    N3 --> N4
```

Если бы JavaScript никогда не освобождал память, каждый запуск тестов оставлял бы после себя все старые объекты.

```mermaid
flowchart TD
    N1["запуск #1 → отчет"]
    N2["запуск #2 → отчет"]
    N3["запуск #3 → отчет"]
    N4["запуск #4 → отчет"]
    N5["память растет без остановки"]
    N4 --> N5
    N1 --> N2
    N2 --> N3
    N3 --> N4
```

JavaScript так не работает. Среда выполнения умеет очищать память, занятую объектами, к которым программа больше не может добраться.

## Теория

Garbage Collector — это механизм среды выполнения JavaScript, который отвечает за автоматическое освобождение памяти.

Разработчик обычно не вызывает ручное освобождение памяти.

Вместо этого модель автоматического управления памятью опирается на достижимость объектов.

```mermaid
flowchart TD
    N1["объект"]
    N2["reachable?"]
    N3["да → оставить в памяти"]
    N4["нет → можно собрать"]
    N1 --> N2
    N2 --> N3
    N2 --> N4
```

Reachable object — это объект, до которого программа может добраться через ссылки.

Сначала важна именно ссылка: переменная, свойство объекта, элемент массива или другая структура данных может удерживать путь к объекту. Только после этого появляется вопрос, reachable объект или unreachable.

Например:

```javascript
const report = {
  status: 'passed',
};
```

Пока переменная `report` ссылается на объект, объект достижим.

```mermaid
flowchart TD
    N1["report"]
    N2["{ status: 'passed' }"]
    N3["reachable"]
    N4["остается в памяти"]
    N1 --> N2
    N2 --> N3
    N3 --> N4
```

Если ссылка исчезает, объект может стать недостижимым:

```javascript
let report = {
  status: 'passed',
};

report = null;
```

Важно: точный момент очистки выбирает среда выполнения. Код не должен зависеть от того, когда именно Garbage Collector освободит память.

### Достижимость, а не счётчик ссылок

Модель проще, чем кажется: у среды выполнения есть набор корней — глобальный объект, переменные активных контекстов из главы 61, — и всё, до чего можно дойти от них по ссылкам, считается достижимым.

Отсюда важное следствие: два объекта, ссылающиеся друг на друга, но недостижимые от корней, будут собраны. Наивный подсчёт ссылок здесь ошибся бы — у каждого из них счётчик не нулевой.

```javascript
let a = { name: 'a' };
let b = { name: 'b' };
a.partner = b;
b.partner = a;

a = null;
b = null;   // оба недостижимы и могут быть собраны
```

### Что делает объект недостижимым

Перечень короткий, и в нём нет ничего про «удаление объекта»:

| Действие | Эффект |
| --- | --- |
| переприсвоить переменную | путь через неё исчезает |
| `delete obj.prop` | путь через свойство исчезает |
| удалить элемент из массива или коллекции | путь через него исчезает |
| выход из функции | локальные переменные перестают быть корнями |

Объект не удаляют — у него забирают **пути**. Когда не остаётся ни одного, сборщик вправе освободить память.

### Момент сборки не определён

Сборщик работает по своему усмотрению: недостижимый объект может быть собран сразу, а может пролежать в памяти значительное время.

Практические следствия:

- нельзя написать тест, проверяющий, что объект «освобождён»;
- рост потребления памяти на коротком отрезке ещё не означает утечку;
- принудительного освобождения в обычном коде нет — `delete` удаляет свойство, а не объект.

Поэтому работают не с моментом сборки, а с достижимостью: задача разработчика — не удерживать лишнего.

### Сборка не бесплатна

Автоматическое управление памятью экономит усилия, но не время выполнения: во время работы сборщика выполнение кода может приостанавливаться.

Для автотестов это одна из причин непредсказуемых задержек: пауза измерения, приписанная «медленному приложению», иногда оказывается работой сборщика в процессе тестов. Это ещё один аргумент против ожиданий, привязанных к точному времени.

### Что это значит на практике

Знание модели нужно не ради оптимизации, а ради одного вопроса при отладке: **что ещё держит ссылку на этот объект?**

Типичные держатели разбираются в следующей главе: долгоживущие массивы, замыкания из главы 65, обработчики событий и таймеры. Все они не «протекают» сами по себе — они просто остаются достижимыми дольше, чем нужно.

## Внутренний механизм

JavaScript можно представить как граф объектов.

Если объект доступен из активной части программы, он остается в памяти.

Все эти объекты reachable.

Если ссылка на объект исчезает, путь к нему может исчезнуть:

Garbage Collector не определяет бизнес-смысл объекта: нужен он логике программы или уже нет.

Критерий другой:

Поэтому ссылка определяет время жизни объекта в памяти.

## Главная ментальная модель

Главная модель главы связывает ссылку, достижимость и время жизни объекта: пока существует путь от корней к объекту, он достижим и остаётся в памяти.

Обратный путь выглядит так: последняя ссылка исчезает, объект становится недостижимым, и сборщик вправе освободить память — в момент, который выбирает сам.

Garbage Collector освобождает не "старые" объекты, а недостижимые объекты. Слово "может" здесь важно: код не управляет точным моментом очистки.

## Пример Automation QA

В тестовом фреймворке отчет может быть доступен во время выполнения теста:

```javascript
let currentReport = {
  testName: 'checkout test',
  status: 'failed',
  logs: ['open page', 'click checkout', 'assert error'],
};
```

Пока `currentReport` указывает на объект, отчет reachable.

После загрузки отчета ссылка может быть сброшена:

```javascript
currentReport = null;
```

Это не заставляет Garbage Collector немедленно запуститься. Но объект отчета больше не удерживается этой переменной.

## Распространённые мифы

**Миф: сборщик считает ссылки на объект.**
Он оценивает достижимость от корней. Взаимные ссылки недостижимой пары не спасают её от сборки.

**Миф: `delete` удаляет объект.**
Он удаляет свойство, то есть один из путей к объекту.

**Миф: после обнуления переменной память освобождается сразу.**
Момент сборки не определён. Гарантируется только возможность сборки.

**Миф: автоматическая сборка ничего не стоит.**
Во время её работы выполнение кода может приостанавливаться.

**Миф: рост памяти всегда означает утечку.**
Недостижимые объекты могут ждать сборки. Утечка — это объекты, остающиеся достижимыми.

## Частые вопросы

**Как сделать объект недостижимым?**
Убрать все пути к нему: переприсвоить переменные, удалить свойства, очистить коллекции.

**Можно ли принудительно запустить сборку?**
В обычном коде — нет. Управляют достижимостью, а не моментом сборки.

**Почему взаимные ссылки не мешают сборке?**
Учитывается достижимость от корней, а не количество ссылок.

**Можно ли проверить освобождение памяти тестом?**
Надёжно — нет: момент сборки не гарантирован.

**Какой главный вопрос при подозрении на утечку?**
Что ещё держит ссылку на этот объект.

## Распространённые ошибки

### Ошибка 1. Думать, что JavaScript освобождает память сразу после строки `object = null`

Сброс ссылки только делает объект потенциально недостижимым. Момент очистки выбирает среда выполнения.

### Ошибка 2. Думать, что Garbage Collector удаляет все "ненужные" объекты

Если объект все еще достижим через ссылку, Garbage Collector должен оставить его в памяти.

### Ошибка 3. Пытаться вручную управлять памятью как в низкоуровневых языках

В обычном JavaScript-коде разработчик управляет ссылками, а не вызывает ручное освобождение памяти.

## Краткие итоги

Garbage Collector освобождает память автоматически.

Главное:

* объект занимает память;
* объект остается в памяти, пока он reachable;
* reachable означает, что к объекту есть путь через ссылки;
* unreachable object может быть собран Garbage Collector;
* точный момент сборки выбирает среда выполнения;
* разработчик обычно управляет не памятью напрямую, а ссылками на объекты.

## Переход

Теперь понятно, почему память не остается занятой навсегда.

Но появляется следующий вопрос:

> Если Garbage Collector существует, почему memory leaks все еще возможны?

Ответ — объект может оставаться reachable дольше, чем мы ожидали.
