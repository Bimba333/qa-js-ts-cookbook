# Анатомия и модель выполнения теста

## Связь с предыдущей главой

Playwright Test отвечает за обнаружение и выполнение тестов. Теперь нужно увидеть, из каких частей состоит тест и в каком порядке тестовый раннер с ними работает.

## Цель главы

Научиться читать минимальный Playwright-тест и связывать его синтаксис с обнаружением, выполнением и результатом процесса.

## Главный вопрос

Как Playwright Test обнаруживает, группирует и выполняет тесты?

## Мотивация

Тестовый файл не является обычным скриптом, который последовательно выполняет всё при импорте. Вызов `test()` сначала объявляет сценарий, а тестовый раннер позже решает, когда и где выполнить его тело.

## Теория

### Объявление и выполнение — разные моменты

`test(title, body)` не запускает сценарий. Он **регистрирует** его: сообщает раннеру название и функцию, которую тот вызовет позже.

Разница заметна сразу, если поставить вывод на верхний уровень файла и внутрь теста:

```ts
console.log("загрузка файла");           // выполняется при обнаружении тестов

test("создаёт заказ", async ({ page }) => {
  console.log("тело теста");             // выполняется только при запуске этого теста
});
```

Первая строка печатается, даже если тест отфильтрован и выполняться не будет. Из этого следуют два практических правила: на верхнем уровне файла не должно быть ни подготовки данных, ни обращений к стенду, а состояние, общее для всех тестов файла, нельзя создавать при загрузке — файл загружается в каждом рабочем процессе заново.

### `test.describe` группирует объявления

`test.describe()` тоже выполняется при загрузке: его тело нужно, чтобы зарегистрировать вложенные тесты и хуки. Сам по себе `describe` тестом не является и в результатах отдельной строкой не появляется.

Область группы задаёт, на какие тесты распространяются `test.beforeEach`, `test.afterEach` и настройки вроде `test.use`. Это её единственное назначение: группировка по предметной области, а не способ переиспользовать код.

```mermaid
flowchart TD
    A[Тестовый файл] --> B[Обнаружение тестов]
    B --> C[Регистрация test и test.describe]
    C --> D[Worker выполняет выбранный тест]
    D --> E{Результат}
    E -->|Успех| F[Код завершения 0]
    E -->|Ошибка| G[Неуспешный результат]
```

### Arrange, Act, Assert как ориентир чтения

Удобная структура сценария — подготовить состояние, выполнить действие, проверить результат. Это ориентир для читаемости, а не требование делить каждый тест комментариями.

```ts
await page.setContent("<button>Сохранить</button>");            // Arrange
await page.getByRole("button", { name: "Сохранить" }).click();  // Act
await expect(page.getByText("Сохранено")).toBeVisible();        // Assert
```

Ценность формы в диагностике: по падению сразу видно, сломалась подготовка, действие или ожидание. Тест, в котором подготовка перемешана с проверками, заставляет читать его целиком, чтобы понять, что именно не сработало.

### Что происходит при падении

Упавшая проверка или отклонённый промис прерывают тело теста: оставшиеся строки не выполняются. Но этапы освобождения ресурсов выполняются — `afterEach` и завершение фикстур вызываются и после падения. Поэтому очистку нельзя писать последней строкой тела теста: именно до неё выполнение и не дойдёт.

Первая же ошибка завершает тест. Если в сценарии пять проверок и упала вторая, о состоянии остальных трёх вы ничего не узнаете, пока не почините первую причину.

### Почему `await` обязателен

Браузерные действия и проверки возвращают Promise. Без `await` тело теста продолжается, не дожидаясь результата, и раннер не может связать исход операции с нужным шагом.

Playwright Test это отслеживает. Действие, начатое и не дождавшееся завершения до конца теста, даёт явную ошибку:

```text
Error: locator.click: Test ended.
```

Сообщение точно указывает на пропущенный `await`. Но полагаться только на него не стоит: операция могла успеть завершиться сама, и тогда тест пройдёт — то стабильно, то нет, в зависимости от скорости стенда. Именно так и появляются флаки-тесты.

### Модель выполнения: рабочий процесс и изоляция

Раннер выполняет тесты в отдельных рабочих процессах. Процесс загружает тестовый файл, получает назначенный тест, готовит для него фикстуры и выполняет тело. Файл при этом загружается в каждом процессе независимо, поэтому модульные переменные не общие.

Результат теста складывается из трёх вещей: завершились ли ожидаемые промисы, прошли ли проверки и уложился ли тест во время. Ненулевой код завершения процесса — итог всего запуска, и в CI он и есть сигнал о неуспехе.

Аннотации (`test.skip`, `test.fixme`, `test.slow`) позволяют помечать или изменять режим отдельных тестов; здесь достаточно понимать их место в модели выполнения.

## Внутренний механизм

```mermaid
flowchart TD
    A[Тестовый файл] --> B[Обнаружение тестов]
    B --> C[Регистрация test и test.describe]
    C --> D[Worker выполняет выбранный тест]
    D --> E{Результат}
    E -->|Успех| F[Код завершения 0]
    E -->|Ошибка| G[Неуспешный результат]
```

Раннер загружает объявления, применяет фильтры и передаёт выбранный тест рабочему процессу. Если ожидаемый промис браузерного действия или проверки завершается ошибкой, оставшаяся часть тела теста обычно не выполняется, а инструмент переходит к применимым этапам освобождения ресурсов. Поэтому асинхронные операции нужно ожидать через `await`: иначе тело может продолжиться до завершения действия, а результат не свяжется с правильным шагом.

Аннотации позволяют помечать или изменять режим отдельных тестов, но здесь достаточно понимать их место в модели выполнения.

### Файл выполняется не один раз

```text
обнаружение тестов   → файл загружен, тела describe выполнены
рабочий процесс № 1  → файл загружен ЗАНОВО, тела describe выполнены
рабочий процесс № 2  → файл загружен ЗАНОВО, тела describe выполнены
```

Загрузка файла и выполнение теста — разные события. Всё, что написано на
верхнем уровне файла или прямо в теле `describe`, выполняется при каждой
загрузке: при обнаружении и в каждом рабочем процессе.

Поэтому запрос к стенду, вынесенный на верхний уровень, выполняется больше
раз, чем есть тестов, и вне всякой изоляции. Такой код принадлежит хукам или
фикстурам.

### Что происходит после падения

Тело теста прекращается на упавшей строке: следующие строки не выполняются.
Освобождение при этом происходит — `afterEach` и освобождение фикстур
выполняются и после падения, поэтому очистка, размещённая там, срабатывает.

Второе следствие менее очевидно: после неуспешного теста раннер берёт **новый
рабочий процесс**, даже когда повторы отключены. Файловый `beforeAll`
выполняется заново, а значит, обязан быть идемпотентным.


## Главная ментальная модель

Объявление описывает тест раннеру, рабочий процесс выполняет его тело, а завершённые промисы и проверки формируют результат.

## Практические примеры

Название `создаёт заказ с валидными данными` сообщает поведение лучше, чем `test 1`. Подготовка локального HTML относится к Arrange, нажатие кнопки — к Act, проверка статуса — к Assert.

## Automation QA

Понятная анатомия теста помогает отличить ошибку обнаружения от ошибки подготовки, действия или проверки. Это сокращает область расследования при падении CI-запуска.

## Концептуальные границы и компромиссы

Слишком строгая форма Arrange/Act/Assert может создавать искусственные блоки, а отсутствие видимого потока делает сценарий трудным для чтения. Группировка `describe` полезна при общей предметной области, но не должна создавать глубокую вложенность.

## Распространённые ошибки

- Забывать `await` перед браузерным действием или проверкой — тест завершается раньше операции. Раннер часто сообщает `Test ended`, но если операция успела пройти, тест окажется зелёным без выполненной проверки.

- Выполнять сценарий во время загрузки файла вместо объявления через `test()` — тело файла выполняется при обнаружении тестов и в каждом рабочем процессе, поэтому код вне `test()` выполняется не один раз и вне изоляции.

- Использовать неинформативные названия — имя теста попадает в отчёт, в отбор по `--grep` и в имя каталога с артефактами. «работает корректно» не помогает ни найти тест, ни понять падение.

- Считать `test.describe()` отдельным тестом — это группировка: её тело выполняется при загрузке файла, а не при запуске. Подготовку внутри неё выполняют хуки, а не прямые вызовы.

- Игнорировать ненулевой код выхода запуска — именно он отличает «прогон прошёл» от «прогон состоялся». Шаг CI, теряющий код выхода, делает красный прогон зелёным.

## Распространённые мифы

**Миф: код на верхнем уровне файла выполняется перед «своими» тестами.**
Он выполняется при загрузке файла — то есть при обнаружении тестов, до любого запуска и даже для отфильтрованных тестов.

**Миф: `test.describe` — это тест.**
Это группировка объявлений. В результатах она отдельной строкой не появляется.

**Миф: забытый `await` всегда заметен.**
Раннер поймает его только если операция не успела завершиться. Иначе тест проходит нестабильно, и причина выглядит как «нестабильность».

**Миф: после падения тест доделывает очистку в теле.**
Оставшиеся строки тела не выполняются. Освобождение ресурсов должно жить в `afterEach` или в завершении фикстуры.

**Миф: модульная переменная общая для всего запуска.**
Файл загружается в каждом рабочем процессе отдельно, поэтому у параллельных процессов свои копии.

## Частые вопросы

**Почему тест прошёл локально и упал в CI без изменений кода?**
Частая причина — пропущенный `await`: на быстрой машине операция успевает завершиться, на загруженной — нет.

**Где размещать подготовку данных?**
В `beforeEach` или в фикстуре, но не на верхнем уровне файла: там она выполнится при обнаружении тестов независимо от того, запустятся ли они.

**Что будет с проверками после первой упавшей?**
Они не выполнятся. Если нужно увидеть несколько независимых фактов, их разносят по отдельным тестам.

**Нужно ли `describe` в файле с одним тестом?**
Нет. Группа оправдана, когда объединяет тесты одной предметной области или общие хуки.

**Почему код выхода важнее вывода в консоль?**
CI принимает решение по коду завершения. Вывод помогает расследовать, но ненулевой код — единственный надёжный признак неуспеха.

## Проверьте себя

1. Что выполняется при загрузке тестового файла, а что — при запуске теста?
2. Почему `test.describe` не появляется в результатах отдельной строкой?
3. Какое сообщение даёт раннер при незавершённом действии без `await`?
4. Почему очистку нельзя писать последней строкой тела теста?
5. Почему модульная переменная не общая для всех тестов запуска?

### Ответы

1. При загрузке файла выполняется весь код верхнего уровня и вызовы `test()`, регистрирующие тесты. Тела тестов выполняются позже, при запуске.
2. Это группировка: она даёт имя и общие хуки, но сама тестом не является.
3. Тест завершается, а затем раннер сообщает о незавершённой операции или о том, что страница уже закрыта. Причина при этом указывает не на настоящую ошибку.
4. При падении теста эта строка не выполнится: до неё дело не дойдёт. Очистка должна жить в фикстуре или хуке, которые выполняются всегда.
5. Тесты распределяются между рабочими процессами, и у каждого своя копия модулей. Переменная общая только внутри одного процесса.

## Краткие итоги

- `test()` регистрирует название и тело теста.
- Обнаружение тестов предшествует выполнению.
- Worker выполняет выбранные тесты.
- Необработанная ошибка или неуспешная проверка делает тест неуспешным.
- Асинхронные операции должны быть ожидаемыми.
