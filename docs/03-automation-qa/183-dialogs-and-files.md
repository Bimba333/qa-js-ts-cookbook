# Диалоги и работа с файлами

## Связь с предыдущей главой

Popup требует ожидания события браузера до действия. JavaScript dialogs и download используют ту же модель синхронизации, а upload передаёт браузеру локальный файл вместо обычного ввода текста.

## Цель главы

Научиться обрабатывать события dialog, загружать файлы, ожидать download и управлять временными артефактами.

## Главный вопрос

Как автоматизировать взаимодействия браузера, которые не являются обычными DOM-действиями?

## Мотивация

`alert`, file chooser и download управляются браузером, а не обычным DOM после клика. Если тест неправильно обрабатывает событие или не определяет владельца файла, сценарий может остановиться либо оставить артефакты.

## Теория

Событие dialog предоставляет объект `Dialog` с типом, сообщением и действиями `accept()` или `dismiss()`. Без обработчика Playwright автоматически отклоняет dialog. Если тест зарегистрировал обработчик, он должен вызвать `accept()` или `dismiss()`, иначе вызвавшее dialog действие не завершится.

Для существующего `<input type="file">` используется `setInputFiles()`. Файл должен быть локальным тестовым ресурсом без секретов. Если приложение создаёт file chooser динамически, ожидание события начинается до клика по элементу-триггеру.

Событие download также ожидается до действия. Объект `Download` сообщает предлагаемое имя файла и позволяет сохранить файл в контролируемый путь. Временный артефакт удаляет тест или fixture, которая его создала.

## Внутренний механизм

Эти API не обходят поведение браузера. Playwright подписывается на события браузерного протокола и связывает их с действием теста. Локальный файл upload читает процесс тестового раннера, а download сначала принадлежит браузерному контексту и затем копируется через `saveAs()`.

## Главная ментальная модель

Событие браузера требует заранее установленного наблюдения, а каждый созданный файловый артефакт требует явного владельца очистки.

## Практические примеры

Dialog подтверждает сохранение профиля. Upload передаёт локальный тестовый файл. Download сохраняется в изолированный путь результата теста, проверяется и удаляется независимо от результата проверки.

## Automation QA

Файловые сценарии должны использовать небольшие контролируемые тестовые ресурсы. Для download проверяют не только имя, но и содержимое или формат, соответствующий цели теста.

## Концептуальные границы и компромиссы

Проверка download в браузере не заменяет проверку всей отчётной системы. Временные файлы допустимы, если путь изолирован, очистка гарантирована, а секретные данные не сохраняются без необходимости.

## Распространённые ошибки

- Регистрировать обработчик dialog после клика.
- Загружать личный файл с машины разработчика.
- Проверять только факт download без содержимого.
- Сохранять артефакты в общий постоянный путь.
- Не выполнять очистку после неуспешной проверки.
- Путать file chooser с обычным текстовым полем.

## Краткие итоги

- Dialog обрабатывается через событие браузера.
- Upload использует локальный контролируемый тестовый ресурс.
- Ожидание download начинается до действия-триггера.
- `saveAs()` переносит download в управляемый путь.
- Временные файлы требуют гарантированной очистки.

## Что нужно запомнить

- Обработчик должен быть зарегистрирован до события.
- Зарегистрированный обработчик обязан закрыть dialog.
- Тестовые ресурсы не должны содержать секреты.
- Путь результата теста должен быть изолирован.
- Владение файлом включает его удаление.
