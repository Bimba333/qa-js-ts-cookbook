# Загрузка и runtime validation конфигурации

## Связь с предыдущей главой

Глава 217 определила внешние источники конфигурации. Их значения остаются недоверенными строками, пока программа не проверит форму и смысл.

## Цель главы

Построить загрузчик, который читает, преобразует и валидирует внешние значения, возвращая типизированный результат или диагностическую ошибку до старта тестов.

## Главный вопрос

> Как завершить запуск сразу, если внешняя конфигурация неполна или некорректна?

## Мотивация

Ошибка `Cannot read properties of undefined` в середине теста скрывает настоящую причину — отсутствующую настройку. Раннее завершение сокращает расстояние между дефектом конфигурации и сообщением о нём.

## Теория

### Четыре шага от строки к конфигурации

Загрузчик конфигурации читает внешние строки, удаляет незначащие пробелы, разбирает значения и проверяет ограничения. Только после этих шагов появляется `RuntimeConfig`.

```mermaid
flowchart LR
    E[Внешние строки] --> N[Удалить внешние пробелы]
    N --> P[Разобрать значения]
    P --> V[Runtime validation]
    V -->|успех| C[Типизированная конфигурация]
    V -->|ошибка| F[Завершить запуск]
```

Каждый шаг отвечает за своё:

| Шаг | Что делает | Пример |
| --- | --- | --- |
| нормализация | убирает допустимые различия | внешние пробелы вокруг значения |
| разбор | переводит строку в нужный тип | `"5000"` → `5000`, строка → проверенный URL |
| проверка | подтверждает ограничения | диапазон, протокол, разрешённое окружение |
| результат | отдаёт типизированный объект | `RuntimeConfig` |

Нормализация нужна не из вежливости: значение, скопированное в переменную CI с переводом строки на конце, внешне выглядит верным и ломает сравнение с разрешённым списком.

### Типы не проверяют внешнюю среду

TypeScript описывает результат загрузчика, но не проверяет `process.env` во время выполнения.

Это то же ограничение, что в главах 195 и 210, и здесь оно наиболее опасно: неверная конфигурация ломает **весь** запуск, а не один тест. Объявление `const config: RuntimeConfig = process.env as any` компилируется и отдаёт остальному коду мусор с правильным типом.

Именно поэтому проверка нужна во время выполнения, а тип — лишь фиксирует её результат.

### Загрузчик либо возвращает валидное, либо не возвращает ничего

Загрузчик не должен возвращать частично валидный объект.

Половинчатый результат — худший исход: часть кода работает, часть падает позже и в другом месте, а связь с исходной причиной теряется. Отказ на границе даёт точное сообщение сразу.

Диагностическая ошибка называет поле и правило, но не раскрывает секрет:

```text
BASE_URL: ожидался протокол http или https
ENVIRONMENT: допустимые значения — local, preview
API_TOKEN: обязательное значение не задано
```

Каждое сообщение отвечает на вопрос «что именно исправить», и ни одно не печатает значение секрета.

### Результат замораживается

После успешного вызова остальной код получает readonly-результат, замороженный через `Object.freeze()`, с примитивными полями и не повторяет проверки каждого поля.

Заморозка здесь не украшение. В модуле присваивание замороженному свойству **бросает исключение**:

```text
TypeError: Cannot assign to read only property 'baseUrl' of object
```

То есть случайная попытка подправить конфигурацию по ходу теста обнаруживается сразу, а не превращается в загадочное расхождение между тестами.

Важная оговорка: это поверхностная, а не глубокая заморозка. Вложенный объект остаётся изменяемым, и `Object.isFrozen` для него вернёт `false`. В примере вложенных изменяемых значений нет — и это сознательное решение, а не случайность.

По той же причине URL возвращается строкой: загрузчик не передаёт вызывающему коду изменяемый объект `URL`.

### `readonly` и `Object.freeze` защищают в разное время

Их легко перепутать, хотя работают они на разных этапах:

- `readonly` в TypeScript запрещает присваивание **при компиляции** — и обходится приведением типа;
- `Object.freeze()` запрещает его **во время выполнения** — и приведением не обходится.

Проверено: `readonly`-поле нельзя присвоить и у `readonly`-массива нет `push`, но `(cfg as { baseUrl: string }).baseUrl = ...` компилируется без замечаний. Для конфигурации, которая приходит извне, нужны оба механизма.

### Загружать до дорогих операций

Конфигурацию следует загрузить до начала дорогих операций браузера, API или базы данных.

Порядок влияет на качество диагностики. Загрузка в самом начале даёт отказ через доли секунды с точным именем настройки. Загрузка по мере надобности даёт падение в середине сценария — и выглядит оно как дефект продукта, потому что к этому моменту уже открыт браузер, создан контекст и выполнено несколько шагов.

Тогда ошибка запуска не маскируется под дефект продукта и содержит точное имя некорректной настройки.

### Где остановиться с проверками

Строгая runtime validation требует описать контракт, но делает запуск воспроизводимым.

Чрезмерная проверка внутренних констант лишь усложняет загрузчик; проверять нужно внешнюю границу. Значение, записанное в коде рядом, не станет неверным между запусками — проверять его бессмысленно.

Практический ориентир: проверке подлежит всё, что пришло из `process.env`, файла, аргументов командной строки или сети. Всё, что объявлено в самом модуле, уже проверено компилятором.

## Распространённые мифы

**Миф: типизированная конфигурация уже проверена.**
Тип описывает ожидание. Значения приходят во время выполнения, и проверять их должен загрузчик.

**Миф: `Object.freeze()` защищает объект целиком.**
Заморозка поверхностная: вложенные объекты остаются изменяемыми.

**Миф: `readonly` заменяет заморозку.**
Он действует при компиляции и обходится приведением типа. Во время выполнения не защищает ничего.

**Миф: лучше вернуть частично валидную конфигурацию, чем упасть.**
Тогда падение случится позже и в другом месте, а связь с причиной потеряется.

**Миф: проверять надо всю конфигурацию, включая внутренние константы.**
Проверке подлежит внешняя граница. Константы в коде уже проверены компилятором.

## Частые вопросы

**Зачем убирать пробелы у значений?**
Значение, скопированное в переменную CI с переводом строки, выглядит верным и не совпадает с разрешённым списком.

**Что должно быть в сообщении об ошибке конфигурации?**
Имя поля и нарушенное правило. Значение секрета — никогда.

**Когда загружать конфигурацию?**
До дорогих операций. Иначе отказ выглядит как дефект продукта в середине сценария.

**Почему URL возвращается строкой?**
Чтобы не отдавать вызывающему коду изменяемый объект и сохранить свойство неизменяемости результата.

**Нужны ли одновременно `readonly` и `Object.freeze()`?**
Для внешней конфигурации — да: они защищают на разных этапах.

## Распространённые ошибки

- Использовать type assertion вместо runtime validation.
- Преобразовывать `Number(value)` без проверки результата.
- Возвращать объект после первой обнаруженной частичной ошибки.
- Включать secret в текст исключения.

## Краткие итоги

- Внешняя строка не становится безопасной из-за TypeScript-типа.
- Загрузчик нормализует строки, разбирает значения и выполняет runtime validation.
- Успех возвращает полный типизированный результат.
- Некорректный запуск завершается до тестовых действий.
