# Architecture review и эволюция Framework

## Связь с предыдущей главой

Глава 248 завершила общий execution и diagnostic flow. Перед финальным проектом нужно проверить, какие архитектурные решения действительно выдерживают изменения и где накопилась измеримая стоимость поддержки.

## Цель главы

Провести architecture review границ, связности и владения, затем выбрать следующий рефакторинг по наблюдаемой проблеме.

## Главный вопрос

> Как оценить готовность framework к росту и выбрать следующий рефакторинг по фактической проблеме?

## Мотивация

Рефакторинг без сигнала создаёт speculative abstractions. Framework получает interfaces, factories и containers, которые никто не использует, а реальные циклы, shared state и слишком широкий cleanup остаются.

## Теория

Review начинается не с желаемого pattern, а с evidence: изменение transport затрагивает tests, fixture создаёт client в нескольких местах, cleanup оставляет остаточное состояние, диагностика теряет `cause` или граф imports содержит цикл. Затем проверяются публичные границы, направление зависимостей, cohesion внутри модулей и coupling между ними.

Стоимость поддержки включает сложность изменения, время локализации failure, стоимость setup и число владельцев одного ресурса. Следующий refactoring должен уменьшать конкретную стоимость небольшим шагом. После изменения те же сигналы измеряются снова.

Контрольный список не объявляет архитектуру навсегда правильной. Он фиксирует текущие ограничения, владельца решения и критерий повторной оценки. Финальный проект использует эти правила, но его реализация начинается в следующей части курса.

## Внутренний механизм

Review собирает evidence, ранжирует проблемы по риску, выбирает одно ограниченное изменение и проверяет результат. Детерминированный выбор использует severity и locale-independent сравнение имени. Отсутствие подтверждённой проблемы является допустимым решением ничего не рефакторить.

## Главная ментальная модель

Evidence превращается в конкретную проблему, проблема — в ограниченный refactoring, а повторная проверка показывает, уменьшилась ли исходная стоимость. Без evidence цикл изменений не начинается.

## Практический пример

```text
examples/03-automation-qa/chapter-249/01-architecture-review.integration.ts
```

Детерминированная функция выбирает проблему с наибольшей severity, разрешает равенство без зависимости от locale и сохраняет evidence как причину решения. При отсутствии сигналов она не предлагает speculative abstraction.

## Automation QA

Review проверяет, можно ли заменить API adapter без изменения tests, имеют ли данные одного владельца cleanup, разделены ли test и worker scopes, сохраняется ли `cause` ошибки и диагностируется ли shard независимо. Цикл, обратный import, global state, разрозненное чтение config и fixture со слишком широкой ответственностью являются наблюдаемыми сигналами, но не требуют одинакового исправления.

## Компромиссы

Узкие границы требуют дисциплины, но уменьшают область влияния изменения. Слишком раннее выделение interface увеличивает стоимость чтения. Решение зависит от подтверждённой изменчивости, а не от универсального шаблона.

## Распространённые ошибки

- Рефакторить ради названия pattern.
- Измерять качество числом interfaces.
- Игнорировать стоимость fixture setup.
- Делать один framework object владельцем всех обязанностей.
- Переносить финальный проект в architecture review.

## Краткие итоги

- Architecture review начинается с evidence.
- Coupling и cohesion оцениваются относительно изменений.
- Рефакторинг решает одну подтверждённую проблему.
- Speculative abstractions не добавляются без необходимости.
