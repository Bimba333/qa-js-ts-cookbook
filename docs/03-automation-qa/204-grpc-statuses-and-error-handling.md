# Статусы gRPC и обработка ошибок

## Связь с предыдущей главой

Глава 203 получила `DEADLINE_EXCEEDED` и `CANCELLED`. Эти результаты входят в отдельную модель gRPC status, которая не совпадает с группами HTTP status.

## Цель главы

Проверять `code`, `details` и metadata объекта `ServiceError` и отличать ожидаемый отказ от недоступности транспорта.

## Главный вопрос

Как gRPC сообщает об отказе и какие свойства ошибки должен проверять тест?

## Мотивация

Проверка только факта отклонения Promise скрывает причину. Механическое сопоставление каждого gRPC status одному HTTP-коду создаёт ложную модель и ухудшает негативные сценарии.

## Теория

### Отказ — это структурированное завершение

Успешный call завершается `OK`. Ошибка приходит как `ServiceError` с числовым `code`, строкой `details` и metadata.

Это настоящий объект `Error`, поэтому он работает со стандартными средствами языка: его можно выбросить, поймать в `catch`, передать в `reject`. Но полезная информация лежит не в `message`, а в трёх полях:

| Поле | Роль | Стабильность |
| --- | --- | --- |
| `code` | классифицирует отказ | часть публичного контракта |
| `details` | уточняет причину | стабильна, только если контракт это обещает |
| `metadata` | служебный контекст отказа | по договорённости |

Тест проверяет только стабильные свойства публичного контракта.

### Карта статусов

Коды имеют собственную нумерацию, и полезно знать хотя бы основные:

| Статус | Код | Когда возникает |
| --- | --- | --- |
| `OK` | 0 | успешное завершение |
| `CANCELLED` | 1 | клиент отменил вызов |
| `INVALID_ARGUMENT` | 3 | request некорректен сам по себе |
| `DEADLINE_EXCEEDED` | 4 | ответ не пришёл вовремя |
| `NOT_FOUND` | 5 | ресурс не существует |
| `ALREADY_EXISTS` | 6 | ресурс уже существует |
| `PERMISSION_DENIED` | 7 | прав недостаточно |
| `FAILED_PRECONDITION` | 9 | операция невозможна при текущем состоянии |
| `UNAVAILABLE` | 14 | сервис временно недоступен |
| `UNAUTHENTICATED` | 16 | личность не установлена |

Эти коды не следует сводить к универсальной таблице соответствия HTTP-кодам. Похожие по смыслу пары существуют, но нумерация разная, а часть статусов — `DEADLINE_EXCEEDED`, `CANCELLED` — аналогов в HTTP не имеет вовсе.

### Две пары, которые путают чаще всего

**`INVALID_ARGUMENT` против `FAILED_PRECONDITION`.** Первый означает, что request некорректен **независимо от текущего состояния** server: пустое обязательное поле останется ошибкой при любых данных. Второй относится к операции, которая невозможна **при текущем состоянии**: завершить уже завершённую задачу. Различие практическое — в первом случае повтор запроса бессмыслен, во втором он может удаться после изменения состояния.

**`NOT_FOUND` против `ALREADY_EXISTS`.** Они описывают разные состояния ресурса и обычно возникают в разных операциях: первый при чтении или изменении несуществующего, второй при создании дубликата.

**`UNAUTHENTICATED` против `PERMISSION_DENIED`** — знакомая по REST пара: личность не установлена против недостаточных прав.

### Сравнивать с константой, а не с числом

Проверка читается лучше и не зависит от памяти читателя, если сравнение идёт с именованным значением:

```ts
expect(error.code, "пустой title недопустим").toBe(status.INVALID_ARGUMENT);
```

Число `3` в тесте требует от читателя знания таблицы, а при ошибке в отчёте покажет `Expected: 3` — что не объясняет ничего.

### `details` проверять осторожно

Текст details может быть диагностическим и меняться, если контракт не обещает его стабильность. В таком случае точный code важнее полного сравнения строки.

Разумный компромисс: сравнивать код точно, а `details` проверять на содержание ключевого признака, если контракт его фиксирует. Полное сравнение строки превращает работу редактора сообщений в падение тестов — ровно как проверка текста ошибки в REST.

### Инфраструктурная ошибка — не бизнес-отказ

Это главная ловушка негативных gRPC-тестов. Недоступный server даёт `UNAVAILABLE` (14) — проверено на обращении к закрытому порту. Тест, который ожидает любой ошибки, на таком ответе «пройдёт» и ничего не проверит.

Точно так же вызов после `client.close()` выбрасывает исключение `Channel has been shut down` — это вообще не gRPC-статус, а ошибка использования клиента.

Отсюда правило: негативный тест ожидает **конкретный** код отказа. Проверка вида «пришла ошибка» пропускает и упавший стенд, и закрытый channel, и неверно настроенный адрес.

### Что доказывает негативный тест

Негативный тест фиксирует одну причину отказа и проверяет `code`, стабильные `details` и отсутствие побочного эффекта.

Третья часть особенно важна: отклонённый create с правильным `INVALID_ARGUMENT` мог всё же создать запись, если валидация распределена по шагам обработки. Без последующего чтения состояния тест подтверждает только формат ответа.

Инфраструктурная ошибка не выдаётся за корректную проверку бизнес-правила — и это относится не только к `UNAVAILABLE`, но и к любому статусу, полученному «случайно», без понимания, почему он возник.

## Внутренний механизм

Обработчик server передаёт в callback объект `ServiceError`. Среда выполнения сериализует status и details при завершении call. Promise на стороне client отклоняется той же ошибкой, сохраняя `code` и диагностические данные.

Пример проверяет `INVALID_ARGUMENT` и `NOT_FOUND` вместе со стабильными details.

## Главная ментальная модель

Ошибка gRPC — структурированное завершение RPC: status code классифицирует отказ, `details` уточняет его, metadata добавляет служебный контекст.

## Практические примеры

- Пустой title → `INVALID_ARGUMENT`.
- Неизвестный ID → `NOT_FOUND`.
- Повтор уникального title → `ALREADY_EXISTS`.
- Недоступный server → `UNAVAILABLE`, а не ожидаемый бизнес-отказ.

## Automation QA

Негативный тест фиксирует одну причину отказа и проверяет `code`, стабильные `details` и отсутствие побочного эффекта. Инфраструктурная ошибка не выдаётся за корректную проверку бизнес-правила.

## Концептуальные границы и компромиссы

Текст details может быть диагностическим и меняться, если контракт не обещает его стабильность. В таком случае точный code важнее полного сравнения строки.

## Распространённые мифы

**Миф: gRPC-коды можно сопоставить HTTP-кодам один к одному.**
Нумерация другая, а `DEADLINE_EXCEEDED` и `CANCELLED` аналогов в HTTP не имеют.

**Миф: достаточно проверить, что пришла ошибка.**
Так «пройдёт» и недоступный стенд с `UNAVAILABLE`, и закрытый channel. Нужен конкретный код.

**Миф: `INVALID_ARGUMENT` и `FAILED_PRECONDITION` взаимозаменяемы.**
Первый не зависит от состояния сервиса, второй именно им и вызван. Повтор запроса имеет смысл только во втором случае.

**Миф: `details` — надёжный предмет проверки.**
Текст меняется, если контракт не обещает обратного. Точный код важнее.

**Миф: правильный код отказа означает отсутствие изменений.**
Сервис мог применить часть операции. Это проверяется отдельным чтением состояния.

## Частые вопросы

**Какой код ожидать при пустом обязательном поле?**
`INVALID_ARGUMENT` (3): запрос некорректен независимо от состояния сервиса.

**А при попытке завершить уже завершённую задачу?**
`FAILED_PRECONDITION` (9): операция невозможна при текущем состоянии.

**Что означает `UNAVAILABLE` в отчёте?**
Обычно проблему стенда или сети, а не бизнес-отказ. Такой результат не подтверждает контракт.

**Стоит ли сравнивать `details` целиком?**
Только если контракт обещает стабильность текста. Иначе достаточно ключевого признака.

**Почему вызов после `close()` не даёт статус?**
Это ошибка использования клиента, а не завершение RPC: исключение возникает до отправки.

## Распространённые ошибки

- Проверять только `rejects.toBeTruthy()`.
- Считать gRPC code HTTP-кодом.
- Путать `UNAUTHENTICATED` и `PERMISSION_DENIED`.
- Путать `DEADLINE_EXCEEDED` и `UNAVAILABLE`.
- Сравнивать нестабильный stack trace.

## Краткие итоги

- `ServiceError` содержит `code`, `details` и metadata.
- Status описывает категорию завершения call.
- Бизнес-отказы и транспортные ошибки требуют разной интерпретации.
- Негативный тест проверяет точную причину.
- Универсального HTTP mapping нет.

## Что нужно запомнить

- Проверяйте code прежде текста.
- Сравнивайте details только как часть контракта.
- Не скрывайте metadata, полезные для диагностики.
- Не маскируйте инфраструктурную ошибку повторными попытками.
