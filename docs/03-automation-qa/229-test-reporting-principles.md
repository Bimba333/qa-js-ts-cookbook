# Принципы тестовой отчётности

## Связь с предыдущей главой

Глава 228 связала доказательства с результатом теста. Теперь нужно определить, какая структура отчёта помогает разным участникам понять результат.

## Цель главы

Сформировать контракт отчёта из идентичности теста, status, duration, steps, сведений об ошибке, контекста окружения, links и владельца.

## Главный вопрос

> Какая информация делает report полезным для разработки, QA и CI?

## Мотивация

Список `passed/failed` не отвечает, какой сценарий запускался, в каком окружении, кто владеет тестом и где искать доказательства. Но отчёт, перегруженный внутренними вызовами helper, скрывает бизнес-поток.

## Теория

Идентичность теста включает стабильное название сценария и при необходимости ссылку на test case. Status и duration дают итог запуска, но не объясняют причину. Steps показывают значимые этапы. Сведения об ошибке сохраняют исходные stack и message. Контекст окружения содержит его безопасное имя, project и версию приложения без секретов.

Владелец направляет результат ответственной команде. Links связывают test case, defect или requirement. History сопоставляет стабильную идентичность теста между запусками и показывает тенденцию, но не устанавливает первопричину. CI может опубликовать отчёт, однако не определяет его смысл: контракт должен быть полезен и при локальном запуске.

## Внутренний механизм

Playwright Test собирает идентичность теста, duration, steps, errors и attachments в результат теста. Reporter преобразует эти данные в представление. Поэтому предметные названия и доказательства создаются в тестовом потоке, а reporter не должен изобретать отсутствующий контекст.

## Главная ментальная модель

Отчёт похож на карту расследования: идентичность теста показывает место, steps — маршрут, сведения об ошибке — точку остановки, attachments — доказательства, а владелец — следующего участника.

## Automation QA

Шаги называют по намерению: «Создать задачу через API», а не «Вызвать helper». Сведения о падении сохраняют исходную ошибку и идентификатор сценария для поиска записей журнала. Созданные reporter файлы являются результатами запуска, а не исходным кодом проекта.

## Компромиссы

Подробность отчёта полезна до определённой границы. Повторение каждой операции locator и каждого вызова helper делает основной сценарий нечитаемым.

## Распространённые ошибки

- Использовать технические названия вместо бизнес-намерения.
- Терять исходный stack при оборачивании Error.
- Добавлять секреты в контекст окружения.
- Ожидать, что reporter восстановит отсутствующие steps.

## Краткие итоги

- Отчёт объединяет идентичность теста, результат, контекст и доказательства.
- Steps отражают бизнес-этапы.
- Сведения о падении сохраняют исходную ошибку.
- Владелец и links ускоряют передачу результата.
