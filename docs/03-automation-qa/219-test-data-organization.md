# Организация test data

## Связь с предыдущей главой

Глава 218 создала валидированную конфигурацию окружения. Тестовые данные отвечают на другой вопрос: какие бизнес-значения нужны конкретному сценарию и кто ими владеет.

## Цель главы

Выбирать между статическими, динамическими, сценарными и зависящими от окружения данными, не смешивая данные теста с конфигурацией и секретами.

## Главный вопрос

> Когда использовать статические данные, а когда создавать их динамически?

## Мотивация

Общая изменяемая запись делает тесты зависимыми друг от друга. Полностью случайные данные, напротив, затрудняют воспроизведение. Нужна классификация по изменяемости и владельцу.

## Теория

Статические данные подходят для неизменяемых справочников: допустимых статусов или кодов. Динамические данные создаются для конкретного запуска. Сценарные данные выражают условие проверки. Данные, зависящие от окружения, допустимы, когда окружения объективно различаются, но такое различие должно приходить из валидированной конфигурации.

Владелец данных отвечает за создание, использование и очистку. Секреты и персональные данные не являются тестовыми заготовками: их нельзя копировать в репозиторий или отчёты. Для сценария используются синтетические значения.

Входные данные и ожидаемый результат должны быть независимыми значениями. Если они разделяют изменяемую ссылку, подготовка запроса способна незаметно изменить ожидание и скрыть дефект. TypeScript-модификатор `readonly` запрещает часть операций при компиляции, но не замораживает объект во время выполнения; для небольшого статического справочника пример дополнительно использует `Object.freeze()`.

## Внутренний механизм

Тестовые данные проходят от источника к сценарию и затем к очистке. Неизменяемый справочник можно безопасно разделять, а изменяемая сущность получает уникальный ID и одного владельца.

## Главная ментальная модель

Данные похожи на инструмент с биркой владельца: общими могут быть только неизменяемые вещи.

## Практический пример

```text
examples/03-automation-qa/chapter-219/01-test-data-ownership.execution.ts
```

Замороженный справочник названий используется совместно, а задача сценария создаётся фабрикой с диагностируемым ID проекта, повтора и worker.

## Automation QA

Page Object не должен хранить бизнес-данные теста, конфигурация — генерировать сущности, а статический JSON — содержать общую изменяемую учётную запись. Сценарий явно получает необходимые данные. Это распределение ответственности не требует единой структуры каталогов для каждого проекта.

## Компромиссы

Статические данные проще читать, но их трудно безопасно изменять. Динамические данные изолируют сценарий, но требуют полезных идентификаторов и воспроизводимого способа создания.

## Распространённые ошибки

- Использовать одну изменяемую сущность для всего набора тестов.
- Считать любой JSON-файл безопасной тестовой заготовкой.
- Смешивать URL окружения и бизнес-поля заказа.
- Копировать реальные персональные данные.

## Краткие итоги

- Статические данные должны быть неизменяемыми во время выполнения.
- Динамические данные помогают изоляции.
- Сценарные данные выражают цель проверки.
- Каждая изменяемая сущность имеет владельца.
