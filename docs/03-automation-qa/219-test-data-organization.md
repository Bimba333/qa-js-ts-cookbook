# Организация test data

## Связь с предыдущей главой

Глава 218 создала валидированную конфигурацию окружения. Тестовые данные отвечают на другой вопрос: какие бизнес-значения нужны конкретному сценарию и кто ими владеет.

## Цель главы

Выбирать между статическими, динамическими, сценарными и зависящими от окружения данными, не смешивая данные теста с конфигурацией и секретами.

## Главный вопрос

> Когда использовать статические данные, а когда создавать их динамически?

## Мотивация

Общая изменяемая запись делает тесты зависимыми друг от друга. Полностью случайные данные, напротив, затрудняют воспроизведение. Нужна классификация по изменяемости и владельцу.

## Теория

### Четыре вида тестовых данных

Данные в тестовом проекте различаются не форматом хранения, а тем, кто ими владеет и как долго они живут.

| Вид | Что это | Можно ли делить |
| --- | --- | --- |
| статические | неизменяемые справочники: допустимые статусы, коды | да, если действительно неизменяемы |
| динамические | создаются для конкретного запуска | нет, у каждого свой владелец |
| сценарные | выражают условие проверки | нет, принадлежат сценарию |
| зависящие от окружения | различаются между стендами | да, но приходят из валидированной конфигурации |

Последняя строка с оговоркой: данные, зависящие от окружения, допустимы, когда окружения объективно различаются, но такое различие должно приходить из валидированной конфигурации, а не из условия `if (env === "preview")` посреди теста.

### Владелец отвечает за весь цикл

Владелец данных отвечает за создание, использование и очистку. Это то же правило, что в главе 211, но здесь оно определяет, **где данные живут в проекте**.

Неизменяемый справочник можно безопасно разделять, а изменяемая сущность получает уникальный ID и одного владельца. Общими могут быть только неизменяемые вещи — данные похожи на инструмент с биркой владельца.

### `readonly` не замораживает

Здесь прячется техническая деталь, из-за которой «неизменяемый справочник» может оказаться изменяемым.

TypeScript-модификатор `readonly` запрещает часть операций при компиляции, но не замораживает объект во время выполнения. Проверено: присваивание `readonly`-полю и `push` в `readonly`-массив компилятор отклоняет, однако приведение типа его обходит, а в обычном JavaScript ограничения нет вовсе.

Поэтому для небольшого статического справочника пример дополнительно использует `Object.freeze()`: он превращает случайную мутацию в исключение во время выполнения.

Без этого общий справочник, который один тест «слегка поправил», начинает влиять на все остальные — и падать будет не тот тест, который сломал.

### Вход и ожидание должны быть независимы

Входные данные и ожидаемый результат должны быть независимыми значениями.

Если они разделяют изменяемую ссылку, подготовка запроса способна незаметно изменить ожидание и скрыть дефект:

```ts
const expected = { title: "Регрессия", labels: ["base"] };
const payload = expected;              // одна и та же ссылка
payload.labels.push("добавлено");      // ожидание тоже изменилось
// сравнение пройдёт при любом поведении системы
```

Тест станет зелёным независимо от того, что вернул сервис. Это тот же класс ошибки, что и «ожидание, взятое из ответа», — тавтология, которая выглядит как проверка.

Обратите внимание, что поверхностная копия эту проблему решает не полностью: вложенный массив останется общим. Для структур с вложенностью нужна копия и на вложенном уровне.

### Синтетические значения вместо настоящих

Секреты и персональные данные не являются тестовыми заготовками: их нельзя копировать в репозиторий или отчёты. Для сценария используются синтетические значения.

Соблазн взять «настоящий пример из базы» понятен — он гарантированно валиден. Цена этого понятна тоже: персональные данные попадают в репозиторий, историю git и отчёты CI, откуда их уже не убрать.

Синтетические значения при этом должны оставаться правдоподобными для системы: валидный формат адреса, допустимая длина, корректная контрольная сумма, если она проверяется.

### Кто что не должен хранить

Распределение ответственности легче запомнить через запреты:

- **Page Object не должен хранить бизнес-данные теста** — иначе два теста с разными данными начнут спорить за один объект;
- **конфигурация не должна генерировать сущности** — она описывает окружение, а не создаёт заказы;
- **статический JSON не должен содержать общую изменяемую учётную запись** — её изменит первый же тест, меняющий профиль.

Сценарий явно получает необходимые данные. Это распределение ответственности не требует единой структуры каталогов для каждого проекта: важно, кто владеет данными, а не в какой папке лежит файл.

### Цена каждого подхода

Статические данные проще читать, но их трудно безопасно изменять: любое изменение затрагивает всех потребителей сразу.

Динамические данные изолируют сценарий, но требуют полезных идентификаторов и воспроизводимого способа создания. Идентификатор без признака теста превращает расследование в поиск иголки, а неповторяемое создание делает падение невоспроизводимым.

Тестовые данные проходят от источника к сценарию и затем к очистке — и на каждом отрезке у них должен быть понятный владелец.

## Распространённые мифы

**Миф: `readonly` делает объект неизменяемым.**
Он действует при компиляции и обходится приведением типа. Во время выполнения нужен `Object.freeze()`.

**Миф: поверхностной копии достаточно для независимости данных.**
Вложенные массивы и объекты остаются общими. Копировать нужно и их.

**Миф: справочник можно свободно делить между тестами.**
Только если он действительно неизменяем и защищён во время выполнения.

**Миф: настоящие данные из базы — хорошая заготовка.**
Персональные данные попадут в репозиторий и отчёты, откуда их не убрать. Нужны синтетические значения.

**Миф: главное — правильная структура каталогов.**
Важно владение данными. Единой структуры, подходящей всем проектам, не существует.

## Частые вопросы

**Почему вход и ожидание нельзя держать в одном объекте?**
Изменение при подготовке запроса тихо изменит и ожидание, и сравнение пройдёт при любом поведении системы.

**Где хранить данные сценария?**
В самом сценарии или в фабрике, которую он вызывает. Не в Page Object и не в конфигурации.

**Можно ли класть учётную запись в статический JSON?**
Общую изменяемую — нет: первый же тест, меняющий профиль, сломает остальные.

**Как сделать синтетические данные пригодными?**
Сохранить формат и ограничения, которые проверяет система: длину, шаблон, контрольную сумму.

**Что делать с различиями между стендами?**
Получать их из валидированной конфигурации, а не из условий внутри теста.

## Распространённые ошибки

- Использовать одну изменяемую сущность для всего набора тестов.
- Считать любой JSON-файл безопасной тестовой заготовкой.
- Смешивать URL окружения и бизнес-поля заказа.
- Копировать реальные персональные данные.

## Краткие итоги

- Статические данные должны быть неизменяемыми во время выполнения.
- Динамические данные помогают изоляции.
- Сценарные данные выражают цель проверки.
- Каждая изменяемая сущность имеет владельца.
