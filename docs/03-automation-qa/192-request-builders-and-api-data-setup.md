# Request Builders и подготовка данных через API

## Связь с предыдущей главой

Глава 191 отделила доступ от бизнес-запросов. Следующая повторяющаяся проблема API-тестов — большие тела данных, в которых сценарий меняет только несколько полей.

## Цель главы

Использовать валидные значения по умолчанию, явные переопределения и уникальные данные без общего изменяемого состояния builder.

## Главный вопрос

Как создавать сложные тела запросов и тестовые данные без копирования деталей запроса?

## Мотивация

Копирование полного JSON в каждый тест скрывает важное отличие сценария. Один изменяемый глобальный объект, напротив, связывает тесты и делает результат зависимым от порядка.

## Теория

Request Builder создаёт валидное тело данных по умолчанию и позволяет явно изменить поля, важные для сценария. `build()` возвращает новое значение, которым тест может владеть независимо.

Валидные значения по умолчанию должны быть нейтральными и понятными. Переопределения показывают причину конкретного теста. Уникальные данные предотвращают конфликт с параллельным или повторным запуском.

Подготовка через API создаёт ресурс быстрее, чем UI, если UI не является предметом проверки. Договорённость об очистке определяет, кто и как удаляет созданные данные даже после падения проверки.

## Внутренний механизм

Builder хранит типизированную модель, методы возвращают `this` для последовательной настройки, а `build()` создаёт копию. Тест отправляет данные через API Client или fixture `request`, сохраняет идентификатор созданного ресурса и удаляет его в `finally`.

Пример создаёт данные задачи, запоминает полученный ID и выполняет очистку только в том случае, если создание завершилось успешно.

## Главная ментальная модель

Builder отвечает за форму входных данных, API создаёт серверный ресурс, а тест владеет идентификатором и очисткой созданного состояния.

## Практические примеры

- Значение `title` по умолчанию делает тело данных валидным.
- `withTitle()` показывает отличие сценария.
- Уникальный suffix может происходить из test info или контролируемого генератора.
- Очистка использует ID ответа, а не поиск по неуникальному имени.

## Automation QA

Builders полезны для заказов, пользователей и конфигураций с большим количеством обязательных полей. Для тела из двух полей обычная фабричная функция часто проще класса.

## Концептуальные границы и компромиссы

Builder не должен выполнять HTTP-запросы: иначе создание данных и построение модели становятся одной скрытой операцией. Он также не проверяет контракт ответа.

## Распространённые ошибки

- Возвращать один общий изменяемый объект.
- Скрывать важное переопределение в значениях по умолчанию.
- Использовать временную метку как единственную стратегию уникальности без необходимости.
- Выполнять запрос внутри `build()`.
- Не сохранять ID созданного ресурса.
- Выполнять очистку только после успешной проверки.

## Краткие итоги

- Builder уменьшает копирование сложных тел данных.
- Значения по умолчанию создают валидную основу.
- Переопределения показывают смысл сценария.
- Unique data защищает независимые запуски.
- Очистка следует за владельцем созданного ресурса.

## Что нужно запомнить

- `build()` должен возвращать независимое значение.
- Builder не является API Client.
- Идентификатор приходит из ответа сервера.
- Очистка размещается в `finally` или управляемой fixture.
- Простым телам данных не всегда нужен builder.
