# Проверка gRPC-ответов и негативных сценариев

## Связь с предыдущей главой

Глава 204 научила интерпретировать `ServiceError`. Полноценный тест должен также проверить успешный response и состояние service после операции.

## Цель главы

Разделить контракт message, проверки бизнес-правил и подтверждение отсутствия изменений для позитивных и негативных RPC-вызовов.

## Главный вопрос

Как проверить message contract, business result и отсутствие нежелательных побочных эффектов?

## Мотивация

Сгенерированный тип не доказывает, что server вернул правильные `title`, `priority` или коллекцию. Ожидаемый код ошибки также не доказывает, что отклонённый request не создал ресурс.

## Теория

### Три уровня проверки RPC

RPC-тест проверяет три уровня, и каждый отвечает на свой вопрос:

1. **завершение call** — вызов закончился `OK` или ожидаемым статусом отказа;
2. **содержание message** — в ответе есть обязательные поля с правильными значениями;
3. **наблюдаемое изменение состояния** — сервер действительно применил или не применил операцию.

Порядок не произволен. Читать поля ответа имеет смысл только после того, как известно, что вызов завершился успешно: иначе `response` окажется `undefined`, и падение произойдёт на обращении к свойству вместо внятного сообщения о статусе.

### Позитивный сценарий: от формы к смыслу

Успешный сценарий проверяет обязательные поля, значения и бизнес-инварианты.

```ts
const task = await tasks.create({ title, labels: ["регресс"] });

expect(task.id, "созданная задача должна получить идентификатор").toBeTruthy();
expect(task.title, "название должно сохраниться").toBe(title);
expect(task.completed, "новая задача не может быть завершённой").toBe(false);
expect(task.labels, "метки должны сохраниться").toEqual(["регресс"]);
```

Последние две проверки разного рода. `completed === false` — бизнес-инвариант: правило системы, а не то, что отправил тест. `labels` — проверка сохранения переданного. Оба нужны, но по разным причинам.

### Особенности проверки полей protobuf

Три вещи, которые отличают проверку message от проверки JSON.

**Repeated-коллекции** проверяются по предусмотренному контрактом порядку или составу. Если порядок не является контрактом, сравнивать упорядоченные массивы нельзя — сервис вправе вернуть элементы иначе.

**Присутствие `optional`-поля** проверяется отдельно от значения по умолчанию. Пустая строка и отсутствие поля — разные факты, и различить их можно только через признак присутствия.

**Enum** сравнивается с именем ожидаемого варианта, а нулевое значение не считается бизнес-выбором без явного указания в контракте.

### Негативный сценарий: одна причина и её последствия

Негативный сценарий задаёт **одну** невалидность, ожидает точный status и затем читает состояние server.

Третий шаг — то, ради чего негативный тест вообще ценен. Если отклонённый create оставил ресурс, контракт нарушен даже при правильном `INVALID_ARGUMENT`:

```ts
const error = await expectRejection(tasks.create({ title: "" }));
expect(error.code, "пустой title недопустим").toBe(status.INVALID_ARGUMENT);

const list = await tasks.list({});
expect(list.tasks, "отклонённый запрос не должен создавать задачу").toHaveLength(0);
```

Без второй половины тест подтверждает формат ответа и ничего не говорит о поведении системы.

### Когда последующее чтение нужно, а когда нет

Последующий call увеличивает время теста, но нужен там, где побочный эффект является частью риска. Не каждый read-only method требует дополнительной проверки состояния.

Практический ориентир:

| Операция | Нужно ли читать состояние |
| --- | --- |
| чтение (`Get`, `List`) | нет — побочного эффекта не предполагается |
| создание или изменение, успешный сценарий | да, если сценарий утверждает сохранение |
| создание или изменение, отказ | да — это и есть проверяемый риск |
| отказ после `DEADLINE_EXCEEDED` | да — сервер мог завершить операцию позже |

Последняя строка особенно неочевидна: истёкший срок означает, что ответ не пришёл вовремя, а не что работа не выполнена.

### Ложный успех и как его устранить

Ложный успех — тест, который проходит независимо от поведения системы. В gRPC-сценариях он возникает тремя способами:

- ожидается «любая ошибка», а приходит `UNAVAILABLE` от упавшего стенда;
- проверяется поле, которое всегда заполнено значением по умолчанию;
- ожидание берётся из того же ответа, который проверяется.

Соединение проверки response с последующим чтением состояния устраняет первый и третий случаи: чтение выполняется отдельным вызовом и подтверждает факт, независимый от проверяемого ответа.

### Чего такой тест не доказывает

Проверка структуры message через сгенерированный client отличается от полного тестирования контракта поставщика: тест наблюдает конкретный response, но не доказывает совместимость всех версий поставщика и потребителя.

Разница в предмете. Ваш тест проверяет, что **этот** стенд с **этой** версией `.proto` ведёт себя по контракту. Совместимость же — свойство пары версий, и проверяется сравнением контрактов, а не одним успешным вызовом.

Порядок проверок при этом даёт главную практическую пользу — точную диагностику: нарушенный контракт, неверное бизнес-значение и неожиданный побочный эффект видны как разные причины падения.

## Главная ментальная модель

RPC-тест проверяет три уровня: завершение call, содержание message и наблюдаемое изменение состояния server.

## Практические примеры

- Проверить поля сгенерированного выходного объекта.
- Проверить бизнес-инвариант `completed === false` для новой задачи.
- После невалидного request убедиться, что список не изменился.
- После допустимого create прочитать ресурс отдельным call.

## Концептуальные границы и компромиссы

Последующий call увеличивает время теста, но нужен там, где побочный эффект является частью риска. Не каждый read-only method требует дополнительной проверки состояния.

## Распространённые мифы

**Миф: правильный код отказа — достаточная проверка.**
Отклонённая операция могла оставить ресурс. Отсутствие побочного эффекта проверяется отдельно.

**Миф: поля ответа можно читать сразу.**
Сначала проверяется завершение вызова: иначе падение произойдёт на обращении к `undefined`.

**Миф: repeated-коллекцию всегда сравнивают по порядку.**
Только если порядок является контрактом. Иначе сравнивают состав.

**Миф: после `DEADLINE_EXCEEDED` изменений точно нет.**
Сервер мог завершить операцию позже. Если это важно, состояние читают.

**Миф: успешный тест подтверждает совместимость версий контракта.**
Он подтверждает поведение текущего стенда с текущим `.proto`.

## Частые вопросы

**В каком порядке проверять RPC-ответ?**
Завершение вызова, обязательные поля, бизнес-значения, затем при необходимости состояние сервера.

**Когда нужен дополнительный вызов для чтения состояния?**
При создании и изменении — и особенно после отказа, где побочный эффект и есть проверяемый риск.

**Как отличить бизнес-инвариант от проверки сохранения?**
Инвариант задаётся правилом системы (`completed === false`), сохранение — тем, что отправил тест.

**Почему тест проходит при упавшем стенде?**
Если ожидается «любая ошибка», `UNAVAILABLE` её удовлетворит. Нужен конкретный код.

**Что делать с полями, всегда заполненными по умолчанию?**
Не строить на них проверку: нулевое значение enum или пустая строка присутствуют независимо от поведения сервиса.

## Распространённые ошибки

- Считать сгенерированный тип проверкой во время выполнения.
- Проверять только `OK` или только отсутствие ошибки.
- Не проверять состояние после отклонённой команды.
- Сравнивать снимок всего message без причины.
- Путать наблюдение потребителя и полное управление контрактами.

## Краткие итоги

- Результат call, message и состояние являются разными уровнями.
- Бизнес-значения проверяются явно.
- Негативный сценарий подтверждает отсутствие изменений.
- Repeated- и `optional`-поля проверяются с учётом семантики protobuf.
- Последующая проверка предотвращает ложный успех.

## Что нужно запомнить

- Проверяйте наблюдаемый бизнес-результат.
- После отклонённой команды ищите побочный эффект.
- Не полагайтесь только на сгенерированный тип.
- Добавляйте последующий call, если этого требует риск сценария.
