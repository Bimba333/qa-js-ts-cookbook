# Структура HTTP-ответа

## Связь с предыдущей главой

Глава 187 разделила запрос на адрес, параметры, заголовки и тело. Ответ сервера также имеет несколько уровней, и каждый отвечает на отдельный вопрос теста.

## Цель главы

Научиться интерпретировать код состояния, заголовки и тело HTTP-ответа, не смешивая транспортный и бизнес-результат.

## Главный вопрос

Какие уровни результата нужно проверить в HTTP-ответе?

## Мотивация

Проверка только `response.ok()` может скрыть неверный код создания, неправильный формат или ошибочное бизнес-состояние. Проверка всего ответа целиком, наоборот, делает тест хрупким к несущественным заголовкам.

## Теория

### Три уровня ответа

HTTP-ответ отвечает на три последовательных вопроса: как сервер классифицировал результат, как описал сообщение и какие данные вернул.

Код состояния кратко классифицирует результат обработки запроса. Заголовки содержат метаданные. Тело переносит представление ресурса или описание ошибки.

Хорошая проверка проходит по всем трём уровням, и при падении сразу видно, какой из них нарушен.

### Семейства кодов и конкретные значения

Семейства 1xx, 2xx, 3xx, 4xx и 5xx описывают информационные ответы, успех, перенаправление, проблему запроса клиента и отказ сервера.

| Код | Обычное значение |
| --- | --- |
| 200 | успешное получение или обработка |
| 201 | ресурс создан, часто с заголовком `Location` |
| 202 | операция принята без гарантии завершения |
| 204 | успех без тела |
| 400 | запрос не соответствует контракту |
| 401 | аутентификация отсутствует или недействительна |
| 403 | клиент известен, но разрешений недостаточно |
| 404 | ресурс не найден |

Эти значения не заменяют контракт конкретного маршрута. Проверять стоит **точный** ожидаемый код, а не семейство: `expect(response.ok()).toBe(true)` пропустит и 200, и 204 — а это разные договорённости.

Особого внимания заслуживает 202: он означает, что операция принята, но не выполнена. Проверка бизнес-результата после 202 требует отдельного ожидания, а не следующей строки теста.

### Заголовки ответа: ключи приведены к нижнему регистру

Заголовки ответа содержат метаданные: `Content-Type`, `Location` созданного ресурса, политику кеширования или correlation ID. Их имена регистронезависимы.

Практическая деталь клиента: `response.headers()` возвращает объект, в котором ключи приведены к нижнему регистру. Сервер может отправить `X-Request-Id`, а читать его нужно как `headers()["x-request-id"]` — поиск по исходному написанию вернёт `undefined`.

Тест выбирает только те заголовки, которые входят в наблюдаемый контракт. `Location` после 201 проверять осмысленно — из него берётся идентификатор созданного ресурса. Проверять каждый заголовок подряд — создавать шум, который сломается при первом изменении инфраструктуры.

### Чтение тела: метод должен соответствовать формату

`response.json()` разбирает JSON, `response.text()` возвращает текст, а `response.body()` — байты. Метод чтения должен соответствовать фактическому `Content-Type`.

`json()` завершится ошибкой в трёх случаях, и сообщения у них разные:

```text
204 без тела          → Unexpected end of JSON input
200 с пустым телом    → Unexpected end of JSON input
text/plain            → ... is not valid JSON
```

Отсюда практическое правило: для 204 и других ответов без тела вызывать `json()` нельзя — используется `text()`, который вернёт пустую строку. А сообщение `is not valid JSON` почти всегда означает, что сервер вернул не то, что ожидалось, — HTML со страницей ошибки, текст прокси или пустой ответ.

### 4xx и 5xx — это нормальные ответы

Полученный 4xx или 5xx остаётся корректным HTTP-ответом и по умолчанию доступен тесту для проверки: исключения не будет, `status()` вернёт 404, `ok()` вернёт `false`, тело прочитается обычным способом.

Это ровно то поведение, которое нужно для негативных сценариев. Опция `failOnStatusCode: true` меняет его: тот же запрос выбрасывает исключение `apiRequestContext.get: 404 Not Found`. Выбор между режимами — осознанное решение, а не настройка по умолчанию.

### Транспортная ошибка — это другое

Ошибку приложения и транспортную ошибку легко перепутать, хотя лечатся они по-разному.

При транспортной ошибке клиент не получает нормальный HTTP-ответ: соединение не устанавливается, узел не найден, истекло время ожидания. Вызов выбрасывает исключение вроде `connect ECONNREFUSED 127.0.0.1:1`, и ни кода состояния, ни тела не существует.

Ошибка приложения приходит **внутри** HTTP-ответа и проверяется как ожидаемый или неожиданный результат. Различать их важно при расследовании: транспортная ошибка означает проблему со стендом, сетью или адресом, а 500 — проблему в сервисе.

### Что именно проверять

Хорошая проверка ответа выбирает точный код состояния, важные заголовки, форму тела и бизнес-значения. При падении такой тест показывает, какой уровень договорённости нарушен.

Кода состояния недостаточно для проверки бизнес-правила: 200 подтверждает, что запрос обработан, но не то, что задача создана с нужным статусом. Проверка же каждого заголовка создаёт шум. Баланс определяется публичным контрактом и диагностической ценностью поля.

## Главная ментальная модель

HTTP-ответ — три последовательных вопроса: как сервер классифицировал результат, как описал сообщение и какие данные вернул.

## Практические примеры

- 200 обычно означает успешное получение или обработку.
- 201 сообщает о создании ресурса и часто сопровождается `Location`.
- 202 означает принятие операции без гарантии её завершения.
- 204 означает успешный ответ без тела.
- 401 указывает на отсутствие или недействительность аутентификации.
- 403 означает, что известному клиенту недостаточно разрешений.

Эти значения не заменяют контракт конкретного маршрута.

## Automation QA

Хорошая проверка ответа выбирает точный код состояния, важные заголовки, форму тела и бизнес-значения. При падении такой тест показывает, какой уровень договорённости нарушен.

## Концептуальные границы и компромиссы

Кода состояния недостаточно для проверки бизнес-правила, но проверка каждого заголовка создаёт шум. Баланс определяется публичным контрактом и диагностической ценностью поля.

## Распространённые мифы

**Миф: 4xx или 5xx выбрасывают исключение.**
По умолчанию это обычный ответ: `status()` и тело доступны. Исключение даёт только `failOnStatusCode: true`.

**Миф: `ok()` достаточно для проверки успеха.**
Он покрывает всё семейство 2xx. Если контракт обещает 201, проверять нужно 201.

**Миф: `json()` можно вызывать на любом ответе.**
На 204, пустом теле или тексте он падает. Формат чтения должен соответствовать `Content-Type`.

**Миф: заголовок читается по тому имени, которое отправил сервер.**
`headers()` приводит ключи к нижнему регистру: `X-Request-Id` читается как `x-request-id`.

**Миф: 500 и недоступный сервер — примерно одно и то же.**
500 — это полученный ответ сервиса. Недоступный сервер даёт исключение без кода и тела.

## Частые вопросы

**Что проверять после 201?**
Заголовок `Location` и, если контракт это обещает, тело с представлением созданного ресурса. Идентификатор удобно брать из `Location`.

**Ответ 202 — можно ли сразу проверять результат?**
Нет. 202 означает принятие операции, а не её завершение. Нужен отдельный этап ожидания результата.

**`json()` падает с «is not valid JSON». Что это значит?**
Сервер вернул не JSON: страницу ошибки, ответ прокси или пустое тело. Посмотрите `text()` и `Content-Type`.

**Когда включать `failOnStatusCode`?**
Когда любой неуспешный код — это дефект и разбирать его отдельно не нужно. Для негативных сценариев он мешает.

**Сколько заголовков проверять?**
Только входящие в наблюдаемый контракт: `Content-Type`, `Location`, диагностический идентификатор. Остальное — шум.

## Распространённые ошибки

- Считать любой 2xx эквивалентом 200.
- Считать 5xx транспортной ошибкой.
- Вызывать `json()` для текстового или пустого ответа.
- Проверять все служебные заголовки.
- Игнорировать тело ошибки негативного сценария.
- Полагаться на порядок свойств JSON.

## Краткие итоги

- Код состояния классифицирует результат.
- Заголовки описывают ответ и связанные ресурсы.
- Тело содержит данные или ошибку.
- 4xx и 5xx можно проверять как обычные HTTP-ответы.
- Транспортные ошибки и ошибки приложения имеют разные причины.

## Что нужно запомнить

- Проверяйте уровни ответа отдельно.
- Ожидайте точный код состояния, если он входит в контракт.
- Читайте тело подходящим методом.
- Не превращайте тест в снимок всех заголовков.
- Бизнес-результат не выводится только из кода состояния.
