# Поля protobuf-сообщений

## Связь с предыдущей главой

Глава 200 выполнила unary call как единое действие. Теперь нужно понимать значения внутри request и response messages, включая значения по умолчанию и признак присутствия поля.

## Цель главы

Корректно подготовить и проверить скалярные, repeated, enum, `optional` и вложенные поля.

## Главный вопрос

Как особенности protobuf fields влияют на подготовку запроса и проверку ответа?

## Мотивация

Отсутствующее скалярное поле в proto3 часто декодируется в значение по умолчанию. Поэтому `false`, `0` или пустая строка не всегда доказывают, что отправитель явно передал поле. Присутствие `optional`-поля и обычное значение по умолчанию отвечают на разные вопросы.

## Теория

### Виды полей и что они означают

Скалярные поля хранят простые значения: строки, числа и boolean. Repeated field представляет последовательность значений. Вложенное message имеет собственный набор полей и отдельное представление отсутствия в сгенерированном API.

Enum ограничивает набор именованных вариантов, но его нулевое значение обычно обозначает неопределённое состояние. По соглашению его называют `*_UNSPECIFIED`, и это не бизнес-выбор, а признак «значение не задано».

### Значения по умолчанию скрывают отсутствие

Это главная особенность proto3, с которой сталкивается каждый тест. Обычное скалярное поле без признака присутствия при чтении получает значение по умолчанию — и отличить «не передали» от «передали пустое» невозможно.

Проверено на реальном ответе при настройках loader этого модуля. Запрос отправил только `title`, а десериализованный объект выглядит так:

```json
{
  "id": "t-1",
  "title": "Минимум",
  "labels": [],
  "priority": "PRIORITY_UNSPECIFIED",
  "owner": null,
  "completed": false,
  "estimate": 0
}
```

Ни одно из этих полей сервер не отправлял. `labels` стал пустым массивом, число — нулём, boolean — `false`, enum — нулевым вариантом.

### Настройки loader определяют форму объекта

Loader этого модуля включает `defaults`, `arrays`, `objects`, `oneofs` и строковое представление enum. Именно поэтому выходной объект содержит пустые repeated-коллекции и значения скалярных полей по умолчанию.

| Настройка | Что даёт | Видно в примере выше |
| --- | --- | --- |
| `defaults` | значения по умолчанию у скалярных полей | `estimate: 0`, `completed: false` |
| `arrays` | пустой массив вместо отсутствия | `labels: []` |
| `objects` | предсказуемое представление вложенных | `owner: null` |
| `enums: String` | имя варианта вместо числа | `"PRIORITY_UNSPECIFIED"` |
| `oneofs` | признак присутствия `optional` | поле `_description` |

Эти настройки — часть контракта тестового кода. Тест, написанный в расчёте на `labels: []`, сломается, если loader настроят иначе и отсутствующая коллекция станет `undefined`.

Обратите внимание на асимметрию: вложенное message при отсутствии даёт `null`, а не пустой объект. Проверка `expect(response.owner.id)` на такой ответ упадёт с ошибкой обращения к `null`, а не с внятным сообщением о контракте.

### Как `optional` возвращает признак присутствия

`optional` в современном proto3 сохраняет признак присутствия: декодер может различить отсутствие поля и переданное значение. В сгенерированном API он выражается служебным `oneof`.

Механика видна на двух вызовах:

```ts
// поле не передано
response._description   // undefined
response.description    // undefined

// передана пустая строка
response._description   // "description"  ← имя присутствующего поля
response.description    // ""
```

Служебное поле `_description` содержит **имя** присутствующего поля, а не булево значение. Проверять присутствие следует именно по нему: `description === ""` не отличит переданную пустую строку от отсутствия.

### Развитие контракта на уровне полей

Изменение типа поля или значения enum требует анализа совместимости.

Добавление нового значения enum может быть совместимо на уровне protobuf: старый декодер примет неизвестное число. Но старый прикладной код должен корректно обработать неизвестный вариант — иначе `switch` без ветви по умолчанию молча провалится, а при строковом представлении тест сравнит имя, которого не знает.

Практический вывод для теста: проверяя enum, сравнивайте с ожидаемым именем варианта, а не полагайтесь на то, что список исчерпывающий.

### Что проверять в message

Тест выбирает поля, важные для сценария, и учитывает параметры loader. Снимок всего message часто хрупок: он включает значения по умолчанию, которые сервис не задавал, и ломается при добавлении любого нового поля.

Точечные проверки лучше показывают нарушенное правило:

- **repeated** — проверить состав и, если порядок является контрактом, порядок;
- **enum** — сравнить с именем ожидаемого варианта, не считая нулевое значение бизнес-выбором;
- **optional** — отличить присутствие от значения по умолчанию через признак;
- **вложенное message** — проверять его поля отдельно, предварительно убедившись, что оно не `null`.

### Чего сгенерированные типы не гарантируют

Сгенерированные типы помогают использовать поля, но не доказывают допустимость бизнес-значений. Тип `string` для `title` не мешает сервису вернуть пустую строку там, где контракт обещает непустую.

Полная проверка совместимости protobuf требует сравнения версий контрактов и не сводится к одной проверке response: одиночный ответ говорит о текущем поведении стенда, а не о том, поймут ли друг друга участники с разными версиями `.proto`.

## Концептуальные границы и компромиссы

## Распространённые мифы

**Миф: пустое поле в ответе означает, что сервер его не отправлял.**
В proto3 обычное поле получает значение по умолчанию. Отличить отсутствие можно только через признак присутствия у `optional`.

**Миф: отсутствующее вложенное message придёт пустым объектом.**
Оно приходит как `null`. Обращение к его полю даст ошибку `null`, а не понятное сообщение о контракте.

**Миф: `_description` — булев признак.**
Оно содержит имя присутствующего поля. Проверяется на наличие, а не на `true`.

**Миф: нулевое значение enum — обычный вариант выбора.**
По соглашению это «не задано». Считать его бизнес-значением можно только если так сказано в контракте.

**Миф: снимок всего message — надёжная проверка.**
Он включает значения по умолчанию и ломается от любого нового поля. Точечные проверки диагностичнее.

## Частые вопросы

**Как отличить пустую строку от отсутствия поля?**
Только через `optional` и его признак присутствия. Обычное поле такой информации не несёт.

**Почему `labels` пришёл пустым массивом, а не `undefined`?**
Так настроен loader: параметр `arrays` подставляет пустую коллекцию. При другой настройке поле будет отсутствовать.

**Как проверять enum?**
Сравнением с именем ожидаемого варианта. При `enums: String` в объект приходит имя, а не число.

**Безопасно ли добавить новое значение enum?**
На уровне protobuf обычно да. Опасность в прикладном коде, который не обработает неизвестный вариант.

**Доказывает ли успешный тест совместимость контракта?**
Нет. Он подтверждает поведение текущего стенда, а не согласие разных версий `.proto`.

## Распространённые ошибки

- Путать отсутствие поля и значение по умолчанию.
- Автоматически считать нулевое значение enum допустимым бизнес-значением.
- Игнорировать порядок repeated field, если он входит в контракт.
- Проверять вложенное message как непрозрачный объект.
- Менять тип поля без анализа совместимости protobuf.

## Краткие итоги

- Скалярные поля имеют значения protobuf по умолчанию.
- Repeated-поля представляют коллекции.
- Нулевое значение enum требует осознанной семантики.
- `Optional`-поля сохраняют признак присутствия.
- Вложенные messages проверяются по собственной структуре.

## Что нужно запомнить

- Читайте параметры loader вместе с проверками.
- Не смешивайте отсутствие поля и пустое значение.
- Проверяйте важные вложенные поля явно.
- Учитывайте неизвестные значения enum при развитии контракта.
