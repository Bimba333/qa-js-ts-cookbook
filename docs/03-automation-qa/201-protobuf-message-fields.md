# Поля protobuf-сообщений

## Связь с предыдущей главой

Глава 200 выполнила unary call как единое действие. Теперь нужно понимать значения внутри request и response messages, включая значения по умолчанию и признак присутствия поля.

## Цель главы

Корректно подготовить и проверить скалярные, repeated, enum, `optional` и вложенные поля.

## Главный вопрос

Как особенности protobuf fields влияют на подготовку запроса и проверку ответа?

## Мотивация

Отсутствующее скалярное поле в proto3 часто декодируется в значение по умолчанию. Поэтому `false`, `0` или пустая строка не всегда доказывают, что отправитель явно передал поле. Присутствие `optional`-поля и обычное значение по умолчанию отвечают на разные вопросы.

## Теория

Скалярные поля хранят простые значения: строки, числа и boolean. Repeated field представляет последовательность значений. Enum ограничивает набор именованных вариантов, но его нулевое значение обычно обозначает неопределённое состояние.

`optional` в современном proto3 сохраняет признак присутствия: декодер может различить отсутствие поля и переданное значение. Обычное скалярное поле без такого признака при чтении получает значение по умолчанию. Вложенное message имеет собственный набор полей и отдельное представление отсутствия в сгенерированном API.

Изменение типа поля или значения enum требует анализа совместимости. Добавление нового значения enum может быть совместимо на уровне protobuf, но старый прикладной код должен корректно обработать неизвестный вариант.

## Внутренний механизм

Loader этого модуля включает `defaults`, `arrays`, `objects`, `oneofs` и строковое представление enum. Поэтому выходной объект содержит пустые repeated-коллекции и значения скалярных полей по умолчанию. `Optional`-поле дополнительно имеет признак присутствия, сгенерированный из служебного `oneof`.

## Главная ментальная модель

Поле имеет не только тип TypeScript, но и семантику protobuf: номер, значение по умолчанию, признак присутствия и правила развития контракта.

## Практические примеры

- Проверить порядок и состав repeated-поля `labels`.
- Не считать нулевое значение enum бизнес-выбором без контракта.
- Отличить отсутствующее `optional`-поле `description` от пустой строки.
- Проверить поля вложенного `owner` отдельно.

## Automation QA

Тест выбирает поля, важные для сценария, и учитывает параметры loader. Снимок всего message часто хрупок; точечные проверки лучше показывают нарушенное правило.

## Концептуальные границы и компромиссы

Сгенерированные типы помогают использовать поля, но не доказывают допустимость бизнес-значений. Полная проверка совместимости protobuf требует сравнения версий контрактов и не сводится к одной проверке response.

## Распространённые ошибки

- Путать отсутствие поля и значение по умолчанию.
- Автоматически считать нулевое значение enum допустимым бизнес-значением.
- Игнорировать порядок repeated field, если он входит в контракт.
- Проверять вложенное message как непрозрачный объект.
- Менять тип поля без анализа совместимости protobuf.

## Краткие итоги

- Скалярные поля имеют значения protobuf по умолчанию.
- Repeated-поля представляют коллекции.
- Нулевое значение enum требует осознанной семантики.
- `Optional`-поля сохраняют признак присутствия.
- Вложенные messages проверяются по собственной структуре.

## Что нужно запомнить

- Читайте параметры loader вместе с проверками.
- Не смешивайте отсутствие поля и пустое значение.
- Проверяйте важные вложенные поля явно.
- Учитывайте неизвестные значения enum при развитии контракта.
