# Builders, factories и уникальные данные

## Связь с предыдущей главой

Глава 219 разделила категории тестовых данных. Для динамических сценарных данных повторение больших объектных литералов быстро скрывает важное отличие конкретного теста.

## Цель главы

Создавать валидные данные через Factory или Builder, сохраняя безопасные значения по умолчанию, точечные overrides, уникальность и воспроизводимость.

## Главный вопрос

> Как создавать валидные данные с минимальными изменениями для конкретного сценария?

## Мотивация

Если каждый тест собирает объект вручную, изменение обязательного поля затрагивает десятки файлов. Если значения по умолчанию случайны и скрыты, падение трудно повторить.

## Теория

Factory возвращает готовое значение из значений по умолчанию и overrides. Builder полезен, когда объект собирается несколькими осмысленными шагами. Оба механизма должны создавать валидный объект по умолчанию и оставлять в тесте только важные отличия.

Уникальное значение предотвращает коллизию, но должно оставаться диагностируемым. Seed или явный префикс позволяет воспроизвести последовательность. В примере seed учитывает имя проекта, индекс повтора и индекс worker. Значения по умолчанию не должны содержать общие изменяемые ID или зависеть от порядка всего набора тестов. Один `Date.now()` или `Math.random()` не объясняет источник значения и сам по себе не образует воспроизводимую стратегию.

## Внутренний механизм

Factory хранит локальную последовательность одного сценария. Каждый вызов создаёт новый объект, затем применяет типизированные overrides. Исходные значения по умолчанию и объект overrides вызывающего кода не изменяются.

## Главная ментальная модель

Factory — форма для валидной заготовки, а overrides — только изменения, важные текущему сценарию.

## Automation QA

Builder удобен для тела запроса, записей базы данных и сложных тестовых заготовок. Builder и Factory создают данные, но не отправляют HTTP-запрос, не выполняют проверки и не владеют очисткой — эти побочные эффекты остаются видимыми.

## Компромиссы

Factory компактнее для простой формы. Builder выразительнее для пошаговых вариантов, но лишний fluent API может скрыть обычный объект без реальной пользы. Не каждой модели нужна отдельная фабрика или построитель.

## Распространённые ошибки

- Возвращать один изменяемый объект из Factory.
- Скрывать сетевой запрос внутри `build()`.
- Использовать случайность без seed или диагностического ID.
- Разрешать overrides, создающие заведомо невалидный сценарий по умолчанию.

## Краткие итоги

- Значения по умолчанию создают валидную базовую сущность.
- Overrides показывают цель сценария.
- Factory возвращает новый объект при каждом вызове.
- Уникальность и воспроизводимость проектируются вместе.
