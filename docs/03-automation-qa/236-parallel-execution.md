# Parallel execution

## Связь с предыдущей главой

Глава 235 ввела процессы workers и владение ресурсами. Теперь можно сравнить уровни параллельного выполнения.

## Цель главы

Различать параллельное выполнение файлов и отдельных тестов, не создавая зависимости от порядка и общего изменяемого состояния.

## Главный вопрос

> Как ускорить suite, сохраняя isolation и предсказуемость результатов?

## Мотивация

Параллельный запуск часто не создаёт дефект, а проявляет скрытый конфликт ресурсов. Последовательный режим может временно скрыть проблему ценой скорости.

## Теория

По умолчанию Playwright распределяет файлы с тестами между workers, а тесты внутри файла выполняются последовательно. `fullyParallel` разрешает параллельное выполнение отдельных тестов во всём project. `test.describe.configure({ mode: "parallel" })` включает его для одной группы. В `mode: "serial"` тесты выполняются последовательно: после падения следующие тесты группы пропускаются, а при retry вся группа повторяется вместе. Это узкая граница последовательного рабочего процесса, а не исправление зависимости обычных тестов.

Число workers задаёт доступное количество процессов, но не режим каждого теста. Projects, retries и повторения набора независимо увеличивают число выполнений. Независимые тесты не полагаются на порядок, используют собственные ресурсы и выполняют точную очистку.

## Внутренний механизм

```mermaid
flowchart LR
    S[Набор тестов] --> F[Файлы между workers]
    F --> T[Тесты внутри файла]
    T -->|По умолчанию| Q[Последовательно]
    T -->|fullyParallel / parallel mode| P[Параллельно]
    P --> O[Ресурсы с разными владельцами]
```

## Главная ментальная модель

Parallel execution меняет расписание, но не должен менять корректность.

## Практический пример

```text
examples/03-automation-qa/chapter-236/01-parallel-isolation.stability.ts
```

Два теста используют собственные независимые файлы и не зависят от очередности.

## Automation QA

UI-, API- и database-сценарии получают уникальные идентификаторы, учётные записи или схемы. Баланс длительности помогает распределять файлы, но не оправдывает объединение зависимых тестов.

## Компромиссы

Больший параллелизм сокращает общее время запуска и увеличивает нагрузку на внешние системы. Serial mode допустим для действительно последовательного рабочего процесса, но не заменяет независимость обычных тестов.

## Распространённые ошибки

- Считать `fullyParallel` механизмом изоляции.
- Хранить состояние предыдущего теста в переменной модуля.
- Исправлять конфликт через `workers: 1`.
- Удалять общий каталог вместо собственного файла.

## Краткие итоги

- Файлы и отдельные тесты имеют разные уровни параллелизма.
- Число workers не создаёт изоляцию ресурсов.
- Последовательная группа имеет явную стоимость и семантику.
- Параллельный набор требует независимых тестов.
