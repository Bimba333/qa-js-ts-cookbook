# Как пользоваться курсом

## Цели обучения

После изучения этой главы вы будете понимать:

* как проходить курс последовательно и без пропусков;
* почему порядок глав влияет на качество понимания;
* как читать теоретические разделы;
* как работать с примерами кода;
* как выполнять практические задания;
* когда открывать решения;
* как использовать `playground/`;
* как вести личные заметки;
* как возвращаться к сложным темам;
* какие ошибки чаще всего мешают обучению;
* как Automation QA Engineer может связывать каждую тему с рабочими задачами.

В предыдущей главе была описана цель курса и его общая логика. Эта глава объясняет не что изучать, а как изучать.

---

## Мотивация

Технический курс можно пройти формально.

Можно читать главы подряд, запускать часть примеров, иногда смотреть решения и двигаться дальше. Внешне это будет похоже на обучение. Но результат окажется слабым: темы будут узнаваться при чтении, но не применяться в реальном коде.

Для Automation QA это особенно опасно. В автотестах ошибка редко выглядит как чистая учебная задача. Она может проявляться как нестабильный тест, неверная проверка API-ответа, неожиданное изменение тестовых данных, неправильная работа fixture или проблема с асинхронным ожиданием.

Если тема была только прочитана, но не встроена в мышление, инженер узнает знакомые слова, но не сможет быстро найти причину.

Эффективное прохождение курса требует цикла:

```text
Прочитать
│
▼
Запустить
│
▼
Объяснить
│
▼
Изменить
│
▼
Ошибиться
│
▼
Исправить
│
▼
Применить в QA-контексте
```

Этот цикл важнее скорости. Быстро прочитанная глава не равна освоенной теме. Освоенная тема — это тема, которую можно объяснить, применить и использовать при анализе ошибки.

## Теория

### Как читать главы

Каждая глава курса устроена как последовательное объяснение механизма.

Читать ее нужно не как справочник, где можно сразу перейти к нужной команде, а как техническое рассуждение. В начале главы обычно формулируется проблема. Затем объясняется, почему появился механизм, как он работает внутри, как выглядит в коде и где применяется в Automation QA.

Правильный способ чтения:

1. Прочитать раздел полностью.
2. Остановиться после каждого кода или схемы.
3. Сформулировать своими словами, что произошло.
4. Проверить, можете ли вы объяснить не только результат, но и причину результата.
5. Если объяснение не получается, вернуться к предыдущему абзацу.

Цель чтения — не пройти страницу. Цель — построить рабочую модель.

Рабочая модель — это короткое внутреннее объяснение, которое помогает предсказывать поведение кода. Например, для объектов это может быть модель "переменная хранит ссылку, объект находится отдельно". Для асинхронности это будет модель очередей и выполнения задач. Подробно эти темы будут разобраны в соответствующих главах.

### Почему порядок глав важен

Порядок глав не является декоративным.

Каждая тема опирается на предыдущие. Если пропустить ранний механизм, следующая тема может выглядеть сложнее, чем она есть на самом деле.

Например, когда курс дойдет до функций, уже понадобится понимание переменных и областей видимости. Когда появятся объекты, понадобится понимание значений и ссылок. Когда начнется асинхронность, понадобится понимание функций, ошибок и порядка выполнения кода.

Зависимость можно представить так:

```text
Тема A
│
├── дает термины
├── дает модель
└── дает ограничения
    │
    ▼
Тема B
│
├── использует термины темы A
├── расширяет модель темы A
└── добавляет новый механизм
    │
    ▼
Тема C
```

Если тема A пропущена, тема B становится набором правил без причины. Если тема B изучена поверхностно, тема C начинает казаться магией.

Поэтому в этом курсе нежелательно перескакивать через главы. Допустимо быстро повторить знакомую тему, но не стоит пропускать ее полностью. Даже в знакомой теме может быть внутренняя модель, которая позже понадобится в QA-задачах.

### Что не даст этот курс

Курс не обещает мгновенного результата.

Он не даст:

* готовые ответы на все вопросы собеседований;
* набор фраз для запоминания;
* универсальный шаблон фреймворка для любого проекта;
* замену документации Playwright, Node.js или TypeScript;
* автоматическое понимание без самостоятельной практики;
* гарантию, что код получится правильным с первой попытки.

Это важно проговорить явно.

Инженерное обучение требует трения. Иногда пример придется запустить несколько раз. Иногда решение будет отличаться от вашего. Иногда тема станет понятной только после возвращения к ней через несколько глав.

Это нормальная часть процесса. Ошибка в обучении — не сам факт непонимания. Ошибка — двигаться дальше, не разобрав, какая модель оказалась неверной.

### Как работать с примерами кода

Пример кода в курсе нужен не для копирования. Он нужен для проверки модели.

Работать с примером следует в четыре шага:

```text
Прочитать код
│
▼
Предсказать результат
│
▼
Запустить пример
│
▼
Объяснить расхождение
```

Самая важная часть — предсказание до запуска.

Если сразу запустить код, вы увидите ответ, но не проверите собственное понимание. Если сначала предсказать результат, запуск превращается в эксперимент.

Пример:

```javascript
const firstUser = {
  name: 'Anna'
};

const secondUser = firstUser;

secondUser.name = 'Maria';

console.log(firstUser.name);
```

Перед запуском нужно ответить:

1. Что будет выведено?
2. Одинаковые или разные объекты используют `firstUser` и `secondUser`?
3. Какая модель объясняет результат?

После запуска нужно сравнить ожидание с фактом. Если ожидание совпало, полезно все равно объяснить причину. Если не совпало, нужно найти ошибку в модели, а не просто запомнить правильный вывод.

### Как изменять примеры

Минимальный пример объясняет одну идею. После запуска его полезно изменить.

Изменение должно быть небольшим:

* переименовать переменную;
* заменить `const` на `let`;
* добавить второе свойство объекта;
* вывести промежуточное значение;
* убрать одну строку и посмотреть, что изменится;
* намеренно вызвать ошибку и прочитать сообщение.

Небольшое изменение помогает увидеть границы механизма.

Плохой подход — сразу превращать учебный пример в большой фрагмент рабочего проекта. В таком коде появляется слишком много факторов, и становится непонятно, что именно вы изучаете.

### Как выполнять практику

Практика существует для проверки понимания.

Она состоит из разных типов заданий:

* вопросы на понимание;
* анализ кода;
* написание кода;
* поиск ошибок;
* QA-задачи;
* мини-проект.

Эти типы проверяют разные навыки.

Вопросы показывают, можете ли вы объяснить тему словами. Анализ кода проверяет способность предсказывать поведение программы. Написание кода проверяет применение механизма. Поиск ошибок тренирует диагностику. QA-задачи связывают тему с автотестами. Мини-проект собирает несколько идей в небольшую систему.

Практику нужно выполнять без решений.

Допустимо вернуться к главе, перечитать теорию, снова запустить пример. Но решение нужно открыть только после собственной попытки.

### Когда читать решения

Решения нужны не для того, чтобы узнать "правильный ответ". Они нужны для сравнения мышления.

Открывать решение стоит, когда выполнены три условия:

1. Вы уже дали собственный ответ.
2. Вы можете объяснить, почему выбрали именно его.
3. Вы отметили места, в которых сомневаетесь.

После открытия решения нужно сравнить:

* совпал ли результат;
* совпала ли причина;
* не пропущен ли важный механизм;
* нет ли более простого способа;
* нет ли QA-риска, который вы не заметили.

Если ваш ответ отличается от решения, это не всегда означает, что он неправильный. Иногда существует несколько корректных вариантов. Но объяснение должно быть строгим: код должен работать, механизм должен быть понятен, побочные эффекты должны быть учтены.

### Как использовать playground

`playground/` — это место для экспериментов.

Его задача — отделить учебные проверки от текста главы и от будущих проектных примеров. В `playground/` можно создавать временные файлы, запускать небольшие фрагменты кода, проверять гипотезы и намеренно ломать примеры.

Рабочий цикл может выглядеть так:

```text
Глава
│
├── пример из текста
│
▼
playground/
│
├── копия примера
├── маленькое изменение
├── запуск
└── заметка о результате
```

В `playground/` полезно проверять только одну гипотезу за раз.

Например:

* что будет, если заменить `const` на `let`;
* что будет, если передать объект в функцию;
* что будет, если убрать `await`;
* что будет, если API-ответ не содержит ожидаемого поля;
* что будет, если helper изменит входной объект.

Не стоит превращать `playground/` в архив всего курса. Для постоянных выводов лучше использовать личные заметки.

### Как вести личные заметки

Личные заметки должны фиксировать не текст главы, а изменение понимания.

Неэффективная заметка:

```text
const нельзя переназначить.
```

Более полезная заметка:

```text
const запрещает переназначить binding.
Если binding хранит ссылку на объект, свойства объекта могут изменяться.
Риск для QA: helper может изменить общий объект тестовых данных.
```

Хорошая заметка содержит:

* короткое правило;
* объяснение причины;
* минимальный пример;
* типичную ошибку;
* связь с Automation QA.

Шаблон заметки:

```text
Тема:

Что это:

Почему существует:

Как работает внутри:

Минимальный пример:

Распространённая ошибка:

Где встречается в Automation QA:
```

Такой формат помогает не превращать заметки в копию книги. Он заставляет выделить механизм.

### Как возвращаться к сложным темам

Сложную тему не всегда нужно понять за один подход.

Некоторые механизмы становятся яснее после следующих глав. Например, область видимости проще понять после нескольких примеров с функциями. Асинхронность проще понять после практики с Promise. Типы TypeScript проще воспринимать, когда уже есть опыт с реальными объектами и API-ответами.

Возврат к теме должен быть управляемым.

```text
Непонимание
│
├── отметить конкретный вопрос
├── продолжить до ближайшей связанной темы
├── вернуться к исходной главе
└── переписать объяснение своими словами
```

Не нужно писать "я не понял JavaScript". Это слишком широкая формулировка.

Лучше написать:

```text
Я не понимаю, почему изменение объекта через одну переменную видно через другую.
```

Такой вопрос можно проверить примером, схемой и задачей. Чем точнее сформулирована трудность, тем легче ее закрыть.

## Внутренний механизм обучения

Обучение в этом курсе можно описать как цикл обратной связи.

Сначала у читателя есть ожидание. Затем он читает объяснение и строит модель. После этого запускает код или выполняет задачу. Результат либо подтверждает модель, либо показывает ошибку. Ошибка не является проблемой, если она разобрана.

```text
Ожидание
│
▼
Модель
│
▼
Проверка
│
├── результат совпал ─────► закрепить модель
│
└── результат не совпал ─► найти неверное предположение
                            │
                            ▼
                         обновить модель
```

Так работает не только обучение. Так же устроена диагностика дефектов в автоматизации.

Например, тест ожидал один результат, система вернула другой. Инженер строит гипотезу, проверяет ее логами, локальным запуском, изменением данных или отдельным запросом. Затем уточняет модель системы.

Поэтому практика курса одновременно тренирует два навыка:

* понимание JavaScript и TypeScript;
* инженерную диагностику.

Внутренний механизм эффективного обучения состоит из трех действий:

1. Предсказать.
2. Проверить.
3. Объяснить.

Если пропустить предсказание, обучение превращается в наблюдение. Если пропустить проверку, модель может остаться неверной. Если пропустить объяснение, правильный результат не закрепляется.

## Ментальная модель

Представьте обучение как отладку собственной модели.

В обычной отладке вы проверяете программу. В обучении вы проверяете то, как представляете работу программы.

```text
Код
│
├── выполняется в runtime
│
▼
Результат

Модель в голове
│
├── предсказывает выполнение
│
▼
Ожидание
```

Если результат и ожидание совпадают, модель может быть правильной. Если не совпадают, нужно искать расхождение.

Важно: совпадение результата не всегда доказывает понимание. Можно угадать. Поэтому после каждого примера нужно задавать вопрос:

> Почему это работает именно так?

Если ответ сводится к "потому что так написано в JavaScript", модель еще слабая. Если ответ объясняет связь между кодом, памятью, порядком выполнения или типами, модель становится рабочей.

## Примеры кода

В этой главе код используется как материал для учебного процесса. Цель примеров — показать, как проверять собственное понимание.

### Пример 1. Предсказание перед запуском

Сначала прочитайте код и предскажите результат.

```javascript
let attemptCount = 1;

function increaseAttemptCount() {
  attemptCount = attemptCount + 1;
}

increaseAttemptCount();
increaseAttemptCount();

console.log(attemptCount);
```

Ожидаемый результат:

```text
3
```

Что произошло:

Переменная `attemptCount` была создана со значением `1`. Каждый вызов функции увеличил ее на `1`. После двух вызовов значение стало `3`.

Почему этот пример полезен:

Он простой, но показывает важный учебный прием. До запуска можно предсказать результат, затем проверить его и объяснить порядок действий.

Последовательность выполнения:

```text
attemptCount = 1
│
▼
increaseAttemptCount()
│
▼
attemptCount = 2
│
▼
increaseAttemptCount()
│
▼
attemptCount = 3
```

### Пример 2. Маленькое изменение примера

Теперь изменим пример так, чтобы функция возвращала новое значение.

```javascript
let attemptCount = 1;

function getNextAttemptCount() {
  return attemptCount + 1;
}

const nextAttemptCount = getNextAttemptCount();

console.log(attemptCount);
console.log(nextAttemptCount);
```

Результат:

```text
1
2
```

Что произошло:

Функция посчитала новое значение и вернула его, но не изменила переменную `attemptCount`. Поэтому исходное значение осталось `1`, а `nextAttemptCount` получил результат вычисления.

Почему это важно:

Маленькое изменение показывает разницу между изменением состояния и вычислением нового значения. В тестовых helper-функциях это принципиально: функция может менять входные данные, а может возвращать новые данные без побочного эффекта.

### Пример 3. QA-контекст

Рассмотрим небольшой helper для тестовых данных.

```javascript
function buildUserEmail(userName) {
  return `${userName}@example.com`;
}

const email = buildUserEmail('qa');

console.log(email);
```

Результат:

```text
qa@example.com
```

Этот пример не требует знания сложных механизмов. Но с ним можно работать правильно:

1. Предсказать результат.
2. Запустить код.
3. Изменить входное значение.
4. Проверить, что функция не меняет внешнее состояние.
5. Записать, где такая функция может использоваться в тестах.

В Automation QA такой helper может применяться при подготовке тестового пользователя. Даже простой пример нужно связывать с реальной задачей, иначе он остается абстрактным.

## Типичные ошибки

### Ошибка 1. Читать без запуска кода

Неправильный подход:

```text
Прочитать пример
│
▼
Понять "примерно"
│
▼
Перейти дальше
```

Что произошло:

Код кажется понятным, пока его не нужно изменить или объяснить.

Почему это произошло:

Чтение создает ощущение узнавания. Запуск и изменение примера проверяют реальное понимание.

Исправленный вариант:

```text
Прочитать пример
│
▼
Предсказать результат
│
▼
Запустить
│
▼
Изменить одну деталь
│
▼
Объяснить новый результат
```

### Ошибка 2. Открывать решения слишком рано

Неправильный подход:

```text
Задание кажется сложным
│
▼
Открыть решение
│
▼
Узнать правильный ответ
```

Что произошло:

Решение заменило самостоятельное рассуждение.

Почему это произошло:

Мозг получил готовую структуру ответа и не проверил собственную модель.

Исправленный вариант:

```text
Сделать попытку
│
▼
Записать сомнения
│
▼
Сравнить с решением
│
▼
Найти отличие в механизме
```

### Ошибка 3. Делать слишком большие эксперименты

Неправильный код для учебного эксперимента:

```javascript
function prepareUserAndSendRequestAndCheckDatabase(user, apiClient, database) {
  user.email = `${Date.now()}@example.com`;
  apiClient.createUser(user);
  database.findUserByEmail(user.email);
}
```

Что произошло:

В одном фрагменте смешаны изменение объекта, генерация данных, API-вызов и работа с базой данных.

Почему это произошло:

Учебная гипотеза не была ограничена. Непонятно, какой механизм проверяется.

Исправленный вариант:

```javascript
function updateUserEmail(user, newEmail) {
  user.email = newEmail;
}
```

Теперь пример проверяет одну идею: функция изменяет объект, который получила на вход.

### Ошибка 4. Вести заметки как конспект текста

Неправильная заметка:

```text
В главе написано, что примеры нужно запускать и решения смотреть после практики.
```

Что произошло:

Заметка повторяет текст, но не помогает применить материал.

Почему это произошло:

В заметке нет механизма, ошибки и личного вывода.

Исправленный вариант:

```text
Перед запуском примера я должен записать ожидаемый результат.
Если результат отличается, фиксирую неверное предположение.
Это похоже на анализ flaky-теста: ожидание, факт, гипотеза, проверка.
```

### Ошибка 5. Пропускать QA-связь

Неправильный подход:

```text
Выучить тему как JavaScript-синтаксис.
Не задавать вопрос, где это встретится в автотестах.
```

Что произошло:

Знание остается учебным и плохо переносится в рабочий код.

Почему это произошло:

Тема не была связана с реальной задачей Automation QA.

Исправленный подход:

После каждой главы записывать один пример применения:

```text
Тема: функции
QA-применение: helper для создания тестовых данных.

Тема: объекты
QA-применение: API response body.

Тема: Promise
QA-применение: ожидание сетевого запроса или действия браузера.
```

## Практическое использование

Для каждой главы используйте один и тот же рабочий процесс.

```text
1. Прочитать цели обучения
2. Прочитать мотивацию
3. Разобрать теорию
4. Запустить примеры
5. Изменить примеры
6. Выполнить практику
7. Сравнить с решениями
8. Записать личные выводы
9. Связать тему с QA-задачей
```

Такой процесс может казаться медленным в начале. Но он снижает количество возвратов позже. Чем точнее построены ранние модели, тем проще изучать сложные темы.

Минимальный формат личного результата после главы:

```text
Глава:

Главная идея:

Механизм:

Пример, который я запустил:

Ошибка, которую я понял:

QA-применение:

Что нужно повторить:
```

Если после главы этот блок заполнить невозможно, тема еще не освоена. Это не проблема. Это сигнал вернуться к нужному месту.

Для сложных тем полезно использовать интервальное повторение:

```text
День 1  ──► прочитать и выполнить практику
День 2  ──► повторить примеры без подсказки
День 7  ──► решить 1-2 задания заново
День 14 ──► найти применение в QA-коде
```

Повторение должно быть активным. Недостаточно перечитать текст. Нужно снова предсказать результат, написать код или объяснить механизм.

## Использование в Automation QA

Automation QA Engineer должен проходить этот курс с постоянным вопросом:

> Как эта тема проявится в тестовом фреймворке?

Это не означает, что каждый пример нужно превращать в Playwright-тест. На ранних главах это только усложнит обучение. Но каждую тему нужно связывать с одним практическим контекстом.

Примеры связей:

```text
Переменные
│
└── хранение URL, токенов, тестовых данных

Функции
│
└── helpers, builders, custom assertions

Объекты
│
└── API responses, fixtures, configuration

Массивы
│
└── списки элементов, наборы тестовых данных

Асинхронность
│
└── Playwright actions, API calls, database queries
```

При выполнении практики полезно добавлять QA-вопросы:

* где этот механизм может сломать тест;
* как эта тема влияет на читаемость framework;
* какой helper можно построить на этой идее;
* какие данные могут измениться неожиданно;
* какую ошибку будет сложно диагностировать без этой темы.

Например, если глава изучает изменение объектов, QA-вопрос может быть таким:

```text
Может ли helper изменить общий объект тестовых данных?
Если да, какой тест начнет падать и почему?
```

Если глава изучает асинхронность:

```text
Есть ли действие, которое тест не дождался?
Что именно возвращает Promise?
Где нужно поставить await?
```

Если глава изучает TypeScript:

```text
Что проверяется компилятором?
Что остается непроверенным в runtime?
Нужна ли дополнительная проверка ответа API?
```

Такой подход готовит к архитектурным главам. Когда курс перейдет к Playwright, API, gRPC, PostgreSQL и framework architecture, темы языка уже не будут отдельной теорией. Они станут инструментами для проектирования.

## Итоги

Эффективное обучение в этом курсе строится на активной проверке понимания.

Недостаточно прочитать главу. Нужно предсказать поведение кода, запустить пример, изменить его, объяснить результат, выполнить практику и только после этого сравнить свой ответ с решением.

Порядок глав важен, потому что каждая новая тема использует модели, построенные ранее. Пропуск ранних тем создает пробелы, которые позже проявляются в функциях, объектах, асинхронности, TypeScript и архитектуре автотестов.

`playground/` используется для небольших экспериментов. Личные заметки нужны для фиксации механизмов, ошибок и QA-связей. Сложные темы нужно пересматривать точечно: через конкретный вопрос, пример и повторную проверку.

Для Automation QA Engineer главный принцип такой: после каждой темы нужно понимать не только учебный пример, но и место этой темы в тестовом коде.
