# Проверяемые задачи

Каталог зеркалит структуру глав: `tasks/<часть>/<глава>.tasks.mjs` соответствует
`docs/<часть>/<глава>.md`.

Файл экспортирует массив задач. Формат:

```js
export default [
  {
    id: 'js-07-counter',          // уникален во всей книге, латиница и дефисы
    title: 'Счётчик на замыкании',
    difficulty: 'easy',            // easy | medium | hard
    lang: 'js',                    // js | ts | api | sql | playwright
    prompt: 'Что нужно сделать.',  // условие задачи
    starter: `function createCounter() {\n  // ваш код\n}`,
    hints: [
      'Подсказка первого уровня: направление.',
      'Подсказка второго уровня: конкретный приём.'
    ],
    tests: [
      {
        name: 'первый вызов возвращает 1',
        code: `const next = createCounter();\nexpect(next()).toBe(1);`
      }
    ],
    solution: `function createCounter() {\n  let count = 0;\n  return () => ++count;\n}`
  }
]
```

## Правила

- `id` не меняется после публикации: по нему хранится прогресс читателя.
- `tests` — то, что читатель не видит до решения. Каждая проверка получает
  отдельное имя, чтобы отчёт говорил, **что** не сошлось, а не только «не прошло».
- `starter` должен запускаться без синтаксических ошибок: читатель начинает
  с рабочего каркаса, а не с исправления опечаток.
- `hints` идут от общего к конкретному. Последняя подсказка не должна быть
  решением целиком.
- `solution` открывается только после решения или явного отказа.

## Подготовка данных для задач стенда

Иногда без подготовки проверки не отличают правильное решение от неправильного.
Тогда задача объявляет `standSetup` — код, который выполняется до проверок и
получает `api`:

```js
standSetup: `await api.post('/work-items', {
  title: 'Запись, не относящаяся к seed',
  description: 'Создана подготовкой задачи',
  priority: 'LOW'
});`
```

Подготовка и решение работают в одном test run, поэтому удаляются вместе с ним.
`standSetup` допустим только для задач стенда.

## Запись в базу: `transaction: true`

Задача с `lang: 'sql'` может объявить `transaction: true`. Тогда ранер
выполняет решение между `BEGIN` и `ROLLBACK`, причём откат идёт в `finally`.
Это позволяет давать задачи с записью — вставками, обновлениями и даже
созданием таблиц в схеме `sandbox`, — не оставляя следов на общем стенде.

Учётная запись проверки доступна только на чтение в рабочих схемах, но имеет
право `CREATE` в схеме `sandbox`. Временные таблицы недоступны.

Запрос из нескольких инструкций возвращает несколько результатов: проверкам
достаётся `rows` последней из них.

## Языки

| `lang` | Где выполняется |
| --- | --- |
| `js`, `ts` | В браузере, в песочнице страницы |
| `api`, `sql` | Локально против учебного стенда через CLI |
| `playwright` | Локально, в настоящем браузере против учебного стенда |
| `grpc` | Локально, настоящим вызовом gRPC к стенду |

Решение задачи `playwright` экспортирует функцию, получающую объект
`{ page, baseUrl, api }`:

```js
export default async function solve({ page }) {
  await page.goto('/login');

  return { title: await page.getByRole('heading').innerText() };
}
```

Проверкам доступны `result`, `page`, `api`, `baseUrl`, `query` и `source`.
Браузер закрывается после проверок, поэтому обращаться к `page` в них можно.

`source` — текст файла решения. Он нужен главам, где предмет урока — форма
кода, а не только результат: например, что селекторы живут в page object,
а не в сценарии.

```js
{
  name: 'в сценарии нет поиска элементов',
  code: `const body = source.slice(source.indexOf('export default'));
expect(/page\.locator|getByRole/.test(body)).toBe(false);`
}
```

Проверять форму кода стоит только там, где она и есть тема главы: в остальных
случаях такая проверка запрещает читателю решать задачу по-своему.

> **Ограничение:** данные, созданные через интерфейс, принадлежат test run
> сессии UI, а не токену API, поэтому `api.cleanup()` их **не удаляет**.
> Пока это не решено, задачи уровня интерфейса должны читать состояние стенда,
> а не создавать записи.

Решение задачи `api` получает два аргумента: подготовленный клиент и адрес
стенда.

```js
export default async function solve(api, baseUrl) {
  // baseUrl нужен, когда запрос идёт в обход клиента — например, без токена.
}
```

Решение задачи `grpc` получает объект `{ client, metadata, grpc, token, target, api }`:

```js
export default async function solve({ client, metadata }) {
  return new Promise((resolve, reject) => {
    client.GetWorkItem({ id }, metadata, (error, response) => {
      if (error) reject(error);
      else resolve(response);
    });
  });
}
```

`client` — клиент службы `WorkItemService`, собранный из того же
`sut/contracts/proto/work_items.proto`, по которому работает сервер.
`metadata` уже содержит токен; `token` и `grpc` нужны задачам, которые
собирают метаданные сами. Обёртки над колбэком намеренно нет: превращение
вызова в промис — тема глав про unary-вызовы.

Проверкам дополнительно доступны `grpc`, `client` и `metadata`, поэтому код
отказа сверяется с константой (`grpc.status.NOT_FOUND`), а не с числом.
Канал закрывает ранер после проверок.

Задачи с языком стенда требуют `npm run sut:up` и проверяются командой
`npm run task:verify <id>`.

## Проверка

```bash
npm run tasks:build       # собрать и проверить формат
npm run tasks:solutions   # эталон проходит свои проверки, стартовый код — нет
npm run tasks:check       # то же плюс проверка движка в браузере
```

Сборка падает при дублирующемся `id`, пустых `tests` и незаполненных полях.
`tasks:solutions` дополнительно ловит две частые ошибки автора: задачу,
которую невозможно решить, и задачу, которая засчитывается сразу.

## Имена, занятые контекстом проверок

Проверка выполняется как функция с параметрами `expect`, `rows`, `rowCount`,
`result`, `api`, `query`, `baseUrl`, `page`, `source`, `grpc`, `client`,
`metadata`. Объявить переменную с таким именем нельзя — получится
`Identifier 'rows' has already been declared`, и проверка упадёт не по существу.
Называйте свои переменные иначе: `dbRows`, `titleRows`, `apiResult`.

## Проверки одной задачи делят область видимости

Все `tests` задачи выполняются в общем контексте, поэтому `const rows` в двух
проверках подряд даёт `Identifier 'rows' has already been declared`, и падают
обе. Имена переменных в пределах задачи должны быть разными:

```js
{ name: 'заголовок', code: `const titleRows = await query(...)` },
{ name: 'версия',    code: `const versionRows = await query(...)` }
```

## Отклонённые промисы в проверках

Если проверка создаёт отклонённый промис, ему нужен собственный обработчик:

```js
const rejected = Promise.reject(new Error('x'));
rejected.catch(() => {});          // страховка
expect(await solve(rejected)).toBe('unknown');
```

Без этой строки неверное решение оставит отклонение без обработки, и Node
завершит процесс проверок целиком — падать будет весь прогон, а не одна задача.
